# 0020. Canvas2D-проекция конструктора планера

- Статус: Принято
- Дата: 2026-08-19

## Решение

Конструктор стен — **вторая проекция того же документа**: `packages/planner/src/projection/canvas2d/` рядом с `projection/three/` (слой `projection/`, ADR 0015 таблица слоёв; решение автора Q17 [аудита](../product/architecture/competitor-practices-audit.md) — как roomtodo, отдельный Canvas-2D вьювер, но без второй модели). Рисует чертёжный вид ([спека 08](../product/features/planner/08-cameras-views.md) «Виды») из документа, `DerivedFloor` (ADR 0017 C1) и `ToolState` (ADR 0019 E1); в документ не пишет; принимает мышь и переводит её в координаты плана для `tools` (ADR 0019 E5). Мутации/undo — [ADR 0018](./0018-mutatsii-tranzaktsii-i-undo-planera.md), автомат инструментов и ввод — [ADR 0019](./0019-avtomat-instrumentov-i-vvod-planera.md); здесь — только вьювер: жизненный цикл, что рисует, камера, экран ↔ план, луп, композиция.

### Класс и жизненный цикл (P1)

`Canvas2dProjection(manager, canvas, { frameBudget, logger, getContext? })` — сигнатура и порядок инициализации как у `ThreeProjection` (задача 0049): `RenderLoop` (валидация бюджета) → 2D-контекст (`getContext` из опций, дефолт `canvas.getContext('2d')`; нет контекста → исключение, `createPlanner` освобождает уже поднятое) → подписки → `ResizeObserver`. Канвас — **второй `<canvas>` в `<Planner />`** (P6), 2D-контекст, тот же контейнер, что у Three-канваса. Активна при `manager.view.get().activeView === 'constructor'`: вне конструктора кадров не рисует (P5). Подписки: `on('document:changed')`, `on('tools:changed')`, `on('view:changed')` → `invalidate()` (плюс смена активности по `view:changed`); DOM — `pointer*`/`wheel`/`dblclick`/`contextmenu` на своём канвасе, `blur` окна (P3–P4). Наружу: `invalidate()`, `isRendering`, `isDisposed`, `getStats(): { frame }` (счётчик отрисованных кадров, то же имя поля, что у Three — гвард слоя 3, в покое не растёт), `getViewport()`, `fitToContent()`, `resetCamera()`, `dispose()`; `planToView/viewToPlan` — чистые функции `document/geometry/viewport.ts` от `Viewport` (P4), их же зовут снап/хит-тест, проекция и DOM-оверлей. `dispose()` в обратном порядке: DOM-слушатели → подписки шины → `ResizeObserver.disconnect()` → `loop.dispose()`; повторный — no-op. Логгер — DI-опция, как в 0049.

### Что рисует и откуда (P2)

Один кадр = полная перерисовка канваса **по запросу** (не по таймеру): `document.get()` (активный этаж, v0 — единственный), `document.getDerived()`, `tools.get()`. Позиция точки для любого слоя — `overrides[id] ?? layout.points[id]`, где `overrides = ToolState.pointOverrides` при драге (граница D ↔ E, ADR 0018/0019): live-драг точки/стены рисуется без ретриангуляции и без мутации документа, треугольники и обводы держат id точек (ADR 0017 C1). Слои снизу вверх, стили (цвета, толщины, пунктир, шрифты) — константы в одном месте по макету, не в ADR:

| Слой                        | Источник                                                                                                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Комнаты (заливка/штриховка) | `DerivedFloor.rooms[].outline` с `holes` (`evenodd`), `hidden` — пропуск                                                                                                                          |
| Стены-тела (плоские серые)  | `DerivedFloor.walls[].triangles` — fill-группы, не лента (ADR 0017 C1)                                                                                                                            |
| Грани контуров              | `layout.contours[]` (`outer`/`inner`), сторона под hover/выделением — акцентом                                                                                                                    |
| Хендлы точек                | `layout.points` (кружки), hover/выделенная — акцентом; `ToolState.editing.hover/selection`                                                                                                        |
| Превью рисования            | `ToolState.making-*`: точки, квады ленты `preview`, прямоугольник, «живой» сегмент к `cursor`                                                                                                     |
| Гайды/крест                 | `ToolState.snap`: `alignerX/alignerY/bisAnchor` — пунктир к источнику, параллельный пунктир второй грани, крест курсора ([спека 01](../product/features/planner/01-walls-and-contours.md) «Снап») |

**Не на канвасе:** подписи размеров сегментов, live-инпуты длины/ширины и подписи комнат (имя + площадь) — **DOM-оверлей `ui/`** (React), один слой над обоими канвасами: позиции считает через `planToView` проекции, viewport берёт из `m.tools.get().viewport` (селектор `usePlannerSelector`, обновляется на `tools:changed`), геометрию — из `document.get()`/`getDerived()`; отдельного канала подписки на проекцию нет; пороги видимости 30/45/70 px и правила ориентации текста ([спека 07](../product/features/planner/07-measurements.md)) — в оверлее (задача 0060). Мебель в конструкторе (приглушённые силуэты, спека 08) — шаг 5+, форма слоя не меняется.

### Камера конструктора (P3)

Камера — **локальное состояние проекции**: `{ scaleIndex, center: PlanPosition }`; в `Document.view` её нет (`ViewCameras` — только `plan/orbit/walk`, ADR 0016 B7), не сохраняется, не переживает пересоздание планера. Единицы: `scale` = CSS px на 1 см, база `1.0` — тогда `SNAP_DIST = 10 px` = 10 см при базовом зуме (спека 01 «Пороги»). Дискретная шкала — таблица-константа проекции `CONSTRUCTOR_ZOOM_SCALES` из 41 значения `0.05×…10.11×`, индекс 20 = `1.0×` — как у конструктора roomtodo (реверс 08 «Конструктор (0)», `scaleVaues` 60571–60576; верифицировано по исходнику, задача 0052); спека 08 для конструктора говорит только «собственный дискретный зум», её «41 шаг» — про 2D-план/3D-orbit, берём ту же длину шкалы по аналогии; дефолт — индекс 20, центр `(0, 0)`. Жесты (спека 08 «2D top-view», «Клавиатура и мышь»): колесо — шаг индекса ±1 **вокруг курсора** (точка плана под курсором остаётся под ним); пан — ПКМ-драг или Space+ЛКМ (`setPointerCapture`, `contextmenu` на канвасе подавлен); стрелки — через keymap → `tools.key({ kind: 'nudge', dx, dy, factor })`, и если автомат ответил `{ handled: false }` (нет выделения — ADR 0019 E5) — проекция панорамирует шагом (константа в px, Shift — `factor`); «в центр» (`fitToContent()`) — bbox всех `layout.points` этажа с полями → ближайший шаг шкалы, не превышающий fit; пустой этаж → дефолт; `resetCamera()` — дефолт (спека 08 «клик по активной кнопке вида — сброс камеры»). Камера локальна, но **каждое изменение viewport попадает в `tools.setViewport` → `tools:changed`** — осознанное исключение из ADR 0015 «покадровое движение камеры в шину не пускать»: Three-проекция при этом приостановлена (P5), селекторы `useSyncExternalStore` дёшевы, а снапу и DOM-оверлею viewport нужен синхронно (ADR 0015 A5/A7 уточняются по месту). Ввод указателя, не относящийся к камере (ЛКМ без Space, `dblclick`, движение), уходит в `tools.pointerDown/Move/Up/doubleClick(input: PointerInput)`, где `PointerInput = { x, y, mods: { ctrl, meta, shift, alt }, button }` в координатах плана (`viewToPlan`); `pointercancel` → `tools.pointerCancel()`, `blur` окна → `tools.blur()` (ADR 0019 E5).

### Экран ↔ план (P4)

Единый тип `Viewport` и чистые функции над ним — **`document/geometry/viewport.ts`** (слой `document/`, ADR 0015: без DOM/Three; отсюда его импортируют `engine/` — поле `ToolState.viewport`, геометрия снапа/хит-теста, проекция и `ui/`); проекция лишь подставляет текущее значение и **единственная пишет** его (`tools.setViewport`):

```ts
type Viewport = { scale: number; center: PlanPosition; width: number; height: number }; // px/см, см, CSS px
planToView(v, p) = { x: (p.x − v.center.x) · v.scale + v.width / 2, y: v.height / 2 − (p.y − v.center.y) · v.scale };
viewToPlan(v, s) — обратное; viewportBounds(v): bbox плана — для куллинга снапа (ADR 0019 E2).
```

Ось `y` плана — **вверх на экране**, как ортокамера Three в 0049 (экранное «вверх» = `+y` плана): один и тот же документ в конструкторе и 2D-плане не зеркалится. `width/height` — CSS px контейнера из `ResizeObserver` на `canvas.parentElement` с `box: 'device-pixel-content-box'` (фолбэк — обычное наблюдение), буфер = CSS × `devicePixelRatio`, `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)` — как в 0049, DPR не капится. На любое изменение viewport (зум/пан/resize) — `getViewport()` отдаёт новый замороженный объект и проекция зовёт `tools.setViewport(viewport)` (тот же тип; `ToolState.viewport` — источник для снапа, куллинга и DOM-оверлея) и `invalidate()`.

### Render-on-demand и переключение с Three (P5)

`RenderLoop` — **общий**: переезжает `projection/three/RenderLoop.ts` → `projection/RenderLoop.ts` вместе с `FRAME_BUDGET` и тестом; класс не меняется (планировщик параметризован — задача 0049). `invalidate()` Canvas2D-проекции — по `document:changed`, `tools:changed`, `view:changed`, resize, интеракциям камеры. **Взаимная приостановка:** у каждой проекции есть набор «своих» видов (`canvas2d` — `constructor`; `three` — `plan | orbit | walk`); пока активен чужой вид, `invalidate()` только ставит флаг «грязно», кадры не планируются; при `view:changed` на свой вид — один `invalidate()` (флаг сбрасывается кадром). Общая база (`ProjectionBase`/утилита «активные виды») — деталь имплементации. Неактивный канвас скрывается атрибутом `hidden` React-обёрткой по `usePlannerSelector(m => m.view.get().activeView)`; размер контейнера от этого не меняется, поэтому `ResizeObserver` обеих проекций молчит и буферы не пересчитываются.

### Композиция (P6)

- `createPlanner({ canvas: { three, canvas2d }, projectId, logger, frameBudget }) → { manager, projections: { three, canvas2d }, dispose }`; порядок подъёма: документ → менеджер → `three` → `canvas2d` → клавиатура; `dispose` — обратный: клавиатура → `canvas2d` → `three` → менеджер; если любая проекция не поднялась — всё поднятое освобождается, ошибка пробрасывается (как 0049).
- `projection/input/keyboard.ts` — **единственный владелец клавиатуры** (ADR 0019 E5): один `keydown`/`keyup` на `window`, guard «фокус в input/textarea/contentEditable → не перехватывать клавиши, конфликтующие с вводом текста» (команды уровня документа проходят — сейчас это ровно Ctrl/Cmd+S), чистый keymap → `KeyAction`; все действия клавиш (`cancel/undo/redo`, стрелки как `nudge`) → `tools.key(...)`, ответ `{ handled: false }` на `nudge` → пан проекции (P3); `keyup` нужен только для состояния «Space зажат», которое отдаётся Canvas2D-проекции. Живёт в `createPlanner`, не в React; панель 0061 клавиш не вешает.
- `<Planner />` — **контейнер** (размер задаёт страница через `className`) и одновременно **строка макета** (задача 0089): слева колонка рейла 60px, справа **рамка холста** (`position: relative`, отступ, радиус и граница 1px по макету, `overflow: hidden`). Два `<canvas key={projectId}>` лежат абсолютом **на всю рамку**, а не на весь контейнер (Three снизу, Canvas2D сверху, неактивный — `hidden`), над ними внутри той же рамки — DOM-оверлей конструктора (`ui/`, компонент пакета) и `children` — панели скина (0061). Рейл обязан стоять **снаружи** рамки (принятый каркас макета), поэтому он и живёт в контейнере, а не в скине, и его колонка занята с первого кадра: иначе рамка сжималась бы уже после того, как проекция её измерила. `PlannerContext` отдаёт `PlannerInstance` (`manager` + `projections`): `usePlannerManager()` не меняется, добавляется `usePlannerProjections()` для действий, локальных вьюверу — кнопка «в центр» → `projections.canvas2d.fitToContent()`, клик по активной кнопке вида «конструктор» → `resetCamera()` (уточнение ADR 0015 A4, правится по месту). Оверлею подписей проекция не нужна: viewport — в `ToolState`, `planToView` — чистая функция. Первый реальный потребитель `activeView = 'constructor'`: новый проект открывается в конструкторе (ADR 0016 B7).

### Тестовый контракт (P7)

Jest (node): `planToView/viewToPlan` — round-trip, знак `y`, центр/масштаб, `viewportBounds`; шкала — 41 шаг, границы (индексы 0/40 не выходят за таблицу), зум вокруг курсора держит точку под курсором; `fitToContent` — bbox/пустой этаж; keymap и guard инпутов; `RenderLoop` — существующие 14 кейсов после переезда. Jest jsdom: `pointerdown/move/up`, `wheel`, ПКМ/Space+ЛКМ на канвасе → `tools.*` в координатах плана / камера, `keydown` → `tools.key`; `hidden` следует за `activeView`; jsdom не даёт `getContext('2d')` — контекст приходит в проекцию через DI-опцию `getContext` (дефолт — `canvas.getContext('2d')`), в тестах — фейк. Playwright (расширение `apps/platform/e2e/planner-render-guard.spec.ts`, ручка `onReady` → `projections`): idle — `frame` обеих проекций не растёт; переключение вида туда-обратно — конечное число кадров и снова покой; unmount — оба канваса сняты, утечек нет; e2e мышью — контур «Стены» реальными кликами → комната → undo → redo (задачи 0056/0057).

## Почему

Отдельный Canvas2D, а не оверлеи в Three-ортосцене: конструктор — чертёжный вид с пиксельно-точными пунктирами, хендлами и крестом (спека 08), а инструментальные оверлеи в Three требуют screen-space толщин и `LineDashedMaterial` (аудит Q17, факты «против»); у roomtodo конструктор — самостоятельный Canvas-2D вьювер (реверс 08, «Конструктор (0)»), и это принято решением Q17 при одном документе. Камера локальна, потому что её никто не хранит: спека 10 «Что сохраняется» перечисляет камеры только 2D-плана/orbit/walk, спека 08 — «не синхронизируется с камерами 2D-плана/3D», у roomtodo камера конструктора сериализуется фикс-заглушкой (реверс 08, 2c); заводить `Document.view.cameras.constructor` значило бы второй формат камеры и версию документа ради несохраняемого. Подписи, инпуты и подписи комнат — DOM: спека 07 требует «клик по подписи превращает её в инпут», Tab между инпутами, Enter/Esc — фокус, IME и навигация нативны в DOM, на канвасе это ручной хит-тест текста и своя клавиатура; аудит 07 (rework) — один слой над рендером, позиция выводится из проекции на каждый рендер, а не «пул из 4 инпутов с ручным пересчётом при зуме» (`updateInputsAfterDraggingCanvasOrZoom`, реверс 07 D). Общий `RenderLoop`, а не свой: класс уже без Three и с параметризованным планировщиком (0049), второй луп — вторая точка ошибок реентерабельности. Приостановка Three при активном конструкторе: `tools:changed` идёт на каждый `pointerMove` (ADR 0019 E1) и через wildcard `*` дёргает `invalidate()` всех проекций — без приостановки скрытый WebGL-канвас рисовал бы кадры на каждое движение мыши, а гвард idle FPS ≈ 0 (0049) терял бы смысл. `scale` в px/см с базой 1.0 — потому что пороги спеки 01 заданы в экранных px и «10 px = 10 см при базовом зуме»; шкала 41 шаг — как у конструктора roomtodo (реверс 08, верифицировано, задача 0052), той же длины, что шкала 2D-плана/3D-orbit спеки 08 — юзер видит одинаковую «густоту» зума во всех видах. Отсекается: перерисовка каждый кадр (аудит 01-walls rework — у нас on-demand); текст размеров на канвасе; синхронизация камеры конструктора с 2D-планом (спека 08 «не синхронизируется» — независимые зумы, как у roomtodo); свой второй `ResizeObserver`-подход или DPR-кап (как 0049 — desktop-only).

## Что важно знать

- **DOM-оверлей ре-рендерится на каждый `tools:changed` (в т.ч. pointerMove) и на каждое изменение viewport** — десятки DOM-узлов для квартиры приемлемо; если подписей станут сотни (шаг 5+), мемоизировать по `document`/viewport, а не переносить текст на канвас.
- **Камера конструктора теряется** при пересоздании планера (смена `projectId`) и при перезагрузке — по спеке. `document.load` камеру не трогает: начальный fit при открытии сохранённого проекта — вопрос ADR F/шага 3 (парковка); при новом проекте — дефолт индекс 20, центр `(0, 0)`.
- **`<canvas key={projectId}>` — теперь два канваса**, оба с `key`; `<Planner />` из фрагмента становится контейнером — `className` страницы переезжает на контейнер (`h-full w-full`; `block` из задачи 0056 снят в 0089 — его всё равно перебивал бы `display: flex` строки макета), `Planner.test.tsx` правится.
- **Переезд `RenderLoop`** — правка импортов Three-проекции и её теста (задача 0056); публичный API не меняется (`FRAME_BUDGET` наружу не экспортируется).
- **Three при `constructor` не рендерит**: гвард 0049 про idle сохраняется как есть; добавляется проверка «переключение вида даёт конечное число кадров» и «в конструкторе `three.getStats().frame` не растёт при движении мыши». `onReady` теперь отдаёт `projections` — `planner-render-guard.spec.ts` и `plannerReadyEvent` правятся под новую форму.
- **Скрытие через `hidden` безопасно только потому, что `ResizeObserver` смотрит на контейнер**, а не на канвас: скрытый канвас имеет нулевой rect, наблюдение за ним обнулило бы буфер.
- **`ToolState.viewport` и `getViewport()` — одно значение**: `tools.setViewport` зовётся на каждое изменение viewport синхронно, поэтому DOM-оверлей читает viewport селектором `m => m.tools.get().viewport` и не зависит от проекции; проекция — единственный, кто его пишет. Цена — `tools:changed` на каждый шаг пана/зума (плюс к pointerMove): для React это один `getSnapshot`, для приостановленной Three — флаг; если появится тяжёлый подписчик шины, throttle ставить у него, а не выключать канал.
- **DPR не капится** (desktop-only, как 0049); ретина 2× — буфер ×4 и `setTransform(dpr, …)` на каждый кадр.
- **Ось `y` вверх** согласована с ортокамерой Three (`PLAN_UP_IN_WORLD`, 0049); экранная ось Canvas2D направлена вниз, поэтому знаки офсетов подписей и углов поворота текста (спека 07) фиксируются тестами `planToView`, а не переносятся из реверса как есть.
