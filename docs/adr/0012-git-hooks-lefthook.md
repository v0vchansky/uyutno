# 0012. Git-хуки: lefthook + lint-staged, pre-commit с ESLint / Prettier / tsc

- Статус: Принято
- Дата: 2026-08-09
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0011 зафиксировал ESLint 10 + Prettier 3 и явно вынес git-хуки в отдельное решение. Работа идёт через вайбкодинг — AI-агент часто коммитит по несколько раз в час, и без хука кривой код (незапущенный линт, битые типы, забытый форматтер) регулярно будет утекать в историю. Ручной запуск `pnpm lint` / `pnpm format` / `pnpm typecheck` перед каждым коммитом не соблюдается ни человеком, ни агентом.

## Драйверы решения

- **Не пропускать в историю очевидно кривой код** (не отформатирован, падает линт, не компилируется).
- **Скорость коммита.** Хук на pre-commit должен отрабатывать за секунды, а не за минуты — иначе его начнут обходить.
- **Простота конфига.** Один компактный файл, а не набор shell-скриптов, которые надо синхронизировать.
- **Минимум магии.** Единая конвенция для всех разработчиков и AI-агента.
- **Отсутствие блокировок при срочных коммитах.** Возможность руками сказать «сейчас без хука» без правки конфига.

## Рассмотренные варианты

### Инструмент управления хуками

- **Вариант A1: lefthook** — Go single-binary, YAML-конфиг, parallel-запуск команд внутри хука. Ставится как npm-пакет (тянет соответствующий бинарь).
- **Вариант A2: husky** — де-факто стандарт, node-based, ставит директорию `.husky/` с shell-скриптами (по файлу на хук). Sequential по умолчанию.
- **Вариант A3: simple-git-hooks** — вся конфига в `package.json`, минимально возможный.
- **Вариант A4: без специальной обвязки** — хуки прописываются вручную в `.git/hooks/` и синхронизируются самописным bash-скриптом.

### Фильтрация staged files

- **Вариант B1: lint-staged** — стандарт, фильтрует по glob'ам, запускает команды только на staged.
- **Вариант B2: встроенные механизмы lefthook** (`glob:` + `files: git diff --name-only --cached`). Позволяет обойтись без lint-staged.

### Состав хуков

- **Вариант C1: pre-commit — lint + format на staged; type-check всей монорепы.**
- **Вариант C2: pre-commit — только lint + format; type-check на pre-push.**
- **Вариант C3: всё на pre-commit включая тесты.**

### Что делать при падении хука

- **Вариант D1: fail (non-zero exit блокирует коммит).** Стандарт.
- **Вариант D2: warning-only.**

### Bypass через `--no-verify`

- **Вариант E1: разрешён** (стандартное поведение git).
- **Вариант E2: заблокирован** через дополнительную обвязку.

## Выбранный вариант

**Выбраны: A1 + B1 + C1 + D1 + E1.**

Итог:

- **Инструмент:** lefthook. Конфиг — единый `lefthook.yml` в корне монорепы.
- **Фильтрация:** lint-staged для ESLint/Prettier на staged файлах. Не заменяем встроенным lefthook-механизмом ради того, что lint-staged даёт (умный batching, работает под всеми ОС одинаково, стандартная модель, привычная агенту).
- **Pre-commit-хук:**
  1. `lint-staged` — ESLint `--fix` на staged `.ts`/`.tsx`/`.js`, затем Prettier `--write` на staged `.ts`/`.tsx`/`.md`/`.json`/`.yaml`/`.css`.
  2. `tsc --noEmit --incremental` — type-check всей монорепы (инкрементальный кеш `.tsbuildinfo` в `.gitignore`).
  3. Оба шага запускаются lefthook'ом **параллельно** (`parallel: true`), потому что не пересекаются по ресурсам и вместе укладываются в секунды.
- **Pre-push-хук:** пусто. Заведём отдельным изменением конфига (не ADR), если появится потребность (например, тесты в CI начнут тормозить и захочется отсечь до пуша).
- **Fail-режим:** non-zero exit блокирует коммит. Стандарт.
- **`--no-verify`:** разрешён. Осознанное поведение для WIP-коммитов, экстренных фиксов и случаев, когда хук временно сломан.

## Обоснование

### Почему lefthook, а не husky

- **Один YAML вместо папки со скриптами.** `.husky/pre-commit`, `.husky/pre-push`, `.husky/_/*` — папка с несколькими файлами, которые надо ревьюить по одному. lefthook — один `lefthook.yml`, все хуки видны разом.
- **Parallel-запуск.** У нас на pre-commit два независимых шага (lint-staged и tsc). lefthook гоняет их одновременно из коробки (`parallel: true`); в husky для этого пришлось бы вручную писать shell с `&` и `wait`, теряя читаемость.
- **Single self-hosted binary.** Совпадает с философией «bash + self-hosted» из общих принципов проекта. husky полагается на node-обвязку.
- **husky не выигрывает ничего существенного** для нас: гибкость shell-скриптов не нужна, потому что вся логика — «запусти команду X» и «запусти команду Y», а это lefthook делает декларативно.

Минус lefthook: чуть менее популярен, чуть меньше готовых примеров. Компенсируется тем, что его конфиг короткий и читается за минуту.

### Почему lint-staged, а не встроенный lefthook-фильтр

- Стандарт для JS-мира, любой AI-агент знает наизусть.
- Умеет группировать команды по глобам в одном конфиге; переносится между husky/lefthook без изменений.
- Встроенный lefthook-фильтр (`files: git diff --name-only --cached | grep ...`) работает, но менее выразителен и хуже читается.

### Почему type-check на pre-commit, а не на pre-push

- **AI-агент коммитит часто.** Между коммитами часто по 30 секунд — если type-check уедет на pre-push, к моменту push'а накопится 10+ коммитов, часть которых ломает компиляцию. Разбирать «какой из десяти сломал типы» — дороже, чем поймать сразу.
- **`--incremental` быстрый.** Первый запуск может занять несколько секунд, дальше — доли секунды при небольших изменениях. Приемлемо для коммита.
- **Всегда можно перекинуть на pre-push** через правку YAML, если пойдёт откат по скорости.

### Почему pre-push пока пустой

- Тестов ещё нет — тестировать нечего.
- CI ещё не заведён — не с чем стыковать.
- Заведём хук по мере появления реальных потребностей, без ADR.

### Почему `--no-verify` разрешён

- Стандартное поведение git, блокировать его — воевать с базовым инструментом.
- Нужен для WIP-коммитов в личной ветке, экстренных фиксов, коммитов при временно сломанном хуке.
- Дисциплина bypass'а — вопрос практики, а не технической блокировки. При соло-разработке некому нарушать её кроме себя.

## Что фиксируется этим ADR

- Инструмент управления хуками — lefthook (мажор **2**), конфиг в корне (`lefthook.yml`).
- Фильтр staged файлов — lint-staged (мажор **17**).
- Единственный активный хук — pre-commit. Внутри: lint-staged (ESLint + Prettier) и `tsc --noEmit --incremental`, оба параллельно.
- Non-zero exit блокирует коммит.
- `--no-verify` разрешён.
- Активация хуков — через `pnpm install` (`prepare`-скрипт или `postinstall`, конкретика — задача имплементации).
- Конкретные npm-скрипты (`pnpm typecheck`, состав globs у lint-staged) — уровень имплементации, не ADR.

## Что НЕ фиксируется этим ADR

- **Pre-push-хук** — сейчас пусто, добавим по факту без ADR.
- **CI-интеграция** — отдельно, когда появится CI.
- **Commit-msg-хук** (проверка формата коммит-сообщений) — не берём. Формат коммитов свободный, только на русском (см. отдельный feedback).
- **Проверка на большие файлы, секреты в коде, `console.log`** — расширяем конфиг lefthook по мере надобности, без ADR.

## Последствия

### Плюсы

- Кривой код (незапущенный линт, битый формат, ошибка компиляции) не попадает в историю ни в человеческих, ни в AI-коммитах.
- Параллельный запуск на pre-commit — коммит остаётся быстрым.
- Один компактный YAML — легко ревьюить и править.
- `--no-verify` даёт аварийный клапан без правки конфига.
- Lefthook — single-binary, без node-обвязки, соответствует общей философии проекта.

### Минусы

- **Дополнительный шаг при первом `pnpm install`** — скачивается lefthook-бинарь, активируются хуки. Приемлемо, происходит один раз.
- **Type-check на каждом коммите может тормозить**, когда монорепа разрастётся. Триггер пересмотра — ниже.
- **`--incremental` иногда флакает** при переключении веток (некорректный кеш) — лечится удалением `.tsbuildinfo` и одним лишним запуском. Редкий случай.
- **lefthook чуть менее популярен husky** — часть готовых рецептов из статей придётся переводить с husky-синтаксиса. Тривиально.

## Как проверить/пересмотреть

- **Type-check на pre-commit начал стабильно занимать более ~5 секунд** → перенести в pre-push, оставить на pre-commit только lint + format.
- **AI-агент или коллеги начали злоупотреблять `--no-verify`** → разбираться с причинами (медленный хук, ненужная проверка), а не блокировать флаг.
- **Появилась потребность в commit-msg-валидации** (например, обязать префикс тикета) → отдельный ADR, заводим commit-msg-хук.
- **Появился CI и он делает те же проверки надёжнее и быстрее** → рассмотреть, оставлять ли pre-commit-хук или полагаться только на CI. По умолчанию оставляем pre-commit как first line of defence.
