# 0008. SSR-стратегия v0: рендерим только шелл, данные — всегда на клиенте

- Статус: Принято
- Дата: 2026-08-09
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0003 зафиксировал SSR через Express + React и TanStack Query для управления серверным состоянием на клиенте. Не решено, **как данные попадают в React-дерево при первом заходе на URL**: тянутся ли они на сервере (isomorphic SSR с prefetch/dehydrate/hydrate), или сервер отдаёт HTML-шелл без данных, а всё запрашивается уже на клиенте.

Разбор наших v0-страниц:

| Страница | Индексация | Данные для первого рендера | Нужен ли SSR-prefetch |
|---|---|---|---|
| Лендинг `/` | Индексируется | Вшитый в разметку текст, статика | Нет |
| `/login`, `/register`, `/forgot-password`, `/reset-password`, `/auth/callback/:provider` | Не индексируется | Пусто, чистые формы | Нет |
| `/project` (список) | `noindex` | Список из БД, приватный | Нет (мигание допустимо) |
| `/project/:id` | `noindex` | Проект, приватный | Нет (мигание допустимо) |

Ни на одной v0-странице SSR-данные объективно не нужны: публичные страницы статичны, приватные не индексируются и терпят мигание шелл → скелетон → данные.

## Драйверы решения

- **Минимум сложности.** Один разработчик, работа через вайбкодинг. Каждый дополнительный слой (dehydrate/hydrate, cookie loopback, per-request QueryClient с данными, staleTime-дисциплина для гидрированных данных) — источник багов и когнитивной нагрузки.
- **Реальные потребности v0.** Не платить сложностью за возможности, которые ни одна страница не использует.
- **SEO лендинга.** Публичная страница должна отдаваться поисковику (в т.ч. Яндексу) как готовый HTML с текстом и мета-тегами, без ожидания JS.
- **Не выкатывать на будущее.** Фиксируем стратегию v0. При появлении реального SEO-требования к динамическим данным — вернёмся отдельным ADR.

## Рассмотренные варианты

- **Вариант A: Full SPA, без SSR.** Сервер отдаёт пустой `index.html` со скриптом, React рендерит в браузере. Никакого рендера на сервере вообще.
- **Вариант B: SSR только шелла и мета-тегов, данные — всегда на клиенте.** Сервер `renderToString` React-дерева с пустым QueryClient (без prefetch). Клиент `hydrateRoot`, дальше `useQuery` в компонентах тянет данные.
- **Вариант C: Полноценный isomorphic SSR.** Сервер prefetch-ит данные в per-request QueryClient, `dehydrate` → инъекция состояния в HTML, клиент `hydrate`. Cookie исходного запроса форвардятся в HTTP-loopback к собственному API.

## Выбранный вариант

**Выбран: Вариант B.** SSR остаётся для быстрого первого пейнта лендинга и мета-тегов, но не тянет данные — TanStack Query работает только на клиенте.

## Обоснование

### Почему не A (Full SPA)

- Плохо для SEO лендинга. Google JS понимает, но с задержкой; Яндекс — существенно хуже. Для проекта с фокусом на органику из РФ (см. `docs/product/release-v0.md`) — недопустимо.
- Плохо для OG-тегов и превью в мессенджерах: соцсети и Telegram JS не выполняют, читают HTML.
- Плохо для первого пейнта: пустая страница до загрузки бандла.

### Почему не C (Полноценный isomorphic SSR)

- Ни на одной v0-странице SSR-данные не дают пользы. Публичные — статичны, приватные — терпят мигание.
- Тянет за собой существенную сложность: per-request QueryClient на сервере, `dehydrate`/`hydrate`, инъекция состояния в HTML (`window.__QC_STATE__`), forwarding cookie при loopback-запросах, дисциплина `staleTime`, отдельная обработка redirect-ов и 404 при SSR через loader-ы. Каждый пункт — источник багов.
- Заводить это без реальной потребности — переоптимизация. При появлении публичной страницы с динамическим SEO (например, страницы ЖК с реальным содержимым) — вернёмся к вопросу отдельным ADR.

### Почему B — правильный компромисс

- Сохраняет всё, что реально даёт SSR в v0: HTML для поисковика, готовые мета-теги, быстрый LCP лендинга.
- Убирает всё, что в v0 не нужно: prefetch, dehydrate/hydrate, cookie loopback, per-request состояние с данными.
- Одна ментальная модель: **сервер = HTML + CSS + мета, клиент = данные**. Никаких «на сервере через loader, на клиенте через useQuery, а на этой странице по-другому».

## Механизм

### Серверный рендер

Middleware `pageMiddleware` (в `src/server/application/`) на каждый `GET *`:

1. Создаёт **пустой** `new QueryClient()` per-request. Никакой prefetch не выполняется. Инстанс нужен только чтобы `<QueryClientProvider>` в React-дереве не падал.
2. Создаёт `staticHandler` / `createStaticRouter` react-router v8 из общей конфигурации роутов.
3. Рендерит дерево через `renderToString`:
   ```
   <QueryClientProvider>
     <RegistryProvider>
       <StaticRouterProvider>
         <App />
       </StaticRouterProvider>
     </RegistryProvider>
   </QueryClientProvider>
   ```
4. Собирает финальный HTML через `renderToStaticMarkup` от JSX-шаблона: `<html>`/`<head>`/`<body>` — обычный React-компонент, отрендеренный в статичный markup. Никакого `react-dom-factories`.
5. CSS инлайнится в `<style>` внутри `<head>` — избегаем FOUC (мигания нестилизованного контента) на первом пейнте.
6. Отдаёт `<!doctype html>${markup}`.

Ничего не форвардится в API, никаких серверных запросов за данными во время рендера.

### Клиентский bootstrap

`src/client/index.tsx` (entry-point webpack-клиента):

1. Создаёт **один** `QueryClient` на приложение с базовым `staleTime` (минуты) и `refetchOnWindowFocus: false`.
2. Оборачивает `<App />` в `<QueryClientProvider>` → `<RegistryProvider>` → `<RouterProvider>` (react-router v8, `createBrowserRouter`).
3. `hydrateRoot(document.getElementById('root'), tree)`.
4. **Никакого `hydrate(qc, ...)`** — данные тянутся `useQuery` по мере рендера компонентов.

### Access control

- **Auth-check** (залогинен ли вообще) — компонент-обёртка `<ProtectedRoute>` в дереве роутов, оборачивает закрытые страницы. Внутри — `useCurrentUser()` (тонкая обёртка над `useQuery(['currentUser'])`). Если гость — `<Navigate to="/login" replace />`.
- **Entity-access** (есть ли доступ к этому проекту) — API возвращает 404 на приватные ресурсы, к которым у текущего юзера нет доступа (а не 403 — чтобы не подтверждать существование). `useQuery` кидает ошибку, компонент рендерит `<NotFound />`.

Ни то, ни другое не выполняется на сервере: сервер отдаёт шелл, клиент после гидрации проверяет и при необходимости навигирует / рендерит 404.

### Роутинг

- react-router v8, `createBrowserRouter` на клиенте, `createStaticRouter` на сервере.
- **Без loader-ов в v0.** Данные тянутся `useQuery` в компонентах. Loader-ы (и связанная механика prefetch на сервере) — потенциальное будущее расширение, если появятся страницы с SEO-требованием к данным.

### Мета-теги

Статичные title/description для v0 достаточно. Динамические (например, `<title>Название проекта — uyutno</title>`) появятся только на приватных страницах, где SEO не требуется — можно проставлять на клиенте после загрузки данных. Конкретный механизм (`react-helmet-async`, встроенное `<title>` в react-router v8, или ручной `document.title = ...`) — решается при написании скелета, не фиксируется этим ADR.

### Статика

В v0 статика раздаётся Express (`express.static('/static', dist/client)`). Вынос на Nginx/Caddy — при подготовке продакшн-деплоя, отдельным решением.

## Что фиксируется этим ADR

- SSR отдаёт HTML-шелл + CSS + мета-теги, без запросов к данным.
- TanStack Query на сервере — пустой per-request инстанс, только для совместимости с `<QueryClientProvider>`.
- Никакого `dehydrate`/`hydrate`, никакой инъекции QC-состояния в HTML, никакого cookie loopback.
- Клиент — один `QueryClient` на приложение, `useQuery` в компонентах.
- Access control — целиком клиентский: `<ProtectedRoute>` для auth-check, API-404 для entity-access.
- react-router v8, `createBrowserRouter` / `createStaticRouter`, без loader-ов в v0.
- HTML-шаблон — JSX + `renderToStaticMarkup`.
- CSS в v0 инлайнится в `<style>` (против FOUC).
- Статику в v0 раздаёт Express.

## Что НЕ фиксируется этим ADR

- Конкретный механизм мета-тегов (helmet-async vs встроенный react-router API vs ручная работа с `document.title`).
- Формат HTML-шаблона в деталях (что именно в `<head>`, порядок скриптов, preload и т.п.) — задача имплементации.
- Стриминг (`renderToPipeableStream`, `<Suspense>` boundaries) — не заводим в v0.
- Deploy-стратегия статики (Nginx/Caddy/CDN) — отдельное решение при деплое.
- Error boundaries на уровне роутинга — по факту при скелете.

## Последствия

### Плюсы

- Минимум кода в SSR-обвязке. Меньше багов, быстрее разработка.
- Никаких hydration mismatch по данным — на сервере и клиенте изначально одинаковое отсутствие данных.
- Никаких утечек кэша между юзерами: серверный QueryClient пуст.
- Простая ментальная модель: сервер = HTML + мета, клиент = данные. Одно правило на всё приложение.
- SEO лендинга покрыто: HTML с текстом отдаётся мгновенно, поисковик и превью в мессенджерах видят готовый контент.
- Механика доступа целиком в одном месте (клиент), не размазана между middleware / loader / компонент.

### Минусы

- **Мигание на приватных страницах.** Шелл → скелетон → данные. Опыт пользователя после логина: секунда пустоты. Стандартно для SPA (Notion, Figma, Linear работают так же), но всё же не «мгновенный контент».
- **Auth-редирект — после гидрации.** Гость, зашедший по прямой ссылке на `/project/xyz`, увидит шелл, потом произойдёт `<Navigate to="/login">`. Не 302 от сервера.
- **Первое понимание доступа — на клиенте.** Приватные страницы отдаются сервером в виде HTML без учёта авторизации (тот же шелл). Небольшой overhead трафика на «отдать шелл гостю, чтобы клиент его тут же увёл на логин».
- **Если появится страница с SEO-требованием к динамическим данным** (публичный контент из БД) — этот ADR потребует пересмотра или дополнения. В v0 такой страницы нет.

## Как проверить/пересмотреть

- **Появится публичная страница с реальными динамическими данными для SEO** (например, страницы ЖК с содержимым из БД в v1) → пересмотреть в пользу гибридной модели: SSR-prefetch для конкретных публичных роутов, остальное — как есть.
- **LCP лендинга окажется недостаточным** из-за клиентской работы (например, тяжёлый первый рендер) → рассмотреть стриминг или предварительную генерацию.
- **UX «мигания» на приватных страницах станет блокером** (жалобы, показатели, конкурентная разница) → рассмотреть SSR-prefetch для конкретных приватных роутов (потребует cookie forwarding и per-request state).
- **Появится нужда в 302-редиректе на сервере для гостей на приватных URL** (например, SEO-соображения по индексации, или ощутимая экономия трафика) → добавить серверную auth-проверку в page-middleware.
