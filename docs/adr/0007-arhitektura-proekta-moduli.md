# 0007. Архитектура проекта: модульная раскладка, граф импортов, registry-паттерн

- Статус: Принято
- Дата: 2026-08-09

## Решение

### Модули (v0)

| Модуль        | Роль                                                                                                                                                                                                                      | Страницы |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `application` | Модуль-сборщик: собирает `Registry`, настраивает роутинг, монтирует SSR-обвязку, root-layout                                                                                                                              | ✅       |
| `landing`     | Публичная часть сайта: главная, статические страницы, **логин/регистрация/сброс пароля, OAuth-колбэки**                                                                                                                   | ✅       |
| `project`     | Список проектов и страница отдельного проекта (собирает `planner` через DI)                                                                                                                                               | ✅       |
| `auth`        | Библиотека: `AuthService` (getCurrentUser, login, register, logout, OAuth-обмены), стейт текущего юзера. Без страниц                                                                                                      | ❌       |
| `planner`     | Изолированный движок редактора: сцена, инструменты, инспектор, undo/redo. Всё внешнее — через DI-пропсы. Живёт не в `src/client`, а в воркспейс-пакете `@uyutno/planner` (`packages/planner`) с шага 1 планера — ADR 0015 | ❌       |
| `core`        | Base-библиотеки без домена: `logger` (реализация), базовые утилиты. Без UI, без сетевого стека, без доменных ошибок                                                                                                       | ❌       |
| `common`      | Общий UI (обёртки над HeroUI, layout-примитивы), HTTP-клиент (`api` на axios), иерархия ошибок (`AppError` и наследники), `Registry`, `RegistryContext`, хук `useRegistry`. Без страниц                                   | ❌       |

### Граф импортов

Стрелка = «может импортировать». Всё, что не в графе, — запрещено.

```
application ──► всё (сборщик)

landing  ──► core, common, planner, auth
project  ──► core, common, planner, auth
common   ──► core, auth, planner
auth     ──► core, common
planner  ──► —
core     ──► —
```

Следствия:

- `application` может импортировать любой модуль. Никто, кроме `application`, не может импортировать `application`.
- `planner` и `core` не импортируют модули — только внешние библиотеки. `planner` — пакет `@uyutno/planner`: потребители (`landing`, `project`, `common`, `application`) импортируют его как `import { Planner } from '@uyutno/planner'`, а не через `@app/planner`; место в графе от этого не меняется.
- **`auth` и `common` образуют разрешённый двусторонний контур:** `auth` берёт из `common` HTTP-клиент и ошибки, `common` в типе `Registry` ссылается на `AuthService` из `auth` через `import type` (циклические `import type` — норма, см. `apps/platform/CLAUDE.md`). Runtime-цикла нет: сборка `Registry` — только в `application`. Формы логина/регистрации живут не в `auth`, а в `landing`, и используют `common`-примитивы и `useRegistry().authService`.

### Registry-паттерн

**Сборка — в `application`. Контракт и хук — в `common`. Доступ — через React context.**

- В `common`: тип `Registry` (запись из инстансов общих сервисов), React context `RegistryContext`, хук `useRegistry()`.
- В `application`: `new Registry({ logger, authService, httpClient, ... })` — на клиенте один раз при бутстрапе, на сервере — per-request (если нужен request-scoped контекст, например `req-id` для логгера).
- `<RegistryContext.Provider value={registry}>` монтируется на самом верху дерева в `application`.
- Модули достают что нужно через `useRegistry()`.

Циклов в графе импортов нет: `common → auth → core → ⊥`, `common → planner → ⊥`.

### Правила размещения кода в модулях

- **Public API** — только через `index.ts` каждого модуля. `import { X } from 'client/auth'` — ок; `import { X } from 'client/auth/internal/foo'` — нет.
- **Переезд в `common`** — когда некий кусок кода реально нужен в **двух и более** модулях. До этого — живёт локально. Не превращать `common` в свалку.
- **Тесты** — co-location: `foo.ts` + `foo.test.ts` рядом. Никаких `__tests__/`.
- **Клиентский API-слой** — внутри модуля-владельца (`client/project/api.ts`, `client/project/queries.ts`). Общая HTTP-обёртка — в `core`.

### Симметрия на сервере

Те же модули (`application`, `auth`, `project`, `common`, `core`) с теми же правилами импортов. Отличия:

- `planner` на сервере отсутствует — это клиентская библиотека. Исходники пакета `@uyutno/planner` попадают в SSR-бандл через allowlist `webpack-node-externals` (потому что `<Planner />` рендерится страницей `project`), но серверные модули его не импортируют.
- `landing` на сервере отсутствует, пока не появится серверная логика для него (SSR лендинга обслуживается общим SSR-механизмом в `application`).
- Модули заводятся по факту. `apps/platform/src/server/auth/` не создаётся, пока нет реальной серверной логики.

### Layout `apps/platform`

```
apps/platform/
  src/
    client/       # клиентские модули
    server/       # серверные модули
    shared/       # изоморфный код: Zod-схемы API, типы, константы, общие утилиты
  db/
    migrations/   # SQL-миграции dbmate
  webpack/        # конфиги webpack (клиент + сервер)
  public/         # статика
```

`db/migrations/` — на уровне `apps/platform/`, а не в `src/server/`: это не TS-код, а SQL-файлы для CLI-инструмента dbmate (дефолт — `db/migrations/`).

### Энфорс

Правила импортов проверяются через встроенное ESLint-правило `no-restricted-imports`, конфигурируется per-directory через `files` в `eslint.config.js`. Без дополнительных зависимостей. Конкретный конфиг — задача имплементации, не ADR.

### Env-переменные

Формальный слой env-конфигурации (`.env.example`, Zod-валидация env на старте) в v0 не заводится. Один разработчик, никаких секретов на клиенте, на сервере — `DATABASE_URL` и креды OAuth. Дев-дефолты хардкодятся в коде, прод-значения через `process.env` из deploy-скрипта. Отдельный ADR — когда секретов станет много или появится необходимость валидации.

## Почему

Один разработчик, вайбкодинг → архитектурные правила должны быть автоматически проверяемыми, иначе быстро протухнут и AI-агент их не знает по построению. Плоская структура превратится в кашу за месяц, движок редактора начнёт незаметно тащить `auth` и потеряет возможность быть вынесенным в пакет. FSD — избыточная методология для одного разработчика и 7 модулей (решает проблему масштаба команд). Свой минимальный набор — под конкретный проект, модули совпадают с доменами. Голые синглтоны ломаются на сервере: SSR per-request с `req-id` в логгере не выразить синглтоном. Чистое прокидывание через пропсы — много бойлерплейта на глубоких деревьях редактора. Registry в context — компромисс: явная сборка в одном месте, простой доступ через хук, легко мокается в тестах. `useRegistry` в `common`, а не `core`: тип `Registry` включает доменные сервисы (`authService: AuthService`), core не должен знать о доменных модулях. HTTP-клиент и иерархия ошибок (`AppError` и наследники) тоже в `common`: это не «base-библиотеки без домена» (тогда были бы в `core`), а инфраструктура доменных модулей — их использует и `auth`, и `landing`, и серверный error-middleware. `common ↔ auth` — разрешённый двусторонний контур: `common` типизируется через `AuthService` (`import type`, циклы на типах — норма), `auth` берёт из `common` HTTP-клиент/ошибки. Runtime-цикла нет, потому что сборка `Registry` — только в `application`. `no-restricted-imports`, а не `eslint-plugin-boundaries` — встроенное правило, для 7 модулей конфиг компактный, без новых зависимостей. Layout по среде (`client/server/shared`), а не по модулям с вложенной средой: две webpack-сборки должны видеть свои entry-points под одним префиксом. `shared/` отдельно — жёсткое напоминание, что там нет ни Node-only, ни DOM-only API.

## Что важно знать

- **`auth` может брать из `common` HTTP-клиент и ошибки, но не UI.** Форма логина живёт в `landing`, `AuthService.login()` — в `auth`. Разработчик редактирует форму в одном месте, логику — в другом. UI-примитивы в `common` предназначены для страничных модулей (`landing`, `project`), не для сервисов.
- **Login/register страницы в `landing`, а не в `auth`.** Концептуально не «лендинг», но раскладывать в отдельный модуль ради изоляции пока избыточно.
- **Registry должен быть стабильным по референсу** (создаётся один раз при бутстрапе), иначе провайдер ре-рендерит всё дерево на каждое изменение.
- **`planner` — отдельный пакет `packages/planner` уже с шага 1** (ADR 0015, задача 0047), а не «модуль с переездом в v1»: изоляция «без импортов из платформы» — физическое свойство (у пакета нет алиаса `@app/*`), а не только правило линтера.
- **`common` не должен стать свалкой** — критерий переезда «нужно в 2+ модулях», при риске раздутия поднять порог до 3+ или разбить на гранулярные модули.
