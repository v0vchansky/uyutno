# 0007. Архитектура проекта: модульная раскладка, граф импортов, registry-паттерн

- Статус: Принято
- Дата: 2026-08-09
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0002–0006 зафиксировали монорепу, стек фронтенда, стек бэкенда, модель аутентификации и схему БД. Внутри `apps/platform` пока пусто — нужно решить, как раскладывается код: какие модули, что во что может импортировать, где живут страницы, где — общий код, как разные части приложения получают доступ к общим сервисам (логгер, HTTP-клиент, `AuthService`).

Ограничения контекста:
- Один разработчик, работа через вайбкодинг → AI-агент постоянно генерирует код, архитектурные правила должны быть автоматически проверяемыми, иначе быстро протухнут.
- Приложение — единый Express-процесс с React SSR на клиенте и API на сервере (ADR 0003, 0004). Общий изоморфный код (Zod-схемы, типы API) должен где-то жить.
- В v1 движок редактора планируется вынести в отдельный npm-пакет (`packages/*`). Значит, уже сейчас он должен быть спроектирован как изолированная библиотека, не зависящая от бизнес-логики приложения.

## Драйверы решения

- **Явные границы модулей.** Каждый модуль имеет чёткую роль и известный список того, что ему разрешено импортировать. Никаких «дерево импортов сложилось стихийно».
- **Изолируемость движка редактора.** `planner` должен уметь работать без знания о том, что вокруг него — auth, роутинг, API. Всё внешнее — через явные пропсы/DI.
- **Автоматическая проверка правил.** Правила импортов проверяются линтером, не только доком. Иначе через месяц никто не помнит, что можно, а что нельзя, и AI-агент этого не знает по построению.
- **Симметрия клиент/сервер.** Одна и та же модульная модель работает и на клиенте, и на сервере. Не нужно держать в голове два разных набора правил.
- **Минимум предвосхищения.** Модули заводятся по факту, не создаём пустых директорий «на будущее».

## Рассмотренные варианты

### Модель модулей

- **Вариант A1: Плоская структура без формальных модулей.** Всё лежит в `src/`, папки — по фиче или по типу (`components/`, `hooks/`, `pages/`). Импорты не ограничены.
- **Вариант A2: Feature-Sliced Design или похожая методология.** Строгая многоуровневая иерархия (`app/entities/features/widgets/pages/shared`) с фиксированными правилами импортов между слоями.
- **Вариант A3: Свой набор модулей, конкретно под проект.** Явный перечень модулей (`landing`, `project`, `auth`, `planner`, `core`, `common`, `application`), явный граф разрешённых импортов, энфорс через ESLint.

### Механизм доступа к общим сервисам (`logger`, HTTP-клиент, `AuthService`)

- **Вариант B1: Голые синглтоны.** `import { logger } from 'core/logger'`. Просто, но нельзя подменить в тестах и per-request на сервере.
- **Вариант B2: Прокидывание через пропсы/DI сверху вниз.** Каждый компонент/функция явно получает нужные сервисы. Чистая изоляция, много бойлерплейта.
- **Вариант B3: Registry-контейнер в React context + хук `useRegistry()`.** Инстансы собираются в одном месте, доступны через хук из любого места приложения.

### Энфорс правил импортов

- **Вариант C1: Только в доке.** Полагаемся на дисциплину.
- **Вариант C2: ESLint `no-restricted-imports`.** Встроенное правило, конфигурируется через паттерны путей per-directory.
- **Вариант C3: `eslint-plugin-boundaries`.** Отдельная зависимость, декларативные правила по типам модулей.

### Layout `apps/platform/src`

- **Вариант D1: Разделение по среде исполнения — `client/`, `server/`, `shared/`.**
- **Вариант D2: Разделение по модулям, среда — вложенная папка внутри модуля (`auth/client/`, `auth/server/`).**

## Выбранный вариант

**Выбраны: A3 + B3 + C2 + D1.**

### Модули (v0)

| Модуль | Роль | Страницы |
|---|---|---|
| `application` | Модуль-сборщик приложения: собирает `Registry`, настраивает роутинг, монтирует SSR-обвязку, root-layout | ✅ |
| `landing` | Публичная часть сайта: главная, статические страницы, **логин/регистрация/сброс пароля, OAuth-колбэки** | ✅ |
| `project` | Работа с проектом: список проектов, страница `/project/:id` (собирает `planner` через DI) | ✅ |
| `auth` | Библиотека: `AuthService` (getCurrentUser, login, register, logout, OAuth-обмены), стейт текущего пользователя. Без страниц | ❌ |
| `planner` | Изолированный движок редактора: сцена, инструменты, инспектор, undo/redo. Всё внешнее — через DI-пропсы. В v1 переезжает в отдельный пакет | ❌ |
| `core` | Base-библиотеки: `logger` (реализация), HTTP-клиент, базовые утилиты. Без UI | ❌ |
| `common` | Общий UI (обёртки над HeroUI, layout-примитивы), `Registry`, `RegistryContext`, хук `useRegistry`. Без страниц | ❌ |

### Граф импортов

Стрелка = «может импортировать». Всё, что не в графе, — запрещено.

```
application ──► всё (сборщик)

landing  ──► core, common, planner, auth
project  ──► core, common, planner, auth
common   ──► core, auth, planner
auth     ──► core
planner  ──► —
core     ──► —
```

Ключевые следствия:
- `application` может импортировать любой модуль.
- Никто, кроме `application`, не может импортировать `application`.
- `planner` и `core` не импортируют ничего из модулей — только внешние библиотеки.
- `auth` не импортирует `common`. Это цена того, что `common` типизируется через `auth` (см. registry-паттерн ниже) — иначе цикл. Формы логина/регистрации живут не в `auth`, а в `landing`, и используют `common`-примитивы и `useRegistry().auth`.

### Registry-паттерн

**Сборка — в `application`. Контракт и хук — в `common`. Доступ — через React context.**

- В `common` объявлены: тип `Registry` (запись из инстансов общих сервисов), React context `RegistryContext`, хук `useRegistry()`.
- В `application` создаётся конкретный инстанс: `new Registry({ logger, authService, httpClient, ... })` — на клиенте один раз при бутстрапе, на сервере один раз per-request (если нужен request-scoped контекст, например `req-id` для логгера).
- Провайдер `<RegistryContext.Provider value={registry}>` монтируется на самом верху дерева в `application`.
- Модули достают что нужно через `useRegistry()` из `common`.

Циклов в графе импортов нет: `common → auth → core → ⊥`, `common → planner → ⊥`.

### Правила размещения кода в модулях

- **Public API** — только через `index.ts` каждого модуля. Импорты вида `import { X } from 'client/auth'` — ок; `import { X } from 'client/auth/internal/foo'` — нет.
- **Переезд в `common`** — когда некий кусок кода реально нужен в **двух и более** модулях. До этого — живёт локально в модуле-владельце. Не превращать `common` в свалку.
- **Тесты** — co-location: `foo.ts` + `foo.test.ts` рядом. Никаких `__tests__/`.
- **Клиентский API-слой** — внутри модуля-владельца (`client/project/api.ts`, `client/project/queries.ts`). Общая HTTP-обёртка — в `core`.

### Симметрия на сервере

Те же модули (`application`, `auth`, `project`, `common`, `core`) с теми же правилами импортов. Отличия:
- `planner` на сервере отсутствует — это клиентская библиотека.
- `landing` на сервере отсутствует до тех пор, пока не появится серверная логика для лендинга (например, отдельные API-эндпоинты). SSR лендинга обслуживается общим SSR-механизмом в `application`.
- Модули заводятся по факту. `apps/platform/src/server/auth/` не создаётся, пока не появится реальная серверная логика auth.

### Layout `apps/platform`

```
apps/platform/
  src/
    client/       # клиентские модули
    server/       # серверные модули
    shared/       # изоморфный код: Zod-схемы API, типы, константы, общие утилиты
  db/
    migrations/   # SQL-миграции dbmate
  webpack/        # конфиги webpack (клиент + сервер)
  public/         # статика
```

`db/migrations/` живёт на уровне `apps/platform/`, а не внутри `src/server/`, потому что это не TS-код: это SQL-файлы, которые запускает CLI-инструмент dbmate (у которого дефолт — `db/migrations/`).

### Энфорс

Правила импортов проверяются через встроенное ESLint-правило `no-restricted-imports`, конфигурируется per-directory через `files` в `eslint.config.js`. Никаких дополнительных зависимостей. Конкретный конфиг — задача имплементации, не ADR.

## Обоснование

### Почему свой набор модулей, а не FSD / плоская структура

- **Плоская структура** отсекается: правила существуют только в голове. Через месяц/полгода вайбкодинга структура превратится в кашу, зависимости запутаются, движок редактора начнёт незаметно тащить в себя `auth` и другую бизнес-логику, потеряется возможность вынести его в пакет.
- **FSD** отсекается: избыточная методология для одного разработчика и приложения с ~7 модулями. FSD решает проблему масштаба команд и больших продуктов, у нас другая задача — быстро писать v0 не разваливая архитектуру.
- **Свой набор модулей** — минимальный необходимый набор правил под конкретный проект. Модули совпадают с доменами приложения, разработчик их держит в голове без методологии.

### Почему registry, а не голые синглтоны или чистый DI через пропсы

- **Голые синглтоны** ломаются на сервере: SSR — per-request, у каждого запроса может быть свой `req-id` в логгере, своя сессия. Синглтоны не позволяют это выразить.
- **Чистое прокидывание через пропсы** архитектурно чище, но даёт много бойлерплейта: каждый нужный сервис тащится через всё дерево компонентов. На масштабе редактора (глубокие деревья, много сервисов) — тяжеловато.
- **Registry в context** — компромисс: явная сборка в одном месте (`application`), явный контракт (тип `Registry`), но простой доступ через хук из любого места. Легко мокается в тестах (подменить `<RegistryContext.Provider value={mockRegistry}>`).

### Почему `useRegistry` в `common`, а не в `core`

- Тип `Registry` включает конкретные сервисы (`authService: AuthService`), значит модуль-владелец типа `Registry` должен импортировать `auth` (или его интерфейс).
- Если положить в `core`: `core → auth` нарушает нижний слой (core не должен ничего знать про доменные модули).
- Если положить в `common`: `common → auth` — это норма, common и так завязан на прикладную часть.
- Цена: `auth` не может импортировать `common` (иначе цикл). Формы логина/регистрации живут в `landing`, а не в `auth`. `auth` — чистая библиотека без UI.

### Почему `no-restricted-imports`, а не `eslint-plugin-boundaries`

- Правило встроенное, никаких новых зависимостей.
- Для 7 модулей конфиг компактный и читаемый.
- `eslint-plugin-boundaries` лучше при десятках модулей и типизации «слоёв» — у нас этого нет.

### Почему layout по среде исполнения (`client/server/shared`), а не по модулям

- **По модулям с вложенной средой** (`auth/client/`, `auth/server/`) выглядит красиво, но плохо ложится на webpack: две сборки (клиент и сервер) должны видеть свои entry-points. Проще, когда всё клиентское лежит под одним префиксом.
- **`shared/`** физически отдельная папка — жёсткое напоминание, что там код без Node-only и без DOM-only API. Иначе легко случайно затащить `fs` или `window` в изоморфный модуль.

### Env-переменные

Формальный слой env-конфигурации (`.env.example`, Zod-валидация env на старте) в v0 не заводится. Причина: один разработчик, никаких секретов на клиенте, на сервере нужны буквально `DATABASE_URL` и креды OAuth (Yandex/VK). Дев-дефолты хардкодятся в коде, прод-значения выставляются `process.env` через deploy-скрипт. Заведём отдельный ADR, когда секретов станет много или появится необходимость валидации.

### Что фиксируется этим ADR

- Список модулей `application`, `landing`, `project`, `auth`, `planner`, `core`, `common`.
- Граф разрешённых импортов между модулями.
- Registry-паттерн (сборка в `application`, контракт и хук в `common`).
- Симметрия клиент/сервер, отсутствие `planner` на сервере.
- Layout `apps/platform/src/{client,server,shared}/`, `db/migrations/`, `webpack/`, `public/`.
- Public API модулей — через `index.ts`.
- Тесты — co-location.
- Энфорс через ESLint `no-restricted-imports`.

### Что НЕ фиксируется этим ADR

- **Внутренняя раскладка модулей** (что внутри `landing/`, `project/`, `auth/`) — по факту, не через ADR.
- **Внутренняя раскладка модуля `application`** — отдельно, если станет спорным.
- **Механика SSR data-fetching** (prefetch, hydration TanStack Query, react-router loaders) — отдельный ADR 0008.
- **Env-переменные** — не формализуются в v0.
- **Логгирование**, метрики, error tracking, background jobs, файловое хранилище — отдельные ADR по мере появления.

## Последствия

### Плюсы

- Явные границы: из любого файла видно, что можно импортировать и почему.
- `planner` изолирован по построению — вынос в пакет в v1 сводится к перемещению папки без переписывания импортов.
- Registry-паттерн даёт единую точку сборки зависимостей и лёгкую подмену в тестах.
- Правила проверяются линтером — не зависят от памяти разработчика или дисциплины AI-агента.
- Симметрия клиент/сервер — одна ментальная модель на всё приложение.
- Минимальный overhead: 7 модулей, простой граф, встроенный линтер.

### Минусы

- **`auth` не может использовать UI из `common`.** Форма логина/регистрации живёт в `landing`, а не рядом с логикой auth. Разработчик редактирует форму в одном месте, `AuthService.login()` — в другом.
- **Компромисс размещения auth-страниц в `landing`.** Концептуально login/register — не «лендинг», но раскладывать их в отдельный модуль ради изоляции пока избыточно.
- **Registry в context — не бесплатно.** Любой ре-рендер провайдера ре-рендерит всё дерево. Registry должен быть стабильным по референсу (создаётся один раз при бутстрапе).
- **Правила надо периодически перечитывать при добавлении модуля** — понимать, куда он вписывается в граф.

## Как проверить/пересмотреть

- **Модулей стало 15+**, граф превратился в спагетти → пересмотреть в пользу FSD или другой формальной методологии.
- **`common` превратился в свалку** (~30% кода приложения) → пересмотреть критерий переезда в `common` (например, поднять порог до «нужно в 3+ модулях») или разбить `common` на более гранулярные модули.
- **Регулярно приходится добавлять исключения в ESLint-конфиг** «ну тут разово надо» → правила не соответствуют реальности, пересмотреть граф.
- **`auth` регулярно дублирует то, что лежит в `common`** (одни и те же формы, валидаторы) → пересмотреть решение о запрете `auth → common` или вынести часть форм в отдельный модуль.
- **Registry-паттерн стал узким местом производительности** (провайдер ре-рендерится и роняет всё дерево) → разбить на несколько контекстов по частоте изменений.
