# 0005. Модель аутентификации: server-side sessions в cookie, email/пароль + Yandex ID + VK ID, argon2id

- Статус: Принято
- Дата: 2026-08-08

## Решение

- **Идентификатор пользователя:** email (нормализация lowercase + trim перед записью/поиском). На v0 без верификации, но поле `email_verified_at` в схеме заводим сразу — включим верификацию в v1+ без миграции таблицы.
- **Сессии:** server-side. Cookie `session_id` — opaque случайная строка (минимум 32 байта энтропии), состояние в таблице `sessions`. TTL 30 дней с rolling refresh (при активности продлеваем `expires_at`). Один пользователь может иметь несколько активных сессий одновременно.
- **Cookie-флаги:** `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`. Домен — основной, без wildcard-поддоменов.
- **CSRF:** обеспечивается `SameSite=Lax` + same-origin проверкой для мутирующих запросов. Отдельный CSRF-токен на v0 не нужен.
- **Пароли:** argon2id с дефолтными безопасными параметрами (`memoryCost`, `timeCost`, `parallelism` — по актуальной OWASP-рекомендации). Хеш — в `users.password_hash`.
- **OAuth-провайдеры:** Yandex ID и VK ID. Стандартный OAuth 2.0 authorization code flow с callback-эндпоинтом на нашем сервере. Токены провайдера **не сохраняются** — используются только для получения `email` и `provider_user_id` в момент входа.
- **Связка OAuth ↔ локальный юзер:** отдельная таблица `oauth_accounts(user_id, provider, provider_user_id, created_at)` с уникальным индексом `(provider, provider_user_id)`. Один юзер = несколько привязок.
- **Коллизия email при OAuth-входе:** **отказ**. Пользователю: «email занят, войдите паролем и привяжите провайдера из настроек». Никаких автопривязок без явного действия юзера.
- **Регистрация через OAuth (email новый):** создаём учётку с пустым `password_hash`, юзер логинится только через OAuth, пока не задаст пароль в настройках.
- **Password reset:** email + одноразовый токен, TTL 1 час. Отдельная таблица `password_reset_tokens(user_id, token_hash, expires_at, used_at)`. При успешной смене — все активные сессии инвалидируются.
- **Email-отправка (для reset):** `nodemailer` + внешний SMTP. Конкретный провайдер — отдельно, не в этом ADR.
- **Rate limiting на auth-эндпоинтах** (login, register, password reset request) обязателен — уровень middleware, не ADR.

## Почему

Server-side sessions вместо JWT: мгновенная инвалидация (`DELETE FROM sessions WHERE user_id = ?`), простая отладка через psql, rolling TTL тривиальный. Один сервер — аргументы за stateless JWT (шаринг между нодами без стука в БД) не работают. Для JWT «разлогинить пользователя» требует blacklist'а, который сам является server-side state — то есть главный аргумент за JWT исчезает. Отдельная таблица `oauth_accounts` вместо колонок в `users`: юзер может привязать несколько провайдеров (email + Yandex + VK), естественный уникальный индекс, унифицированный код callback'а; JSONB отсекается (теряется индексируемость `provider_user_id`). Отказ при коллизии email вместо автопривязки: провайдеры не гарантируют, что email реально верифицирован на их стороне — автопривязка = account takeover через чужой Yandex/VK-аккаунт с тем же email. Argon2id — рекомендация OWASP на 2026, устойчив к GPU/ASIC (bcrypt уязвимее из-за низкого memory cost); для нового проекта в 2026 нет причин выбирать legacy. Email-верификация не с v0: не критична для функционала сохранения проектов, экономит регистрационный flow; поле `email_verified_at` в схеме сразу — включим без миграции. Password reset с v0 — иначе первая забытая паролька = потерянный пользователь; при платформе, где ценность = сохранённые проекты, это неприемлемо.

## Что важно знать

- **БД дёргается на каждый аутентифицированный запрос** (проверка сессии по `session_id`). На v0 копейки; при масштабе — in-memory или Redis-кеш отдельным ADR.
- **UX «email занят» при OAuth-регистрации нужно продумывать явно** — юзер не понимает, почему «просто войти через Яндекс» не работает. Нужна понятная формулировка ошибки и deep-link «войти паролем → привязать Yandex».
- **SMTP-зависимость с v0** — при недоступности SMTP не работает password reset. Отдельная точка отказа.
- **`SameSite=Lax` без CSRF-токена** ломается при появлении iframe-встраиваний / cross-origin интеграций — тогда придётся вводить CSRF-токен и, возможно, пересмотреть `SameSite`.
- **Argon2 требует нативной сборки** (или WASM-fallback) — легкий overhead на первом `pnpm install`.
- **Второй инстанс сервера** (горизонтальное масштабирование) сессионную модель не ломает (БД общая), но ломает in-memory rate limiting.
