# 0005. Модель аутентификации: server-side sessions в cookie, email/пароль + Yandex ID + VK ID, argon2id

- Статус: Принято
- Дата: 2026-08-08
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

По продуктовым решениям v0: без гостевого режима (свой проект = только через регистрацию), поддерживаемые способы входа — email/пароль + Yandex ID + VK ID. Приложение — SSR-монолит на Express (один процесс, один сервер), десктоп-only, аудитория РФ. Нужно зафиксировать модель аутентификации: как хранится сессия, как связываются локальный пользователь и внешние OAuth-провайдеры, как хэшируются пароли, как устроен reset password.

Схема БД (конкретные таблицы и колонки) — предмет следующего ADR 0006. Здесь фиксируем **модель**, из которой она вытекает.

## Драйверы решения

- **Простота отладки и мгновенная инвалидация.** «Разлогинить пользователя сейчас» / «убить все сессии» — должно быть тривиальной операцией, а не костылём вокруг blacklist'а токенов.
- **Один сервер, один процесс.** Нет микросервисов, нет распределённости — соответственно, нет требований, из-за которых обычно тянут stateless JWT.
- **Российская специфика.** OAuth-провайдеры — Yandex ID и VK ID. Оба возвращают email как первичный идентификатор пользователя.
- **Минимум внешних зависимостей на v0.** Не тащим SMS-инфру, не тащим email-верификацию до появления реальной необходимости.
- **Дисциплина безопасности с первого дня.** Хеширование паролей, cookie-флаги, защита от CSRF — не откладываем «на потом», делаем сразу по умолчанию.

## Рассмотренные варианты

### Сессионная модель

- **Вариант A1: Server-side sessions.** Cookie содержит opaque `session_id` (случайная строка), состояние сессии живёт в БД (таблица `sessions`).
- **Вариант A2: Stateless JWT.** Cookie/localStorage содержит подписанный JWT со всеми claims. БД не трогается на каждый запрос.
- **Вариант A3: Гибрид.** Короткоживущий access-JWT + refresh-token в БД.

### OAuth-связывание

- **Вариант B1: Отдельная таблица `oauth_accounts`** (user_id + provider + provider_user_id). Один локальный пользователь может иметь любое количество OAuth-привязок.
- **Вариант B2: Колонки прямо в `users`** (`yandex_id`, `vk_id`).

### Что делать, если email из OAuth уже занят

- **Вариант C1: Автоматически привязать OAuth к существующей учётке.** Риск: чужой Yandex-аккаунт с тем же email захватит доступ.
- **Вариант C2: Отказать в OAuth-регистрации** («email занят, войдите паролем и привяжите провайдера из настроек»).
- **Вариант C3: Разрешить только через email verification** (сначала подтверждаем владение email по ссылке, потом линкуем).

### Хеширование паролей

- **Вариант D1: argon2id** — современный, устойчив к GPU/ASIC-атакам, победитель Password Hashing Competition.
- **Вариант D2: bcrypt** — legacy-стандарт, всё ещё безопасен, но старше.

### Password reset

- **Вариант E1: Через email + одноразовый токен с TTL.**
- **Вариант E2: Без reset flow на v0** («напишите в поддержку»).

## Выбранный вариант

**Выбраны: A1 + B1 + C2 + D1 + E1.**

Итоговая модель:

- **Идентификатор пользователя:** email (без верификации на v0, поле `email_verified_at` заводим в схеме заранее — включим верификацию в v1+ без миграции таблицы).
- **Хранение сессии:** server-side. Cookie `session_id` — opaque случайная строка (минимум 32 байта энтропии), состояние — в таблице `sessions`. TTL сессии — 30 дней с rolling refresh (при активности продлеваем `expires_at`). Один пользователь может иметь несколько активных сессий одновременно (браузер, второй компьютер).
- **Cookie-флаги:** `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`. Домен — основной домен приложения (без wildcard-поддоменов на v0).
- **CSRF-защита:** обеспечивается флагом `SameSite=Lax` + same-origin проверкой для мутирующих запросов. Отдельный CSRF-токен не нужен на v0 (пересмотрим, если появятся cross-site сценарии).
- **Пароли:** хешируются **argon2id** с дефолтными безопасными параметрами (`memoryCost`, `timeCost`, `parallelism` берём из рекомендаций OWASP актуальных на момент старта). Хеш хранится в `users.password_hash`.
- **OAuth-провайдеры:** Yandex ID и VK ID. Стандартный OAuth 2.0 authorization code flow с callback-эндпоинтом на нашем сервере. Токены провайдера **не сохраняются** — используются только для получения `email` и `provider_user_id` в момент входа, дальше живёт наша сессия.
- **Связка OAuth и локального пользователя:** отдельная таблица `oauth_accounts(user_id, provider, provider_user_id, created_at)` с уникальным индексом `(provider, provider_user_id)`. Один локальный пользователь может иметь несколько привязок (email/пароль + Yandex + VK — всё это одна учётка).
- **Правило «email уже занят».** Если при OAuth-входе email от провайдера уже есть в `users` — **отказ**. Пользователю показывается: «email занят, войдите паролем и привяжите провайдера из настроек». Никаких автоматических привязок к существующему аккаунту без явного действия пользователя.
- **Регистрация через OAuth.** Если email от провайдера в `users` отсутствует — создаём новую учётку с этим email, пустым `password_hash` (пользователь никогда не задавал пароль), и записью в `oauth_accounts`. Такой пользователь входит только через OAuth, пока не задаст пароль в настройках.
- **Password reset flow:** через email + одноразовый токен с TTL 1 час. Отдельная таблица `password_reset_tokens(user_id, token_hash, expires_at, used_at)`. В email отправляем ссылку с токеном, при переходе — форма нового пароля, после успешной смены — токен помечается использованным, все активные сессии пользователя инвалидируются.
- **Email-отправка** (для password reset) — необходима с v0. Конкретный SMTP-провайдер выбирается отдельно (не в этом ADR), но стек `nodemailer` + внешний SMTP закладывается как ожидаемое.
- **Rate limiting на auth-эндпоинтах** — обязателен (login, register, password reset request). Конкретный механизм (in-memory / postgres-backed) — уровень middleware, не ADR.

## Обоснование

### Почему server-side sessions, а не JWT

- **Мгновенная инвалидация из коробки.** Логаут = удалить строку из `sessions`. «Разлогинить пользователя со всех устройств» = `DELETE FROM sessions WHERE user_id = ?`. С JWT это требует blacklist'а токенов, который сам по себе является server-side state — то есть исчезает главный аргумент за JWT.
- **Простота отладки.** Сессия в БД — это строка, которую можно посмотреть в psql. JWT — это подпись, которую надо декодировать.
- **Нет требований, из-за которых обычно берут JWT.** У нас один сервер, один процесс, никаких отдельных API-нод, между которыми надо шарить состояние без стука в БД. Всё в одном месте.
- **Rolling TTL.** Продление срока действия при активности пользователя тривиально с server-side sessions (`UPDATE sessions SET expires_at = ...`). С JWT это требует refresh-token flow — то есть возвращаемся к гибриду.

### Почему отдельная таблица oauth_accounts

- Один пользователь может привязать сразу несколько провайдеров (email + Yandex + VK). Модель «колонки в `users`» плохо это поддерживает: либо `nullable`-колонка на каждого провайдера (плохо масштабируется), либо JSONB (теряется индексируемость `provider_user_id`).
- Отдельная таблица даёт естественный уникальный индекс `(provider, provider_user_id)`, легко расширяется новым провайдером (добавлением строки, а не миграции таблицы).
- Одинаковая модель для всех OAuth-провайдеров — унифицированный код обработки callback'а.

### Почему отказ при коллизии email, а не автопривязка

- **Автопривязка небезопасна.** Провайдеры не гарантируют, что email в userinfo действительно подтверждён провайдером. Если чужой человек создал у себя Yandex-аккаунт с email жертвы — при автопривязке он получит доступ к аккаунту жертвы в нашем приложении.
- **Верификация email через OAuth-провайдера не решает проблему**, потому что мы не контролируем процесс верификации на стороне провайдера и не можем на него полагаться как на источник доверия.
- **Явная привязка из настроек** — единственный безопасный путь. Пользователь входит паролем, доказывает владение аккаунтом, потом сам линкует OAuth.
- Это стандартный подход у большинства зрелых сервисов.

### Почему argon2id

- Рекомендация OWASP на 2026 год для новых проектов.
- Устойчив к GPU/ASIC-атакам (bcrypt — уязвимее к таким атакам из-за низкого memory cost).
- Родная поддержка в Node через пакет `argon2` — простой API, WASM-fallback если нативный модуль не собрался.
- Bcrypt отсекается только потому, что для нового проекта в 2026 нет причин выбирать legacy-алгоритм.

### Почему без email-верификации на v0

- Не критично для функциональности (сохранение проектов, вход) — верификация нужна ради антифрода и «настоящего» email, чего v0 не требует.
- Экономит время на регистрационном flow и убирает зависимость от SMTP на первичной регистрации.
- **НО:** SMTP всё равно нужен для password reset. Значит инфраструктура email-отправки будет с v0. При появлении реального use-case (маркетинговые письма, антифрод) — включаем верификацию без миграции: колонка `email_verified_at` заводится в схеме сразу, просто пока не заполняется автоматически при регистрации.

### Почему password reset с v0

- Иначе первая же забытая паролька = потерянный пользователь. При платформе, где ценность — сохранённые проекты, это неприемлемо.
- Реализация тривиальна поверх уже нужного SMTP.

### Что фиксируется этим ADR

- Server-side sessions + opaque cookie как модель.
- `SameSite=Lax` + `HttpOnly` + `Secure` для session cookie, CSRF без отдельного токена.
- argon2id для паролей.
- Отдельная таблица `oauth_accounts`, отказ при коллизии email.
- Password reset flow через одноразовый токен + email.
- Email — primary identifier, без верификации на v0, но с полем `email_verified_at` в схеме.
- Токены OAuth-провайдеров не сохраняются в БД.

### Что НЕ фиксируется этим ADR

- **Конкретные таблицы и колонки** (`users`, `sessions`, `oauth_accounts`, `password_reset_tokens`) — ADR 0006.
- **SMTP-провайдер и конфигурация email-отправки** — отдельный ADR по инфре, когда придёт время выбирать.
- **Rate limiting** — уровень middleware, не ADR.
- **Флоу настроек безопасности** (смена пароля из UI, отвязка OAuth-провайдера, просмотр активных сессий) — уровень фичей, документируем в feature-документе перед реализацией.
- **2FA/MFA** — не делаем на v0, отдельный ADR если понадобится.

## Последствия

### Плюсы

- Мгновенная инвалидация сессий, простая отладка через psql.
- Единая модель OAuth, легко добавлять новых провайдеров.
- Отказ при коллизии email закрывает целый класс account-takeover атак без дополнительного кода.
- Argon2id — актуальный best-practice, не придётся мигрировать через год.
- Password reset с v0 — не теряем пользователей на первой же забытой пароле.

### Минусы

- **БД дёргается на каждый аутентифицированный запрос** (проверка сессии по `session_id`). На v0 это копейки; при масштабе — решается кешем в памяти процесса или Redis отдельным ADR.
- **Отказ при коллизии email** усложняет UX регистрации через OAuth: пользователь может не понимать, почему «просто войти через Яндекс» не работает. Нужна понятная формулировка ошибки и понятный путь «войдите паролем → привяжите Яндекс».
- **SMTP-зависимость с v0** — нужен провайдер (пусть даже базовый), и это отдельная точка отказа. При недоступности SMTP password reset не работает.
- **`SameSite=Lax` без CSRF-токена** — приемлемо, пока приложение живёт на одном домене и не открывает cross-site POST-сценариев. При появлении iframe-встраиваний или cross-origin интеграций — придётся вводить CSRF-токен.
- **Argon2 требует нативной сборки** (либо WASM-fallback) — легкий overhead на первом `pnpm install`.

## Как проверить/пересмотреть

- **Проверка session на каждом запросе стала узким местом** → ввести in-memory или Redis-кеш активных сессий отдельным ADR.
- **Появилась реальная потребность в cross-site сценариях** (виджет для встраивания, публичное API из браузера) → ввести CSRF-токен и, возможно, пересмотреть `SameSite` в пользу `Strict` для основного flow + отдельный поток для встраиваний.
- **Появился антифрод-риск или маркетинговые письма** → включить обязательную email-верификацию (без миграции схемы).
- **Пользователи регулярно жалуются на «email занят» при OAuth-регистрации** → пересмотреть UX (не саму модель безопасности): более понятное сообщение, deep-link «войти паролем и привязать Yandex».
- **Появилась потребность в 2FA** → отдельный ADR, дополнительные таблицы (`user_totp_secrets`, `user_recovery_codes`).
- **Появился второй инстанс сервера** (горизонтальное масштабирование) → session model не меняется (БД общая), но нужно пересмотреть Rate limiting (in-memory перестанет работать).
