# 0003. Стек фронтенда: Express + React SSR на Webpack, HeroUI/Tailwind, голый Three.js

- Статус: Принято
- Дата: 2026-08-08

## Решение

- **Runtime и сборка:** Express + React SSR через Webpack, мажор **5** (двух-битная сборка client + server).
- **UI-библиотека:** React последней стабильной major-версии.
- **Роутинг:** `react-router` последней стабильной major-версии.
- **UI-kit и стайлинг:** HeroUI поверх Tailwind CSS (конкретные версии — ADR 0009).
- **Данные с сервера:** TanStack Query (React Query), мажор **5**.
- **Локальное состояние:** штатные хуки React (`useState`, `useReducer`, `useContext`), без внешнего state-manager'а.
- **Формы:** `react-hook-form` (мажор **7**) + `@hookform/resolvers/zod` (те же Zod-схемы валидируют `req.body` на сервере — см. ADR 0004).
- **3D:** голый Three.js, без обёрток, версия **0.185.x** (three ведёт semver в диапазоне 0.x — фиксируем на минор, обновление минора может ломать API). Инициализация внутри React-компонента через `ref` на `<canvas>` и `useEffect` с явным `dispose()` в cleanup.
- **Тесты:** Jest, мажор **30**.
- **Язык:** TypeScript, мажор **6**, с общим корневым `tsconfig`.

## Почему

`apps/platform` совмещает SEO-требовательный лендинг, авторизованный UI и SPA-редактор — нужен стек, где сервер под нашим контролем (для будущих auth-cookie, iframe-интеграций, тонкой настройки SSR-стрима). Next/Remix отсекаются: их «из коробки» упирается в vendor-специфику при первых нестандартных требованиях (кастомная auth-логика, RSC-границы с HeroUI). Webpack, а не Vite — сознательный выбор в пользу знакомого инструмента; незнакомая система сборки на старте нового проекта — риск в самой критичной инфраструктуре. Голый Three, а не react-three-fiber: WebGL-ресурсы (`geometry`, `material`, `texture`) обязаны диспозиться вручную; голый Three заставляет писать `dispose()` явно в cleanup, R3F пытается управлять этим через reconciler и при частом mount/unmount может «терять» ресурсы. Плюс R3F добавляет собственный слой абстракции поверх Three — для человека без опыта Three дебажить приходится в двух слоях. Jest, а не Vitest: тайтовая интеграция Vitest с Vite нам не нужна (у нас Webpack), а Jest — де-факто стандарт с максимальной экосистемой и рецептами. TanStack Query + локальное состояние вместо state-manager'а: большинство «глобального» — это серверные данные (кеш держит TanStack Query), UI-состояние локально по природе. Redux/Zustand/Jotai на v0 — solution в поисках problem.

## Что важно знать

- **Больше boilerplate**, чем в Next/Remix: свои `webpack.client.ts` + `webpack.server.ts`, свой SSR-шаблонизатор, свой `pageMiddleware`.
- **HeroUI + кастомный SSR** — не самый прохоженный путь (библиотека заточена под Next). Возможны нюансы с hydration и провайдерами (framer-motion, react-aria SSR-контекст).
- **Голый Three требует дисциплины `dispose()`** — утечки GPU-памяти проявляются не сразу и болезненно дебажатся. Компенсируем юнит-тестами движка и code-review-чеклистом на mount/unmount 3D-объектов.
- **Отсутствие state-manager'а** станет узким местом, если редактор начнёт делить состояние с внешними панелями UI — тогда отдельный ADR.
- **Модель состояния редактора** (undo/redo, storage сцены, event-loop инструментов) — отдельный ADR перед стартом работ над редактором.
- **TypeScript 6, а не 7 (latest):** `typescript-eslint` 8 (ADR 0011) держит peer `typescript <6.1.0`, TS 7 пока не поддерживается (tracking: `typescript-eslint#10940`). Как только релиз с поддержкой TS 7 выйдет — апгрейдимся, ADR правим по месту.
