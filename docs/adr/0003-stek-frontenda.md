# 0003. Стек фронтенда: Express + React SSR на Webpack, HeroUI/Tailwind, голый Three.js

- Статус: Принято
- Дата: 2026-08-08
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

`apps/platform` в v0 — единое приложение, внутри которого сосуществуют разноприродные части:

- **Маркетинговый лендинг** — критичен для технической базы SEO (SSR, meta, sitemap, structured data — см. `release-v0.md`).
- **Личный кабинет / список проектов** — типовой авторизованный React-UI.
- **Редактор** (`/project/:id`) — SPA поверх WebGL2, никакого смысла в SSR для него нет.

Нужен единый фронтенд-стек, который умеет отдавать SSR-страницы для маркетинга и авторизованных экранов и при этом не мешает редактору жить как чистой CSR-зоне с полным контролем над рендер-лупом.

## Драйверы решения

- **SSR из коробки** для лендинга и других не-редакторных страниц.
- **Гибкость сервера.** SSR-runtime = продовый сервер, на который позже лягут API-роуты (`/api/*`), auth-сессии, iframe/webhook-интеграции. Не хочется через год упереться в ограничения выбранного мета-фреймворка.
- **Явный контроль над жизненным циклом WebGL-ресурсов.** Утечки в редакторе — самый дорогой класс багов; стек должен позволять диспозить `geometry`/`material`/`texture` руками и явно.
- **Знакомый инструментарий.** У автора нулевой опыт в Three.js — компенсируется тем, что вокруг Three (сборка, UI, роутинг, стейт) всё должно быть максимально предсказуемым.
- **Само-хостинг без vendor-специфики.** Стек должен запускаться `node dist/server.js` на своём сервере без привязки к платформе.
- **Тестируемость движка редактора.** Юниты на геометрию/коллизии — обязательны с самого начала кода движка.

## Рассмотренные варианты

### Мета-фреймворк vs самосбор

- **Вариант A: Next.js** (self-hosted, `next start`). Единая среда с SSR/CSR/API-routes из коробки.
- **Вариант B: Remix.** Аналогично Next, но с более линейной моделью загрузки данных.
- **Вариант C: Express + React SSR на Webpack** (client + server бандлы, `renderToString`/`renderToPipeableStream`, кастомный шаблонизатор). Полный ручной контроль над сервером и сборкой.

### Обёртка над Three.js

- **Вариант D1: react-three-fiber (R3F).** Декларативный React-подход поверх Three, JSX-описание сцены.
- **Вариант D2: Голый Three.js.** Императивное создание сцены/объектов внутри React-компонента (обычно через `useEffect` и `ref` на canvas).

### Тестовый фреймворк

- **Вариант E1: Vitest** — ESM-first, быстрый watch mode, тайтовая интеграция с Vite; как standalone-раннер тоже работает.
- **Вариант E2: Jest** — де-факто стандарт JS-тестирования, максимально широкая экосистема (моки, снапшоты, coverage, testing-library), TS-трансформация через `ts-jest` / `@swc/jest` / `babel-jest`.

## Выбранный вариант

**Выбраны: C + D2 + E2.**

Итоговый стек фронтенда:

- **Runtime и сборка:** Express + React SSR через Webpack (двух-битная сборка client + server).
- **UI-библиотека:** React последней стабильной major-версии.
- **Роутинг:** `react-router` последней стабильной major-версии.
- **UI-kit и стайлинг:** HeroUI поверх Tailwind CSS.
- **Данные с сервера:** TanStack Query (React Query) последней стабильной major-версии.
- **Локальное состояние:** штатные хуки React (`useState`, `useReducer`, `useContext`), без внешнего state-manager'а.
- **Формы:** `react-hook-form` последней стабильной major-версии + `@hookform/resolvers/zod` для интеграции с Zod-схемами из `src/shared/` (те же схемы валидируют `req.body` на сервере — см. ADR 0004).
- **3D:** голый Three.js, без обёрток. Инициализация сцены внутри React-компонента через `ref` на `<canvas>` и `useEffect` с явным `dispose()` в cleanup.
- **Тесты:** Jest.
- **Язык:** TypeScript с общим корневым `tsconfig` (см. ADR 0002).

## Обоснование

### Почему Express + React SSR + Webpack, а не Next/Remix

- **Next.js** отсекается: даёт много «из коробки», но плата — жёсткая модель роутинга (app/pages router), скрытая сборка, свой lifecycle серверных компонентов. При появлении нестандартных требований (кастомная auth-cookie логика, тонкая настройка SSR-стрима, специфика API-роутов) быстро упираешься в «а как это в Next» вместо «а как это в Node». Плюс vendor-специфика (RSC, `use client` границы) осложняет интеграцию сторонних UI-kit'ов, в т.ч. HeroUI.
- **Remix** отсекается по тем же соображениям + меньшее сообщество, значит меньше готовых рецептов для типовых задач.
- **Express + React SSR** даёт полный контроль: сервер — это обычный Node-процесс, React рендерится через `renderToPipeableStream`, роуты SSR-страниц и будущие API-роуты живут в одной кодовой базе на равных правах. Никаких скрытых слоёв.
- **Webpack** — сознательный выбор в пользу знакомого инструмента. Vite потенциально даёт лучший DX и скорость, но незнакомая система сборки на старте нового проекта — это неизвестные подводные камни в самой критичной инфраструктуре. Vite можно рассмотреть позже отдельным ADR, если Webpack начнёт мешать.

### Почему голый Three.js, а не react-three-fiber

- **Явный контроль над жизненным циклом ресурсов.** WebGL-ресурсы (`BufferGeometry`, `Material`, `Texture`) обязаны диспозиться руками — иначе утечка GPU-памяти. Голый Three заставляет писать `dispose()` явно в cleanup-функции `useEffect`; это единственный правильный путь. R3F пытается управлять этим через свой reconciler, но при частом mount/unmount компонентов может «терять» ресурсы, если пропустить нюансы (например, ключи на `<mesh>`, реиспользование materials).
- **Меньше магии для человека без опыта Three.js.** R3F добавляет собственный слой абстракции поверх Three; чтобы дебажить проблему рендера, нужно понимать И Three, И R3F reconciler. Голый Three оставляет только один слой понимания.
- **Прямой доступ к рендер-лупу.** Свой `requestAnimationFrame`, свой control над кадром, легче добавлять кастомные рендер-пассы, если понадобятся в v1+.
- **Экосистема Three-примеров.** Подавляющее большинство туториалов и Stack Overflow-ответов по Three — на голом API. С R3F пришлось бы каждый раз мысленно переводить.

### Почему TanStack Query + локальный state, без state-manager'а

- **Большинство «глобального состояния» в приложении — это серверные данные** (текущий пользователь, список проектов, каталог мебели). Их держит TanStack Query — кеш, invalidation, retries, background refetch.
- **UI-состояние (модалки, формы, hover, drag)** локально по природе — хватает `useState`/`useReducer` + context для скоупа.
- **Состояние редактора** (сцена, undo/redo, инструменты) — не глобальное, живёт внутри `apps/platform/src/client/editor/*`, к моменту начала работ над редактором заведём собственную модель (отдельный ADR).
- Redux/Zustand/Jotai на v0 — solution в поисках problem.

### Почему HeroUI

- Готовый набор доступных, стилизуемых React-компонентов поверх Tailwind — экономит время на UI-примитивах.
- Работает с кастомным Express SSR (не только с Next). Требует ручной настройки провайдеров (framer-motion, react-aria SSR-контекст) — это принято как известный компромисс.

### Почему Jest, а не Vitest

- **Ключевое преимущество Vitest — тайтовая интеграция с Vite.** У нас Webpack (см. выше), Vite в проде нет, значит этот плюс не играет: Vitest в такой связке становится просто «ещё одним standalone-раннером».
- **Jest — де-факто стандарт JS-тестирования.** Самая широкая экосистема (моки, снапшоты, coverage, `@testing-library/react`, `jest-environment-jsdom`), самый большой объём готовых рецептов на Stack Overflow. Для человека, работающего через вайбкодинг с нулевым опытом Three.js, «стандартный и предсказуемый» весит больше, чем «быстрее и моднее».
- **Скорость на масштабе v0 не критична.** Тесты движка редактора будут гоняться десятками-сотнями кейсов — Jest 30 c параллелизмом справляется без проблем.
- **TS-трансформация — известная задача.** На старте берём `ts-jest`; при необходимости легко заменяется на `@swc/jest` без правки самих тестов (API у Jest единый).

### Что фиксируется этим ADR

- Стек `apps/platform` со стороны фронтенда и SSR-runtime: Express + React + Webpack + HeroUI/Tailwind + TanStack Query + react-router + react-hook-form + голый Three.js + Jest.
- Смена любого из этих слоёв (например, Webpack → Vite, HeroUI → shadcn/ui, голый Three → R3F) = новый ADR, замещающий этот.

### Что НЕ фиксируется этим ADR

- **Серверная часть API** (роутинг API-эндпоинтов, ORM/query builder, драйвер PostgreSQL) — отдельным ADR 0004.
- **Внутренняя структура `apps/platform`** (раскладка `client/`, `server/`, `shared/`, доменное деление серверных модулей) — уровень ниже ADR, зафиксируем по факту, если станет спорным.
- **Модель состояния редактора** (undo/redo, storage сцены, event-loop инструментов) — отдельный ADR перед стартом работ над редактором.
- **Аутентификация** (сессии/JWT, куки, интеграция Yandex ID / VK ID) — отдельный ADR.

## Последствия

### Плюсы

- Полный контроль над сервером и сборкой — при появлении нестандартных требований не упираемся в мета-фреймворк.
- Голый Three даёт явный `dispose()` — самый надёжный способ избежать GPU-утечек в редакторе.
- HeroUI + Tailwind закрывают UI-примитивы без изобретения дизайн-системы с нуля.
- Jest — знакомый и предсказуемый инструмент с максимально широкой экосистемой для юнит-тестов движка.
- Стек само-хостится обычным `node dist/server.js` — никакой vendor-специфики.

### Минусы

- **Больше boilerplate**, чем в Next/Remix: свой `webpack.client.ts` + `webpack.server.ts`, свой SSR-шаблонизатор, свой `pageMiddleware`, свой роутинг-мост между SSR и клиентом. Приемлемо, но нужно осознавать, что стартовая инфраструктура — не «из коробки».
- **HeroUI + кастомный SSR** — не самый прохоженный путь (библиотека заточена под Next). Возможны нюансы с hydration/провайдерами; готовы поймать и решить руками.
- **Голый Three требует дисциплины `dispose()`** — если её не соблюдать, утечки GPU-памяти будут проявляться не сразу и дебажиться болезненно. Компенсируется юнит-тестами движка и (в перспективе) code review-чеклистом на mount/unmount 3D-объектов.
- **Webpack медленнее Vite** на dev-сборке и cold start. Ощутимо только когда монорепа разрастётся; на v0 — не проблема.
- **Отсутствие state-manager'а** может стать узким местом, если редактор начнёт делить состояние с внешними панелями UI. К этому моменту — отдельный ADR.

## Как проверить/пересмотреть

- **HeroUI + Express SSR становится источником постоянных hydration-багов** и заплаток → рассмотреть переход на shadcn/ui или голые Tailwind-компоненты.
- **Webpack cold start превысил ~30 секунд** или начал ощутимо мешать разработке → рассмотреть переход на Vite отдельным ADR.
- **В редакторе стабильно ловятся GPU-утечки, несмотря на дисциплину `dispose()`** → пересмотреть в пользу R3F с более строгими соглашениями по ключам, или ввести обязательную обёртку `useDisposable`.
- **TanStack Query + локальный state перестал справляться** (UI-состояние начало дублироваться между модулями, cross-component подписки стали сложными) → рассмотреть Zustand/Jotai отдельным ADR.
- **Появилась потребность в React Server Components** для какой-то конкретной задачи → отдельный ADR, но осознавать: переход на RSC = переход на Next/Remix, т.е. фактически пересмотр этого ADR целиком.
