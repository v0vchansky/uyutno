# 0006. Схема БД для v0: auth-таблицы и projects (без содержимого сцены)

- Статус: Принято
- Дата: 2026-08-08
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0004 зафиксировал стек работы с БД (Kysely + `pg` + миграции через dbmate). ADR 0005 зафиксировал модель аутентификации (server-side sessions, email/пароль + Yandex ID / VK ID, argon2id, password reset через одноразовый токен). Нужно перевести это в конкретную схему PostgreSQL: таблицы, колонки, типы, ограничения, индексы.

Скоуп этого ADR ограничен минимальным набором таблиц, необходимым для Этапа 1 разработки v0 (скелет платформы: регистрация, вход, пустой `/project/:id`):

- `users`
- `sessions`
- `oauth_accounts`
- `password_reset_tokens`
- `projects` — только структурная оболочка (id, владелец, имя, timestamps). Содержимое сцены (JSONB или отдельные таблицы), превью, поле «последнее открытие» и т.п. — **TODO**, отдельный ADR перед стартом работы над редактором.

За пределами ADR:

- **Каталог мебели** (`furniture_*`) — отдельный ADR перед Этапом 3, когда пойдёт наполнение.
- **Демо-проект** — механика хранения пока не решена, откладывается; отдельный ADR ближе к реализации.
- **История/undo, версии проекта, «корзина»** — не тащим на v0, отдельный ADR если появится запрос.

## Драйверы решения

- **Согласованность с моделью из 0005.** Каждая таблица напрямую вытекает из принятой auth-модели.
- **Минимальность.** Только то, без чего Этап 1 не поднимется. Никаких «а вдруг пригодится».
- **Идентификаторы, не раскрывающие порядок и количество.** URL проектов (`/project/:id`) не должен палить, что у нас 42 проекта в системе.
- **Возможность безболезненно расширять.** Первая же миграция сцены/каталога не должна ломать существующую схему.
- **Одинаковая ментальная модель.** Одни и те же соглашения (naming, timestamps, cascade) во всех таблицах — предсказуемо для человека и AI-агента.

## Рассмотренные варианты (макро-выборы)

- **Primary keys:** `bigint serial` vs `UUID v4` vs `UUID v7`.
- **Naming convention:** `snake_case` + множественное число vs `camelCase` vs единственное число.
- **Soft-delete:** нигде vs только на пользовательских сущностях vs везде.
- **Email — тип колонки:** `TEXT` + нормализация в коде vs `CITEXT` extension.
- **`updated_at`:** триггер БД vs ручное обновление в коде.

## Выбранный вариант

### Соглашения (применяются ко всем таблицам)

- **PK:** `UUID v7`. Генерация — на стороне приложения (пакет `uuid` v10+), не через БД-функцию. `UUID v7` даёт сортируемость по времени (лучше индексы, чем `v4`) и не раскрывает порядок/количество (в отличие от `bigint`).
- **Naming:** `snake_case` для таблиц и колонок, множественное число для таблиц (`users`, `projects`, `sessions`, `oauth_accounts`, `password_reset_tokens`).
- **Timestamps:** тип `TIMESTAMPTZ` (UTC-aware). Везде `created_at NOT NULL DEFAULT now()`. `updated_at` — только на таблицах, где сущность реально мутирует (`users`, `projects`), обновляется руками в коде (без триггеров БД — прозрачнее для отладки, проще для тестов).
- **Cascade:** `ON DELETE CASCADE` на всех FK, ведущих к `users` — удаление пользователя автоматически удаляет его сессии, OAuth-привязки, reset-токены, проекты.
- **Email — тип:** `TEXT` + нормализация в коде (перед insert/select приводим к lowercase и trim). CITEXT отсекается ради минимализма — не требуем от Postgres дополнительного extension'а, вся логика в приложении и прозрачна.
- **Soft-delete:** не используется. Всё hard-delete. «Корзину» проектов и восстановление удалённых пользователей — отдельным ADR по запросу.
- **Индексы:** все `UNIQUE` создают индексы автоматически; на все FK добавляем индексы вручную (Postgres не создаёт их сам).
- **Enum-подобные поля:** храним как `TEXT` + `CHECK` constraint. `ENUM` тип Postgres отсекается — `ALTER TYPE ... ADD VALUE` болезненно эволюционирует.
- **Файлы миграций:** одна миграция на одну таблицу в этом ADR (пять миграций общим числом). Порядок: `users` → `sessions` → `oauth_accounts` → `password_reset_tokens` → `projects`. Каждая с `-- migrate:up` и `-- migrate:down` (drop table + drop indexes).

### `users`

Учётка пользователя. Один email = одна учётка. `password_hash` nullable — юзеры, зарегистрированные через OAuth, могут не иметь пароля, пока не установят его в настройках.

| Колонка | Тип | Ограничения | Комментарий |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY` | UUID v7, генерируется в приложении |
| `email` | `TEXT` | `NOT NULL UNIQUE` | Нормализуется (lowercase + trim) перед записью и поиском |
| `password_hash` | `TEXT` | `NULL` | argon2id-хеш; `NULL` для OAuth-only пользователей |
| `email_verified_at` | `TIMESTAMPTZ` | `NULL` | Заложено на будущее; на v0 не заполняется |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | Обновляется в коде при мутации |

Индексы: `UNIQUE (email)` — автоматически.

### `sessions`

Server-side sessions из 0005. `id` = сама случайная строка, которая живёт в cookie у пользователя (opaque, ≥32 байта энтропии, hex/base64url).

| Колонка | Тип | Ограничения | Комментарий |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | Сам `session_id`, случайная строка из cookie |
| `user_id` | `UUID` | `NOT NULL REFERENCES users(id) ON DELETE CASCADE` | |
| `expires_at` | `TIMESTAMPTZ` | `NOT NULL` | Абсолютный дедлайн сессии (rolling refresh продлевает) |
| `last_activity_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | Обновляется при активности для rolling TTL |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | |

Индексы:
- `(user_id)` — для операции «инвалидировать все сессии пользователя» (например, после password reset).
- `(expires_at)` — для периодической очистки протухших сессий (cron / `DELETE FROM sessions WHERE expires_at < now()`).

**Session ID хранится как есть**, без хеширования. Обоснование: session_id никогда не публикуется наружу (живёт только в HttpOnly cookie), при компрометации БД злоумышленник получает более серьёзные последствия, чем возможность залогиниться. Хеширование добавит cost на каждый запрос без реального security-профита в этой модели.

### `oauth_accounts`

Привязки локального пользователя к OAuth-провайдерам (Yandex ID, VK ID). Один пользователь может иметь несколько привязок (например, и Yandex, и VK), но не больше одной на каждого провайдера.

| Колонка | Тип | Ограничения | Комментарий |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY` | UUID v7 |
| `user_id` | `UUID` | `NOT NULL REFERENCES users(id) ON DELETE CASCADE` | |
| `provider` | `TEXT` | `NOT NULL CHECK (provider IN ('yandex', 'vk'))` | Расширяется через новую миграцию (drop + recreate CHECK) |
| `provider_user_id` | `TEXT` | `NOT NULL` | Идентификатор пользователя у провайдера |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | |

Индексы:
- `UNIQUE (provider, provider_user_id)` — быстрый lookup при OAuth-логине; гарантирует, что один провайдерский аккаунт не привязан к двум локальным.
- `UNIQUE (user_id, provider)` — один пользователь = максимум одна привязка на провайдера.
- `(user_id)` — для чтения всех привязок пользователя (страница настроек безопасности).

Токены провайдера (access_token, refresh_token) **не сохраняются** — по решению из 0005 они используются только в момент callback'а для получения `provider_user_id`/email.

### `password_reset_tokens`

Одноразовые токены для сброса пароля из 0005. В БД хранится **sha256-хеш** от raw токена (raw токен уходит в email — сохранять raw в БД повышает риск утечки через backups/логи).

| Колонка | Тип | Ограничения | Комментарий |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY` | UUID v7 |
| `user_id` | `UUID` | `NOT NULL REFERENCES users(id) ON DELETE CASCADE` | |
| `token_hash` | `TEXT` | `NOT NULL UNIQUE` | sha256 от raw токена; raw токен хранится только в письме |
| `expires_at` | `TIMESTAMPTZ` | `NOT NULL` | TTL 1 час от `created_at` (см. 0005) |
| `used_at` | `TIMESTAMPTZ` | `NULL` | Заполняется при успешном использовании; повторное использование запрещено |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | |

Индексы:
- `UNIQUE (token_hash)` — автоматически, основной lookup при переходе по ссылке из письма.
- `(user_id)` — для инвалидации всех reset-токенов пользователя после успешной смены пароля.
- `(expires_at)` — для периодической очистки протухших токенов.

### `projects`

Проект интерьера, принадлежащий пользователю. **В v0 в этом ADR фиксируется только структурная оболочка** — id, владелец, имя, timestamps. Хранение сцены (геометрия комнаты, объекты, материалы) откладывается на отдельный ADR перед реализацией редактора; технически это будет либо колонка `scene JSONB`, либо отдельные таблицы `project_walls` / `project_objects` — решение по итогам обсуждения UX редактора и требований к запросам по содержимому сцены.

| Колонка | Тип | Ограничения | Комментарий |
|---|---|---|---|
| `id` | `UUID` | `PRIMARY KEY` | UUID v7 |
| `user_id` | `UUID` | `NOT NULL REFERENCES users(id) ON DELETE CASCADE` | |
| `name` | `TEXT` | `NOT NULL` | Название проекта, отображаемое пользователю |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` | Обновляется при любом изменении проекта |

Индексы:
- `(user_id)` — для страницы «мои проекты».
- **TODO** — индексы по будущим полям (например, `(user_id, updated_at DESC)` для сортировки «последние изменённые») добавим вместе с этими полями.

**Что явно оставлено TODO для отдельного ADR:**

- Хранение сцены: `scene JSONB` целиком vs отдельные таблицы объектов сцены.
- Превью проекта: `thumbnail_url` или blob (после появления генерации превью).
- Поле «последнее открытие»: `last_opened_at` (после появления сортировки в списке проектов).
- Механика демо-проекта: живёт ли он в БД (system-user + `is_demo` флаг) или seed-ом в коде.

## Обоснование

### Почему UUID v7 в приложении, а не в БД

- `UUID v7` даёт сортируемость по времени → индексы работают лучше, чем на `v4` (случайные вставки в B-tree создают дефрагментацию).
- Генерация в приложении даёт свободу от `pgcrypto`/`uuid-ossp` extension'ов, а встроенный `gen_random_uuid()` даёт `v4`. Ждать нативного `uuidv7()` во всех версиях Postgres смысла нет — библиотека `uuid` в Node это уже умеет.
- Приложение всегда знает ID до `INSERT` — удобно для логов, идемпотентных операций, retry-логики.

### Почему `TEXT` + нормализация email, а не CITEXT

- CITEXT требует включения extension'а — дополнительный setup-шаг, лишняя зависимость от версии Postgres.
- Нормализация в коде прозрачна: явно видно `email.trim().toLowerCase()` перед запросом, легко покрыть тестами.
- CITEXT медленнее обычного TEXT на индексах.

### Почему `updated_at` руками в коде, а не через триггер

- Триггер прячет мутацию — при debug'е неочевидно, почему `updated_at` изменился.
- Ручное обновление проще тестировать (в тесте не нужно поднимать реальный Postgres с триггерами).
- Kysely без магии: `.set({ ..., updated_at: new Date() })` в каждом update — согласуется с философией «никакой магии» из 0004.

### Почему hard-delete

- «Корзина» проектов и восстановление пользователей — это фичи, которые нужны, когда они нужны. На v0 нет запроса.
- Soft-delete добавляет `WHERE deleted_at IS NULL` в каждый запрос — риск забыть и показать удалённые данные.
- Каскадное удаление через FK покрывает базовую consistency (удалили пользователя → удалили его данные).

### Почему `TEXT` + `CHECK` для enum-подобных полей, а не PostgreSQL `ENUM`

- `ALTER TYPE ... ADD VALUE` в Postgres не работает внутри транзакции с использованием этого значения → миграции становятся хрупкими.
- `TEXT + CHECK` даёт то же самое ограничение, но легче эволюционирует (`ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT`).
- Kysely-типы enum'ов пишутся руками в TS-схеме — не зависит от того, `ENUM` в БД или `TEXT`.

### Почему session_id не хешируется, а password reset token — хешируется

- **session_id** живёт только в HttpOnly cookie, никогда не публикуется через API. Attack surface — компрометация БД. Если БД скомпрометирована, есть проблемы посерьёзнее возможности логина.
- **reset token** уходит в email — потенциально попадает в почтовые логи провайдера, в backup'ы, в screenshots. Attack surface шире; хеширование в БД — стандартная защита.

## Последствия

### Плюсы

- Минимальная схема — только auth + оболочка `projects`. Ничего лишнего.
- Все PK, FK и cascade-правила согласованы, каскадное удаление пользователя работает предсказуемо.
- Соглашения одинаковы во всех таблицах — легко добавить новую таблицу по образцу.
- Ничего не завязано на extension'ы Postgres — минимальные требования к БД.
- Расширение схемы для сцены и каталога не потребует переделывать существующие таблицы.

### Минусы

- **`projects` без содержимого сцены не даёт реального функционала** — только «создать пустой проект». Полноценный редактор требует отдельного ADR перед стартом Этапа 2.
- **Ручное обновление `updated_at`** — риск забыть в новом коде. Компенсируется общей обёрткой в repository-функциях (когда появятся).
- **`ON DELETE CASCADE` для `projects`** означает, что удаление пользователя мгновенно уничтожит все его проекты. Если появится требование «сохранить проекты при удалении аккаунта» — переделывать через soft-delete + отвязку.
- **CHECK-констрейнт на `provider`** нужно обновлять миграцией при добавлении нового OAuth-провайдера. Приемлемо: провайдеры добавляются редко.
- **`sessions.id` как opaque строка** означает, что при отладке в БД её нельзя сопоставить со «своей» сессией без cookie в браузере. Приемлемо.

## Как проверить/пересмотреть

- **Появилась потребность в кросс-сущностных запросах** (например, «все проекты, обновлённые за последние 7 дней») → добавить нужные индексы отдельной миграцией.
- **Пользователи регулярно жалуются на утерянные проекты после удаления аккаунта** → пересмотреть cascade-политику для `projects` в пользу soft-delete/архива.
- **Rate limiting на auth-эндпоинтах потребовал состояние в БД** (не in-memory) → отдельная таблица `auth_rate_limits` через новую миграцию.
- **Появился второй OAuth-провайдер, не влезающий в текущий CHECK** → миграция на расширение CHECK-констрейнта.
- **Появились требования к аналитике** (метрики регистраций, ретенция) → отдельные таблицы событий, не тащим в основную схему.
- **Формат session ID перестал устраивать** (например, требование к длине из-за smart TV клиента) → миграция типа или отдельного поля.
