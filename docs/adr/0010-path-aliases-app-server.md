# 0010. Path aliases: `@app/*` для клиента, `@server/*` для сервера

- Статус: Принято
- Дата: 2026-08-09
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0007 зафиксировал модульную раскладку `apps/platform/src/`: `client/`, `server/`, `shared/`. Внутри каждого — несколько модулей верхнего уровня (`core`, `common`, `application`, доменные модули). К моменту старта скелета нужен зафиксированный синтаксис импортов между модулями — иначе один разработчик неизбежно наплодит разных стилей в разных файлах, а вайбкодинг-агент будет угадывать.

## Драйверы решения

- **Устойчивость при перемещении файлов.** Модули будут переезжать и переименовываться в v0 — импорты не должны ломаться на каждом рефакторинге.
- **Enforcement client/server-границы.** ADR 0007 запрещает импорты между `client/` и `server/`. Синтаксис алиасов должен делать такое нарушение визуально очевидным (и, в идеале, ломаться на этапе резолвинга).
- **Читаемость.** По одному импорту в шапке файла должно быть понятно, из какой стороны приложения он тянется.
- **Автокомплит в IDE.** Алиасы должны корректно резолвиться TS-сервером без танцев с бубном.

## Рассмотренные варианты

- **Вариант A: Относительные пути** — `import { api } from '../../core/api'`.
- **Вариант B: Один общий алиас** — `@/*` для всего `apps/platform/src/`.
- **Вариант C: Раздельные алиасы по сторонам** — `@app/*` для `src/client/*`, `@server/*` для `src/server/*`.

## Выбранный вариант

**Выбран: Вариант C.** Раздельные алиасы явно подкрепляют границу client/server, зафиксированную в ADR 0007, и делают нарушение границы визуально невозможным незаметно.

## Обоснование

### Почему не A (относительные)

- В модульной структуре с 5+ модулями на каждой стороне относительные пути превращаются в `../../../common/hooks/useX` — нечитаемо, ломается при каждом перемещении файла.
- Не даёт никакого enforcement для client/server-разделения: `import { db } from '../../server/lib/db'` из клиентского файла выглядит как обычный относительный импорт.

### Почему не B (общий `@/*`)

- Не отражает границу. Импорт `@/lib/db` из клиентского файла и `@/lib/http` из серверного — визуально идентичны, хотя имеют принципиально разное значение.
- Ошибочный кросс-импорт (клиент тянет из `@/server/...`) будет разрешаться резолвером и заметится только на билде или в рантайме.
- Стандартный `@/*` пришёл из шаблонов монолитных SPA (Vite, Next.js), где нет client/server-раздела на уровне файловой структуры — у нас есть.

### Что даёт C

- **Явная граница.** В шапке файла сразу видно: `@app/*` → клиентский код, `@server/*` → серверный. Нет двусмысленности.
- **Ошибка на резолвинге.** `import { db } from '@server/lib/db'` в клиентском файле не пройдёт: клиентский `tsconfig` не знает про алиас `@server/*`, webpack-клиент — тоже не знает. Билд падает сразу, а не в проде.
- **Симметрия.** Клиент и сервер выглядят как два самостоятельных приложения со своими локальными импортами — это соответствует ADR 0007 (client и server — самостоятельные графы модулей, соединённые через `shared/` и HTTP).

## Что фиксируется этим ADR

- В клиентском `tsconfig` и webpack-конфиге клиента: `@app/*` → `apps/platform/src/client/*`. Никаких других алиасов на клиенте.
- В серверном `tsconfig` и webpack-конфиге сервера: `@server/*` → `apps/platform/src/server/*`. Никаких других алиасов на сервере.
- Импорты из `src/shared/*` — относительными путями либо через отдельный алиас `@shared/*` (см. ниже). В v0 стартуем с относительных, потому что `shared/` в v0 плоский (несколько файлов, не модули).
- Между `client/` и `server/` — импорты запрещены (ADR 0007), алиасы это подкрепляют.

## Что НЕ фиксируется этим ADR

- Алиас `@shared/*` — не заводим на старте. Если `shared/` разрастётся до модульной структуры (5+ директорий) — добавить отдельным решением, не ADR.
- Алиасы внутри отдельных модулей (например, `@core/*` внутри `core`) — не заводим, это переусложнение.

## Последствия

### Плюсы

- Кросс-импорты client ↔ server физически не резолвятся — граница enforced без ESLint-правил.
- Читаемость: по одному импорту понятно, к какой стороне относится файл.
- Устойчивость к перемещениям файлов внутри `client/` или `server/`.
- Автокомплит и «go to definition» работают из коробки — TS-сервер понимает алиасы по `tsconfig`.

### Минусы

- **Два алиаса вместо одного стандартного `@/*`.** Небольшой отход от привычного для новых разработчиков (если такие появятся) шаблона.
- **Дублирование конфига.** Алиасы прописываются и в `tsconfig`, и в webpack-конфигах (клиент, сервер) — три места на изменение. Приемлемо, потому что меняются крайне редко.
- **Импорты из `shared/`** — относительные (пока), что немного асимметрично с client/server.

## Как проверить/пересмотреть

- **Если `shared/` разрастётся до модульной структуры** → добавить алиас `@shared/*` (не через ADR, простым конфигом).
- **Если начнутся кейсы, когда `@app/*` действительно нужен на сервере или наоборот** (например, если появится SSR-prefetch, требующий вызова клиентского кода из серверного middleware) → это сигнал, что нарушается ADR 0007 или 0008, а не что алиасы плохие.
