# 0010. Path aliases: `@app/*` для клиента, `@server/*` для сервера

- Статус: Принято
- Дата: 2026-08-09

## Решение

- В клиентском `tsconfig` и webpack-конфиге клиента: `@app/*` → `apps/platform/src/client/*`. Никаких других алиасов на клиенте.
- В серверном `tsconfig` и webpack-конфиге сервера: `@server/*` → `apps/platform/src/server/*`. Дополнительно на сервере зарегистрирован `@app/*` → `apps/platform/src/client/*`, но **пользоваться им можно только внутри `src/server/application/**` и только для SSR-обвязки** (см. «Исключение для SSR» ниже). Никаких других алиасов на сервере.
- У воркспейс-пакетов (`packages/*`, например `@uyutno/planner`, ADR 0015) алиаса `@app/*`/`@server/*` нет и быть не должно: внутри пакета — относительные импорты, платформа импортирует пакет по npm-имени (`@uyutno/planner`), а не по алиасу.
- Импорты из `src/shared/*` — относительными путями (в v0 `shared/` плоский, несколько файлов). Алиас `@shared/*` — заведём, если разрастётся до модульной структуры (5+ директорий), не через ADR.
- Между `client/` и `server/` — импорты запрещены (ADR 0007). Единственное исключение — SSR-точка входа в модуле `application`, см. ниже.

## Почему

Относительные пути в модульной структуре с 5+ модулями на каждой стороне превращаются в `../../../common/hooks/useX` — нечитаемо, ломается при каждом перемещении файла и не даёт enforcement для client/server-разделения (`import { db } from '../../server/lib/db'` из клиентского файла выглядит как обычный относительный импорт). Один общий `@/*` не отражает границу — `@/lib/db` из клиентского файла и `@/lib/http` из серверного визуально идентичны, ошибочный кросс-импорт разрешится резолвером и заметится только на билде или в рантайме. Раздельные алиасы: `import { db } from '@server/lib/db'` в клиентском файле не пройдёт резолвинга (клиентский `tsconfig` не знает про `@server/*`, webpack-клиент — тоже) — билд падает сразу, а не в проде. Симметрия с ADR 0007, где client и server — самостоятельные графы модулей, соединённые через `shared/` и HTTP.

## Исключение для SSR

Серверу нужно рендерить корневой React-компонент клиента (`Application`) в `renderToString` — это неизбежно, иначе SSR не работает. Формально это кросс-импорт client → server, но по факту — единственная точка стыковки двух графов, и она полностью изолирована в модуле `application` (SSR-middleware).

Правила:

- `@app/*` на сервере разрешён **только в `src/server/application/**`** (в частности — в SSR-middleware, который импортирует корневой `Application` из клиента). В остальных серверных модулях `@app/*` не должен резолвиться на уровне линтера.
- Из клиента импортируется **только корневой `Application`-компонент** (публичный API модуля `application` клиента). Никаких «залезаний» в конкретные страницы, хуки, сервисы клиента с сервера.
- Обратное направление (`@server/*` на клиенте) остаётся полностью запрещённым — на клиенте алиаса `@server` нет вообще.

Enforcement: ESLint-override для `apps/platform/src/server/**` (кроме `application/**`) через `no-restricted-imports`, запрещающий паттерн `@app/*`. Заведём одновременно с настройкой остального `no-restricted-imports` по ADR 0007.

## Что важно знать

- **Дублирование конфига.** Алиасы прописываются в `tsconfig` и в webpack-конфигах (клиент, сервер) — три места на изменение. Приемлемо, меняются редко. Из-за исключения для SSR серверный `tsconfig` и `webpack.server.js` содержат `@app/*` — это не ошибка.
- **Импорты из `shared/`** — относительные, что немного асимметрично с client/server.
- **Если появится кейс, где `@app/*` нужен на сервере вне `application/**`** — это сигнал, что нарушается ADR 0007, а не что алиас плохой. Решать переносом кода в `shared/` или на клиент, а не расширением исключения.
