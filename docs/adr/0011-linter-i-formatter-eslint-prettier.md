# 0011. Линтер и форматтер: ESLint 10 (flat config) + Prettier 3

- Статус: Принято
- Дата: 2026-08-09
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0002 упомянул «общие конфиги ESLint / Prettier в корне монорепы» как данность, ADR 0007 зафиксировал энфорс модульных границ через `no-restricted-imports`. Но выбор самого линтера, форматтера и стиля правил как отдельное решение нигде не оформлен. Перед стартом скелета `apps/platform` этот выбор нужно зафиксировать — иначе первый же файл будет отформатирован «как получилось», а конфиг соберётся из случайных статей.

## Драйверы решения

- **Один source of truth для всей монорепы** (ADR 0002) — без per-package дрейфа стиля.
- **Возможность энфорсить модульные границы** через встроенное ESLint-правило `no-restricted-imports` (ADR 0007).
- **Zero-conflict setup.** Линтер и форматтер не должны спорить друг с другом (классическая ловушка ESLint + Prettier без `eslint-config-prettier`).
- **Форматирование не только JS/TS.** У нас много MD (ADR, CLAUDE.md), JSON, YAML (конфиги, `docker-compose`), редко — CSS. Форматтер должен покрывать всё, а не только код.
- **Минимум магии.** Стандартные инструменты с предсказуемым поведением, максимум готовых материалов — под вайбкодинг это критично, потому что AI-агенту проще писать конфиг под мейнстрим-стек.

## Рассмотренные варианты

### Линтер

- **Вариант A1: ESLint 10** (flat config) + `typescript-eslint` + плагины для React.
- **Вариант A2: Biome** — быстрый Rust-линтер, объединяет линтинг и форматирование в один инструмент.
- **Вариант A3: oxlint** — ещё быстрее Biome, но существенно моложе и уже линтинг-ориентирован.

### Форматтер

- **Вариант B1: Prettier 3.**
- **Вариант B2: `@stylistic/eslint-plugin`** — форматирование остаётся в ESLint, отдельный форматтер не нужен.
- **Вариант B3: Biome (formatter)** — если выбран Biome в A.

### Организация конфига

- **Вариант C1: Один общий конфиг в корне монорепы**, per-package конфиги наследуются через `extends` при необходимости.
- **Вариант C2: Per-package конфиги** без общего корневого.

### Строгость правил

- **Вариант D1: Recommended-пресеты** каждого плагина (`@eslint/js/recommended`, `typescript-eslint/recommended`, `react/recommended`, `react-hooks/recommended`).
- **Вариант D2: Strict-пресеты** (`typescript-eslint/strict`, дополнительные правила).
- **Вариант D3: Готовый community-preset** (`airbnb`, `standard`, `xo`).

## Выбранный вариант

**Выбраны: A1 + B1 + C1 + D1.**

Итоговый стек тулинга кода:

- **Линтер:** ESLint 10 (flat config, `eslint.config.js`) + `typescript-eslint` 8 + `eslint-plugin-react` + `eslint-plugin-react-hooks` + `eslint-config-prettier` (гасит правила ESLint, конфликтующие с Prettier).
- **Форматтер:** Prettier 3 — форматирует JS/TS/TSX, MD, JSON, YAML, CSS.
- **Организация конфига:** один `eslint.config.js` и один `.prettierrc` (плюс `.prettierignore`) в корне монорепы. Per-package переопределения — только через flat-config `files`-скоуп в корневом конфиге (по образцу ADR 0007), без отдельных `eslint.config.js` в пакетах.
- **Строгость:** recommended-пресеты плагинов, без strict и без community-стилей. Локальные правила (энфорс модульных границ по ADR 0007, `no-restricted-imports` в клиентских/серверных зонах) — поверх recommended.

## Обоснование

### Почему ESLint, а не Biome / oxlint

- **Экосистема плагинов.** У нас уже задекларирован `no-restricted-imports` (ADR 0007), впереди — правила под TanStack Query, HeroUI, React Aria. Biome/oxlint пока не имеют сравнимой экосистемы плагинов, кастомные правила там писать сложнее.
- **`typescript-eslint`.** Стандарт для TS-специфичных проверок (типизированные правила через parserServices), в Biome/oxlint аналога такой глубины нет.
- **Стабильность.** ESLint 10 (август 2026) — восьмой мажор с 2013 года, поведение и API устаканены. Biome и oxlint активно ломаются между минорами.
- **Скорость не критична.** Мы не Google-масштаб, ESLint 10 на монорепе из одного `apps/platform` отработает за секунды.

### Почему Prettier, а не @stylistic-in-ESLint

- **Prettier форматирует всё:** TS/JS/TSX/MD/JSON/YAML/CSS. `@stylistic/eslint-plugin` — только JS/TS, для MD/JSON/YAML всё равно понадобится второй инструмент. Смысла держать два, когда один справляется, нет.
- **Prettier opinionated.** Не спорим о запятых, длине строк, переносах — экономит десятки коротких дискуссий (внутренних и с AI-агентом).
- **Стандарт.** «Отформатировано Prettier» — общепризнанное решение, любой AI-агент и любая статья по стеку это подразумевает.
- **Развязка ответственностей.** ESLint отвечает за **качество кода** (потенциальные баги, антипаттерны, границы модулей), Prettier — за **форматирование**. Это соответствует официальной позиции ESLint с версии 8.53 (октябрь 2023), где все formatting rules были выделены из ядра.

### Почему один конфиг в корне

- Соответствует ADR 0002 («общие корневые конфиги — цель, не побочный эффект»).
- Flat config ESLint 10 позволяет описывать per-directory скоупы через ключ `files` — все правила клиента/сервера/тестов лежат в одном файле, читаются последовательно, нет каскада наследования из нескольких конфигов.
- Один файл на PR — проще ревью, невозможен per-package дрейф.
- Локальные переопределения (если понадобятся) вводим через `files`-скоуп в этом же файле, а не через отдельный `eslint.config.js` в пакете.

### Почему recommended, а не strict / airbnb

- **Recommended = разумный дефолт.** Ловит настоящие баги и антипаттерны без прения о стиле.
- **Strict** для `typescript-eslint` тянет за собой правила уровня `no-unnecessary-condition`, которые дают много ложных срабатываний в проекте, где типы иногда описывают внешние данные с частично неизвестной формой (Zod-выход, ответы БД до валидации). Включим на конкретные горячие места, если понадобится.
- **Airbnb / standard** — вкусовые пресеты 2010-х годов, тянут кучу spacing/naming-правил, которые пересекаются с Prettier и создают шум. Смысла в них нет.

## Что фиксируется этим ADR

- Линтер — ESLint 10 (мажор), flat config (`eslint.config.js`).
- Плагины линтера — `typescript-eslint` 8 (мажор), `eslint-plugin-react`, `eslint-plugin-react-hooks`, `eslint-config-prettier`. Актуальные минорные/патч-версии тянем на момент установки.
- Форматтер — Prettier 3 (мажор). Форматирует все поддерживаемые типы файлов (JS/TS/TSX/MD/JSON/YAML/CSS).
- Один `eslint.config.js` и один `.prettierrc` в корне монорепы. Per-package конфигов нет.
- База правил — recommended-пресеты плагинов. Поверх — только правила из ADR 0007 (модульные границы).
- ESLint запускается через `pnpm lint`, Prettier — через `pnpm format` (проверка) и `pnpm format:write` (правка). Конкретные npm-скрипты — задача имплементации, не ADR.

## Что НЕ фиксируется этим ADR

- **Stylelint / CSS-линтинг** — не берём. Собственного CSS у нас почти нет (ADR 0009: Tailwind v4, стили классами), тратить конфиг на этот угловой случай нерационально.
- **Git-хуки** (lefthook, husky, pre-commit) — отдельный ADR после стабилизации набора инструментов. Пока линт/формат гоняются руками и в CI.
- **CI-интеграция** — отдельно, когда появится CI.
- **Конкретные правила ESLint** для энфорса модульных границ — уже в ADR 0007, здесь не дублируем.
- **Конкретные ключи `.prettierrc`** (printWidth, tabWidth, semi, trailingComma) — уровень имплементации. Дефолты Prettier 3 нас устраивают, отклонения — по факту в PR.

## Последствия

### Плюсы

- Мейнстрим-стек, максимальная предсказуемость для человека и AI-агента.
- Одно место правды для правил — один PR меняет стиль во всей монорепе.
- Развязка «качество vs форматирование» — ESLint и Prettier делают разные вещи и не спорят.
- Один форматтер на все типы файлов, включая MD/JSON/YAML — не надо держать в голове разные тулы для доки и кода.
- Flat config современнее legacy `.eslintrc` и заявлен ESLint как единственный поддерживаемый формат в мажорах 10+.

### Минусы

- **ESLint медленнее Biome/oxlint** — на масштабе v0 незаметно, при росте монорепы может стать ощутимым.
- **Два инструмента вместо одного** (ESLint + Prettier) — два конфига, две зависимости, два CLI. Компенсируется тем, что каждый делает своё дело хорошо.
- **`eslint-config-prettier` — обязательная зависимость.** Без него ESLint и Prettier начнут ругаться на одни и те же строки с разных сторон. Легко забыть при первичной настройке — фиксируем это здесь явно.
- **Flat config** пока имеет меньше готовых пресетов, чем legacy — часть плагинов ещё догоняют. На нашем наборе (`typescript-eslint`, `eslint-plugin-react`) поддержка полная.

## Как проверить/пересмотреть

- **ESLint стал заметно тормозить CI/локальный `lint`** (десятки секунд на маленькой монорепе) → рассмотреть переход на Biome/oxlint отдельным ADR.
- **Postоянно натыкаемся на баги, которые recommended не ловит** → включить `typescript-eslint/strict` целиком или точечно.
- **Prettier-дефолты начали раздражать** (например, printWidth) → правим `.prettierrc`, не пересматривая ADR.
- **Появилось много собственного CSS**, не покрываемого Tailwind → добавить Stylelint отдельным решением (не обязательно ADR).
