# Архитектурные решения (ADR)

В этой директории хранятся Architecture Decision Records (ADR) проекта uyutno.

ADR — это короткий документ, фиксирующий важное архитектурное решение и его причины. ADR нумеруются последовательно. Если решение поменялось — **переписываем существующий ADR** по месту (обновляем содержимое, дату, при необходимости имя файла и индекс). Новый ADR-заместитель не заводим — история хранится в git.

## Формат

Каждый ADR состоит из трёх секций:

- **Решение** — что решили, конкретно и без воды. Если у решения несколько компонентов — списком или таблицей.
- **Почему** — реальные ограничения и причины. Если отсекали альтернативы — коротко, «X отсекается, потому что Y». Никаких выдуманных плюсов/минусов «для галочки».
- **Что важно знать** _(необязательно)_ — неочевидные последствия, компромиссы, подводные камни. Не пишем, если нечего сказать.

Шаблон: [`template.md`](./template.md).

### Правила

- **Не выдумывать.** В «Почему» и «Что важно знать» — только то, что реально обсуждалось или является неочевидным следствием. Не заполнять секции ради структуры.
- **Не писать альтернативы отдельным блоком.** Если альтернатива была отвергнута — упомянуть в «Почему» одной строкой с причиной. Списки «Рассмотренные варианты» с сравнительной таблицей плюсов/минусов не заводим.
- **Не писать «Плюсы» и «Минусы» отдельно.** Плюсы — это и есть решение с его «Почему». Минусы, если неочевидные, идут в «Что важно знать».
- **Не заводить секцию «Ссылки».** Если ссылка нужна — вставляем inline в текст.
- **Держать в один экран.** Если получается больше — вероятно, пытаемся зафиксировать несколько решений в одном ADR. Разбиваем.

## Когда писать ADR

ADR нужен, когда решение:

- **дорого или невозможно откатить** (модель данных, паттерн undo/redo, формат хранения, система координат, схема идентификаторов и т.п.);
- **затрагивает несколько модулей или слоёв**;
- **противоречит очевидному дефолту** (например, «почему НЕ react-three-fiber?»);
- **скорее всего вызовет вопросы позже** («а почему мы так сделали?»).

**Не нужно писать ADR** для обратимых локальных решений (структура конкретного UI-компонента, именование CSS-классов, выбор мелкой утилитарной библиотеки).

## Как добавить новый ADR

1. Скопировать `template.md` в файл `NNNN-короткое-название-через-дефис.md`, где `NNNN` — следующий 4-значный номер по порядку.
2. Заполнить секции. Держать коротко — по возможности один экран.
3. Поставить `Статус: Предложено`.
4. Открыть PR. Обсудить.
5. После мержа — поменять статус на `Принято`.

## Переходы статусов

- `Предложено` → `Принято` (мерж) или `Отклонено` (закрытие без мержа).
- `Принято` → `Устарело` (больше не применяется).

Не удаляем ADR. При изменении решения — редактируем существующий ADR по месту (см. вступление); история изменений — в git.
