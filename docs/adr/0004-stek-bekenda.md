# 0004. Стек бэкенда: REST на Express, Kysely + pg, миграции через dbmate, валидация через Zod

- Статус: Принято
- Дата: 2026-08-08
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

ADR 0003 зафиксировал, что `apps/platform` — единое приложение на Express с React SSR. Тот же Express-процесс обслуживает и API-эндпоинты, к которым обращается клиентский код редактора и личного кабинета. Нужно зафиксировать, как устроен серверный API-слой поверх Express: стиль API, работа с PostgreSQL, миграции схемы, валидация входа.

Из общих ограничений проекта: PostgreSQL — self-hosted, инфра — РФ-хостинг, деплой — bash-скриптами, vendor-специфика нежелательна. Разработчик один, БД в единственном экземпляре, схема на v0 будет меняться часто.

## Драйверы решения

- **Минимум магии и vendor-специфики.** Стек должен быть предсказуемым и легко отлаживаемым — от HTTP-запроса до SQL-строки.
- **Типобезопасность без цены.** Тайпы должны идти сквозь стек (валидация запроса → SQL → ответ клиенту), но не за счёт тяжёлых code-gen пайплайнов и своих schema-языков.
- **Синхронизация кода и схемы БД.** Учитывая работу через вайбкодинг и один продовый инстанс — изменения схемы должны быть версионированы и воспроизводимы, иначе будут постепенно расходиться с кодом.
- **Простота отладки.** REST-эндпоинт можно дёрнуть curl'ом, SQL из query builder'а — прочитать глазами. Никаких «а как это в фреймворке» на критическом пути.
- **Возможность потом отдать API наружу.** Публичный API в v0 не нужен, но стек не должен закрывать эту дверь (например, tRPC — закрывает).

## Рассмотренные варианты

### API-стиль

- **Вариант A1: REST.** Доменные роуты вида `/api/v1/<domain>`, JSON-payloads, стандартные HTTP-статусы.
- **Вариант A2: tRPC.** End-to-end type-safe RPC, типы шарятся между клиентом и сервером через single TS-модуль.
- **Вариант A3: GraphQL.** Единый эндпоинт со схемой, клиент запрашивает нужные поля.

### Работа с PostgreSQL

- **Вариант B1: Голый `pg` (node-postgres) + сырые SQL-запросы.**
- **Вариант B2: Kysely** — тонкий типобезопасный query builder поверх `pg`, схема БД описывается TS-типами, запросы — SQL-подобный chain API.
- **Вариант B3: Drizzle** — легковесная ORM с SQL-first подходом и собственным DSL для описания схемы.
- **Вариант B4: Prisma** — полновесная ORM с собственным schema-языком (`schema.prisma`) и генерируемым клиентом.

### Миграции БД

- **Вариант C1: Без миграций** — все изменения схемы вносятся руками через psql на продовой БД.
- **Вариант C2: dbmate** — single-binary migrator, файлы миграций — чистый SQL с секциями `-- migrate:up` / `-- migrate:down`, состояние в таблице `schema_migrations`.
- **Вариант C3: Встроенный migrator query builder'а/ORM** (Kysely Migrator, Prisma Migrate, Drizzle Kit).
- **Вариант C4: `.sql`-файлы + свой bash-раннер.**

### Валидация входных данных API

- **Вариант D1: Zod** — TS-first schema-валидатор, схемы = типы.
- **Вариант D2: без формальной валидации** — руками разбирать `req.body`.

## Выбранный вариант

**Выбраны: A1 + B2 + C2 + D1.**

Итоговый стек бэкенда:

- **API-стиль:** REST, доменные роуты `/api/v1/<domain>` под `router`-модули (по домену — `auth`, `projects`, `catalog` и т.п.). JSON-payloads, стандартные HTTP-статусы.
- **PostgreSQL:** Kysely (тайпобезопасный query builder) поверх `pg` (node-postgres). Схема БД описывается TS-типами; запросы пишутся SQL-подобным chain API без code-gen.
- **Миграции:** dbmate. Файлы миграций — чистый SQL в `apps/platform/db/migrations/<timestamp>_<name>.sql` с секциями `-- migrate:up` и `-- migrate:down`. Состояние в таблице `schema_migrations`. Ручные `ALTER TABLE` на проде запрещены — любое изменение схемы едет миграцией, вместе с кодом в одном PR.
- **Валидация входных данных:** Zod. Схемы объявляются один раз и переиспользуются на сервере (валидация `req.body`/`req.query`/`req.params`) и на клиенте (валидация форм, типизация ответов).

## Обоснование

### Почему REST, а не tRPC/GraphQL

- **tRPC** отсекается: даёт бесплатный type-safety, но жёстко связывает клиент и сервер (общий TS-код), плохо ложится на будущих сторонних потребителей (SEO-краулеры, потенциальный мобильный клиент, публичный API) и хуже отлаживается стандартными инструментами. Type-safety без tRPC достижим — через шаринг Zod-схем.
- **GraphQL** отсекается: избыточен для v0-объёма данных и добавляет отдельный слой (schema, resolvers, DataLoader). Для случая «пары CRUD-эндпоинтов + endpoints редактора» — overkill.
- **REST** — понятный, отлаживаемый curl'ом, любой инструмент из коробки, отсутствие vendor-специфики.

### Почему Kysely, а не Prisma/Drizzle/голый pg

- **Prisma** отсекается: тяжёлая, свой schema-язык (`.prisma`), гигантский генерируемый клиент, скрывает SQL. Vendor-подход, противоречит self-hosted-философии и увеличивает cold start.
- **Drizzle** — сильный кандидат, но: собственный DSL с местами странным API, активно ломающиеся изменения — риск на длинной дистанции.
- **Голый `pg`** — теряется типизация runtime-ответов, каждый запрос требует ручного описания результирующего типа. Больно на этапе, где схема меняется часто.
- **Kysely** — минимальный слой поверх `pg`: тайпы приходят из объявленной схемы БД (единый интерфейс `Database`), запросы читаются как SQL, никакой магии и code-gen. Из query builder'а всегда видно, какой SQL уйдёт в БД. Если ситуация требует raw SQL — Kysely его тоже поддерживает.

### Почему dbmate, а не встроенный migrator и не голые SQL-файлы

- **Без миграций** отсекается: с одним продовым инстансом и вайбкодингом схема через месяц начнёт расходиться с ожиданиями кода, воспроизвести состояние на новом сервере станет невозможно, история изменений схемы теряется.
- **Встроенный migrator query builder'а** (Kysely Migrator) отсекается ради развязки: миграции не должны зависеть от конкретного query builder'а. Если завтра захочется сменить Kysely — не хочется одновременно переписывать миграционную систему.
- **Свой bash-раннер поверх `.sql`-файлов** технически возможен, но dbmate уже делает ровно это: single-binary, идемпотентный, up/down, отслеживает применённые миграции. Изобретать здесь нечего.
- **dbmate** — минимальный инструмент, файлы миграций читаются как чистый SQL, никакой magic. Ложится в философию bash-first и self-hosted.

### Почему Zod

- Де-факто стандарт TS-мира для рантайм-валидации со статической типизацией. Схема Zod = TS-тип.
- Одна схема на сервере (валидация `req.body`) и клиенте (валидация форм, типизация ответа API) даёт «бесплатный» type-safety на границе клиент↔сервер без tRPC.
- Активно развивается, огромная экосистема совместимых библиотек (react-hook-form-адаптеры, OpenAPI-генераторы и т.п.).

### Что фиксируется этим ADR

- REST как API-стиль.
- Kysely + `pg` как способ работы с PostgreSQL.
- dbmate как система миграций; ручные изменения схемы на проде запрещены.
- Zod как валидатор входных данных API.
- Смена любого из этих слоёв = новый ADR, замещающий этот.

### Что НЕ фиксируется этим ADR

- **Схема БД v0** (`users`, `projects`, `sessions` и т.п.) — отдельный ADR 0005.
- **Аутентификация** (сессии/JWT, куки, интеграция Yandex ID / VK ID, password hashing) — отдельный ADR.
- **Логгирование**, метрики, error tracking — отдельные ADR по observability, когда придёт время.
- **Background jobs, очереди, cron-задачи** — на v0 не нужны, заведём ADR если появятся.
- **Файловое хранилище** (S3-совместимое / локальные файлы) — заведём ADR, когда появятся файлы (например, превью проектов, загрузка своей мебели в v1).
- **Rate limiting, CORS-политика, security headers** — уровень middleware, не ADR.
- **Организация серверного кода `apps/platform/src/server/*`** — доменное деление и файловая структура зафиксируются по факту, если станет спорным.

## Последствия

### Плюсы

- Полный контроль над SQL: из Kysely-запроса всегда видно, что реально уходит в БД.
- Тайпы идут сквозь стек: Zod-схема валидирует запрос, Kysely-типы описывают ответ БД, всё это шарится с клиентом.
- Миграции синхронизируют код и схему в одном PR — рассинхрон невозможен по построению.
- Все инструменты — минимальные, без code-gen и своих DSL. Одинаковая ментальная модель у автора и у AI-агента, который пишет код.
- Отсутствие vendor-специфики: любой слой заменяется без переезда всего остального.

### Минусы

- **Без ORM больше boilerplate** для типовых CRUD-операций (writeUser, updateUser, deleteUser — три отдельных query builder-цепочки). Приемлемо на масштабе v0, при росте — можно завести собственные repository-хелперы.
- **Ручные миграции требуют дисциплины.** Любое изменение схемы должно ехать миграцией, включая «мелкие» правки (переименование колонки, добавление индекса). Нарушение дисциплины даст рассинхрон.
- **Zod-схемы для API-эндпоинтов надо писать явно** — это отдельный слой boilerplate. Компенсируется тем, что схемы шарятся с клиентом.
- **REST требует ручного описания API-контрактов** между клиентом и сервером. Компенсируется Zod и, при необходимости, генерацией OpenAPI-спеки.
- **Kysely — молодой инструмент** по сравнению с Prisma. Экосистема меньше, некоторые редкие сценарии (сложные CTE, специфичные PostgreSQL-фичи) могут потребовать raw SQL.

## Как проверить/пересмотреть

- **CRUD-boilerplate становится реально болезненным** (десятки почти одинаковых repository-функций) → ввести собственные хелперы или пересмотреть в пользу Drizzle.
- **Kysely перестал справляться со сложными запросами** (постоянно падаем в `sql`-эскейп-хатч) → пересмотреть в пользу более выразительной альтернативы или чистого SQL с типизацией через кодоген.
- **Миграции стали хроническим источником багов** (down-миграции не работают, откат ломает данные) → пересмотреть подход к rollback-стратегии, возможно отказаться от down-секций в пользу forward-only.
- **Появилась реальная потребность в публичном API** → зафиксировать это отдельным ADR, при необходимости добавить OpenAPI-спеку поверх REST.
- **Zod стал узким местом производительности** (валидация тяжёлых payload'ов в редакторе) → рассмотреть более быстрые альтернативы (Valibot, TypeBox) для конкретных горячих путей.
