# 0002. Монорепа на pnpm workspaces с apps/ и packages/

- Статус: Принято
- Дата: 2026-08-08
- Автор(ы): @v0vchansky

## Контекст и постановка задачи

Перед первой строчкой кода нужно зафиксировать физическую структуру репозитория. У проекта на v0 одно приложение (`platform`), но в дальнейшем ожидается разделение общего кода (типы, утилиты, ui-kit) и появление вспомогательных пакетов. Структура должна выдерживать рост без переезда файлов и переписывания импортов.

## Драйверы решения

- **Скорость разработки на v0.** Один пакетный менеджер, один lock-файл, одна команда установки — минимум церемоний.
- **Общий код и конфиги без публикации в npm.** Внутренние пакеты должны быть доступны через простой импорт вида `@uyutno/*`, не через npm-релизы.
- **Возможность вырастать без ломки структуры.** Добавление нового приложения (например, отдельного admin) или нового пакета не должно приводить к пересадке всего репо.
- **Экономия дискового пространства и install-time.** У проекта на React + Three.js и без того будет тяжёлый `node_modules`.
- **Единый source of truth для TypeScript / ESLint / Prettier.** Одинаковые правила по всему коду без per-package дрейфа.

## Рассмотренные варианты

- **Вариант 1: Полирепо.** Отдельные репозитории для каждого приложения и пакета. Общий код публикуется в npm (публичный или приватный registry).
- **Вариант 2: Монорепа на pnpm workspaces, деление `apps/*` + `packages/*`.** Приложения (конечные бинарники/сервисы) лежат в `apps/`, переиспользуемый код — в `packages/`. Внутренние зависимости через `workspace:^`.
- **Вариант 3: Монорепа на pnpm workspaces + Turborepo (или Nx).** То же деление плюс task runner с кешем сборок и графом зависимостей.
- **Вариант 4: Плоская монорепа без разделения `apps/`/`packages/`.** Все воркспейс-пакеты в корне (или в одной директории `workspaces/`) без семантики «приложение vs библиотека».

## Выбранный вариант

**Выбран: Вариант 2** — pnpm workspaces с делением `apps/*` + `packages/*`, без task runner-обвязки поверх.

## Обоснование

- **Полирепо** отсекается: на v0 один app, добавляется overhead координации версий, релизов и разъездов конфигов. Проблема, которую полирепо решает (независимые релиз-циклы, изоляция прав), у нас в v0 не стоит.
- **Turborepo/Nx** отсекается на старте: пока `apps/*` = 1 штука, кеш и `--filter`-граф ничего не ускоряют, а добавляют слой абстракции и конфигов. Ввести Turborepo позже — задача одного вечера и не требует ломки структуры пакетов. Если понадобится — заведём отдельным ADR.
- **Плоская монорепа** отсекается ради читаемости: явное деление `apps/` vs `packages/` сразу отвечает на вопрос «это конечное приложение или переиспользуемая библиотека».
- **pnpm** вместо npm/yarn выбран из-за симлинк-архитектуры (быстрее и компактнее, чем hoisting), встроенных workspaces и корректного разрешения фантомных зависимостей.

### Что фиксируется этим ADR

- Пакетный менеджер: **pnpm** (смена pnpm → что-то другое = новый ADR).
- Структура: `apps/*` для приложений, `packages/*` для переиспользуемого кода.
- Префикс воркспейс-пакетов: `@uyutno/*`.
- Внутренние зависимости резолвятся через `workspace:^`.
- **Общие конфиги TypeScript / ESLint / Prettier — в корне репозитория**, пакеты наследуются от них.
- Версия Node фиксируется через `.nvmrc`.
- Корневой `package.json` — только общие dev-зависимости (линт/форматирование) и общий tooling; продуктовые скрипты живут в пакетах и вызываются через `pnpm --filter <name> <script>`.

### Что НЕ фиксируется этим ADR (остаётся на следующие)

- Стек фронтенда и бэкенда (следующий ADR).
- Внутренняя структура `apps/platform` (клиент/сервер/шаред — отдельное решение).
- CI/CD, деплой, версионирование релизов.
- Task runner (Turborepo/Nx) — вернёмся, если/когда pnpm-скриптов станет мало.

### Стартовый состав

- `apps/platform` — единственное приложение v0 (лендинг + редактор + бэкенд; внутренняя раскладка — вопрос следующих ADR).
- `packages/` — пусто. Заводим пакет тогда, когда появляется реальный дубль кода между приложениями/сервисами.

## Последствия

### Плюсы

- Единый `pnpm install` поднимает весь репозиторий, единый lockfile.
- Общие типы и утилиты выносятся в `packages/*` без npm-публикации.
- Один набор правил TS/ESLint/Prettier — нет per-app дрейфа стиля.
- Понятная семантика директорий: `apps/` = что деплоится, `packages/` = что переиспользуется.
- Простая миграция на Turborepo/Nx позже — без ломки структуры пакетов.

### Минусы

- Требует pnpm-know-how (`--filter`, `workspace:^`, `pnpm-workspace.yaml`) — для команды из одного разработчика приемлемо, для скейлинга — потребуется onboarding-заметка.
- Без Turborepo нет кеша сборок — при росте числа пакетов `pnpm -r build` будет линейным по времени. Приемлемо до 3–5 пакетов.
- Общие конфиги в корне создают связанность: изменение правила ESLint затрагивает все пакеты одновременно (плюс это ещё и цель).
- Параллельный dev-запуск нескольких приложений (когда они появятся) придётся организовывать руками (`pnpm --filter` + `&` / concurrently), пока не введём task runner.

## Как проверить/пересмотреть

- **Число пакетов ≥ 5 и `pnpm -r build` стал заметно медленным** → пересмотреть в пользу Turborepo/Nx.
- **Появилась потребность в независимых релизных циклах или изолированных правах доступа** (например, отдельная команда на отдельное приложение с закрытым доступом) → пересмотреть в пользу полирепо для этого конкретного приложения.
- **Общие корневые конфиги начали мешать** (одному пакету нужны существенно другие правила ESLint / target TS) → допустить локальное переопределение через extends, но не отказ от общего базового конфига.
- **pnpm перестал устраивать** (например, начнутся баги с симлинками в конкретном стеке) → новый ADR, замещающий этот.
