# 0002. Монорепа на pnpm workspaces с apps/ и packages/

- Статус: Принято
- Дата: 2026-08-08

## Решение

- Пакетный менеджер: **pnpm** (workspaces через `pnpm-workspace.yaml`).
- Структура: `apps/*` — конечные приложения, `packages/*` — переиспользуемый код.
- Префикс воркспейс-пакетов: `@uyutno/*`, внутренние зависимости через `workspace:^`.
- **Общие конфиги TS / ESLint / Prettier — в корне монорепы.** Пакеты наследуются от них.
- Корневой `package.json` — только общие dev-зависимости и tooling. Продуктовые скрипты живут в пакетах, вызываются через `pnpm --filter <name> <script>`.
- Версия Node фиксируется через `.nvmrc`.
- Стартовый состав: `apps/platform` (единственное приложение v0), `packages/` — пусто. Заводим пакет, когда появляется реальный дубль кода между приложениями.

## Почему

На v0 один app, но общий код (типы, утилиты, ui-kit) и вспомогательные пакеты будут появляться. Монорепа даёт единый lockfile, единые правила линтинга, шаринг кода без npm-публикации. Полирепо отсекается: overhead координации версий/релизов без реальной задачи, которую он решает. pnpm вместо npm/yarn — симлинк-архитектура (быстрее hoisting), корректное разрешение фантомных зависимостей, встроенные workspaces. Turborepo/Nx не заводим на старте: при одном app кеш и `--filter`-граф ничего не ускоряют, добавление позже — задача одного вечера без ломки структуры пакетов. Плоская структура без `apps/`/`packages/` отсекается ради читаемости — явное деление сразу отвечает «это конечное приложение или библиотека».

## Что важно знать

- **Общие корневые конфиги создают связанность** — правка правила ESLint затрагивает все пакеты сразу. Это цель, не побочный эффект.
- **Без Turborepo `pnpm -r build` линеен по времени** — приемлемо до 3-5 пакетов. При росте — вводим отдельным решением.
- **Параллельный dev-запуск нескольких приложений** (когда они появятся) — руками через `pnpm --filter` + `&` / concurrently, пока не введём task runner.
