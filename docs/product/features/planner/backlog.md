## Планируется после MVP

### Custom uploads: пользовательские модели и текстуры

**Источник:** обсуждение блокера при проектировании планера (2026-08-14); соответствует разделу [12-catalog-uploads.md](12-catalog-uploads.md).
**Ценность:** пользователь может принести свою 3D-модель мебели (GLTF/OBJ) или текстуру (PNG/JPG для обоев, полов, ковров, картин) и использовать наравне с каталогом. Снимает потолок «мой любимый диван IKEA в каталоге не найдётся».
**Стоимость (оценка):** L (2–4 недели). Требует: upload endpoint, серверная валидация файлов (poly count, размер, формат, отсутствие внешних URL), генерация превью, storage файлов, вкладка «My uploads» в UI, конвертирование форматов если решим поддерживать OBJ→GLB.
**Зависимости:**

- Каталог из коробки наполнен (иначе uploads будут единственным источником моделей — рискованно).
- Storage backend для файлов (S3-подобный).
- Решение по квотам (сколько MB на юзера).
- Sandbox для парсинга GLTF (некоторые файлы могут падать рендерер).

**Причина отсрочки:** значительная инженерная работа со своим набором рисков (security, edge cases GLTF), при этом value заменяется хорошим стартовым каталогом. Второй волной — как отдельная фича с чёткой ценностью «принеси своё».

**Sub-questions to resolve when activating:**

- Поддерживаемые форматы кроме GLB (OBJ, GLTF-директория, нужен ли клиентский конвертер).
- Публикация пользовательских загрузок в общий каталог (public flag, workflow модерации).
- Удаление модели, которая уже используется в существующих проектах (soft-delete uploads, warning про ссылки).
- Синхронизация «My uploads» между устройствами (device-level sync, конфликты).
- Квоты на объём личной коллекции (сумма МБ, число загрузок, тарифная сетка).
- Валидация геометрии (UV, нормали, замкнутость): клиент, сервер или оба.
- Цветовые варианты одного продукта: одна карточка с color-picker'ом или отдельные записи (влияет на модель custom uploads и на роль ownership-флага).

### Multi-floor: несколько этажей в одном проекте

**Источник:** обсуждение блокера при проектировании планера (2026-08-14). Data-model уже поддерживает `floors: [Floor]`, но в UI показываем один этаж.
**Ценность:** пользователь проектирует двух-/трёхэтажный дом, видит этажи стопкой в 3D, ходит по лестнице между ними.
**Стоимость (оценка):** L (2–4 недели). Работа: UI-переключатель активного этажа, лестницы как проёмы между этажами, 3D-навигация между этажами в walk-режиме, копирование объектов между этажами.
**Зависимости:**

- Стабильный single-floor в проде.
- Продуктовое решение по лестницам: как их рисуют, как считаются размеры (высота = толщина перекрытия + высота этажа), UX подъёма/спуска в walk.

**Причина отсрочки:** удваивает объём MVP. Data-model уже готова, поэтому retrofitting дешёвый — доделываем только UI и лестницы.

**Sub-questions to resolve when activating:**

- Пол и потолок между этажами: потолок 1-го этажа и пол 2-го — это один объект или два.
- Мини-карта в walk-режиме для ориентации в многоэтажных / больших планировках.

### Read-only просмотр на мобильных и планшетах

**Источник:** обсуждение блокера device-scope при проектировании планера (2026-08-14).
**Ценность:** пользователь может открыть свой проект на смартфоне или планшете, чтобы **посмотреть** или показать клиенту — 2D-план, 3D-orbit, walk-through. Редактирование не работает; пользователь видит подсказку «редактируйте на компьютере». Закрывает основной use-case «показать работу без ноутбука».
**Стоимость (оценка):** M (2-3 недели). Работа: responsive layout, touch-жесты для pan/zoom/orbit, отключение редактирующего UI, режим просмотра сцены в 3D и walk. Ядро планера не трогается.
**Зависимости:**

- Технические заделы в MVP: pointer events, density tokens, размеры через CSS-переменные, responsive-first layout (см. соответствующий ADR).
- Стабильный desktop-режим.

**Причина отсрочки:** отдельная UI-работа, не блокер основного редактирования. Ценность появляется, когда планер уже используется и клиенты хотят «глянуть с телефона».

### Полная touch-поддержка редактирования на планшетах

**Источник:** обсуждение блокера device-scope при проектировании планера (2026-08-14).
**Ценность:** полноценный редактор на iPad — рисование стен, drag углов, размещение мебели, ввод размеров, всё через touch. Сильная фича сама по себе («редактор интерьеров на планшете»), важна для дизайнеров-фрилансеров и продажников на выезде.
**Стоимость (оценка):** L (4-8 недель). Работа: touch-жесты (pinch/two-finger pan/three-finger undo), увеличенные touch-targets через density-токен `comfortable`, on-screen keyboard для SFK-ввода размеров, альтернатива hover (long-press / tap-hold), заменитель клавиатурных shortcut'ов, iPad-специфичные UX-паттерны. Требует полноценного продуктового дизайна для touch-режима.
**Зависимости:**

- Read-only режим просмотра уже реализован (предыдущая фича).
- Продуктовый дизайн touch-UX (какие жесты для каких действий).
- Технические заделы в MVP (те же, что для просмотра).

**Причина отсрочки:** полноценный touch-редактор — это отдельный продукт со своим UX, а не «мобильная версия десктопа». Делать параллельно с MVP — утроить объём работ.

**Sub-questions to resolve when activating:**

- Touch-жесты для мебели (long-press, двухпальцевые пороги).
- Долгий тап и двухпальцевые жесты для выделения/трансформации объектов.
- Полноценный pinch-to-zoom как первичный жест зума (Pointer Events + `setPointerCapture`, а не «два пальца = rotate/pan»).
- Undo на touch (жест, coalescing длинного touch-drag).

### Persistent-группы мебели (Ctrl+G / Ctrl+Shift+G)

**Источник:** обсуждение medium-блокера при проектировании планера (2026-08-14). В MVP работает temporary multi-select (Shift+клик → transform на всех выделенных), но выборка сбрасывается на клик мимо.
**Ценность:** пользователь сохраняет «сцену» — например, обеденную зону (стол + 4 стула + ковёр + люстра) — как persistent-группу. Дальше двигает/поворачивает как единую сущность, даже после закрытия проекта. Экономит выделение при частой работе с типовыми наборами.
**Стоимость (оценка):** M (1-2 недели). Работа: расширение data-model мебели (`groupId?: GroupId`), заведение сущности `Group` в проекте, UI-индикация выделенной группы vs объекта в группе, вход/выход в группу для правки одного объекта, transform как единой сущности (rotate вокруг центра группы), опционально — вложенные группы. Ctrl+G / Ctrl+Shift+G клавиши.
**Зависимости:**

- Multi-select уже работает (в MVP).
- Продуктовое решение по вложенным группам: разрешаем или flat-only?

**Причина отсрочки:** ~80% ценности групп даёт обычный multi-select (уже в MVP). Persistent-часть — дополнительная фича «сохранил и вернулся», меньший приоритет. Data-model мебели расширяется без миграции старых проектов (старые записи = ungrouped).

### Пипетка материала

**Источник:** решение из обсуждения планера (2026-08-15), уточнено 2026-08-17. В MVP материалы применяются через свойства выделенного объекта; Ctrl+C/V материала между гранями конструктива — **есть в v0** (как в reference). Отложен инструмент «пипетка» и список «недавно применённые материалы» (решение 2026-08-17: в v0 быстрый повторный доступ — только через «Избранное» каталога).
**Ценность:** «тыкнул по грани — её материал стал активным, тыкнул по другой — применился» без Ctrl+C/V и без модалки; удобнее для серийной перекраски и для мебели (где copy-paste слота в v0 нет). «Недавние» — полка последних N материалов в модалке каталога.
**Стоимость (оценка):** S (несколько дней). Работа: режим-инструмент в тулбаре, курсор-пипетка, чтение материала грани/слота мебели, применение по клику; для «недавних» — хранение per-user на сервере (как избранное) + полка в модалке.
**Зависимости:** буфер материала (уже в v0), панель свойств, серверное избранное (для «недавних» — та же модель хранения).
**Причина отсрочки:** Ctrl+C/V + избранное закрывают основной сценарий; пипетка и «недавние» — удобство для профи. В reference ни того, ни другого нет.

### Rect zones: многозонная раскладка стены

**Источник:** обсуждение материалов при проектировании планера (2026-08-15); решение снять из v0 — 2026-08-17. В v0 сторона стены несёт один материал (база + финиш) на всю плоскость.
**Ценность:** одна сторона стены несёт несколько материалов, разделённых прямоугольными зонами — панель/вагонка снизу, вертикальная полоса других обоев, акцентная вставка по центру, бордюр из плитки. Reference даёт это только через отдельный саб-редактор «тайл-конфигуратор» (вход → рез плоскости перегородками пополам → выход); мы хотим родной слой поверх грани без смены контекста — это расширение над reference.
**Стоимость (оценка):** M-L. Работа: модель зон на стороне стены (прямоугольники в координатах плоскости стены + материал каждой + «остаточный» материал), UV-раскладка и рендер по зонам, разрывы под проёмами, UI рисования/правки зон, сериализация, миграция save-формата (старые стены = одна зона).
**Зависимости:** стабильные материалы стен v0; выбор UI-подхода (см. ниже); UI-handoff редактора.
**Причина отсрочки:** значительная работа над рендером и UI ради сценария, который у обывателя редок; в v0 хватает «база + финиш».

**Уже принятые решения (2026-08-17), чтобы не перерешивать при активации:**

- **UI-подход — кандидаты в порядке предпочтения:** (а) вид «в фас на стену»: выделил сторону стены → «Раскладка» → ортографический вид стены во всю рабочую область, прямоугольники рисуются как на 2D-плане (снап к краям/друг к другу, размерные инпуты) + числовые поля в панели свойств — переиспользует 2D-инструментарий, точнее 3D; (б) drag прямоугольника прямо на грани в 3D; (в) только числовые поля. Финальный выбор — вместе с UI-дизайном.
- **Undo:** по общему правилу 09 — создание зоны (с унаследованным материалом стены) = 1 шаг; назначение материала зоне = отдельный шаг; сдвиг/ресайз зоны — 1 шаг на mouseUp; удаление зоны = 1 шаг. Никакого отдельного «транзакционного» режима «зона + первый материал атомарно».

### Корзина проектов: soft-delete и восстановление

**Источник:** обсуждение save/load при проектировании планера (2026-08-15); решение снять из v0 — 2026-08-17. В v0 удаление проекта безвозвратное сразу (как в reference и в `features/projects.md`).
**Ценность:** удалённый проект 30 дней лежит в «Корзине» с превью и датой удаления, «Восстановить» возвращает его в галерею с тем же id; прямая ссылка на проект в корзине показывает «Проект в корзине — восстановить?». Защита от «случайно удалил планировку квартиры».
**Стоимость (оценка):** S-M. Работа: `deleted_at` на проекте, фильтрация в списке, раздел «Корзина» в галерее, endpoint restore, cron hard-delete через 30 дней, экран для прямой ссылки на soft-deleted проект, очистка localStorage-черновика.
**Зависимости:** галерея проектов; save/load планера.
**Причина отсрочки:** в v0 проектов мало и они дёшевы; модель хранения проще без второго состояния проекта.

### Мини-карта в walk-режиме

**Источник:** обсуждение планера (2026-08-15).
**Ценность:** в walk-режиме юзер видит своё положение и направление на мини-карте плана в углу экрана. Помогает ориентироваться в больших квартирах / многоэтажках.
**Стоимость (оценка):** S. Работа: overlay в углу walk-viewport, канвас 200×200, рисуем 2D-план + маркер камеры + треугольник направления.
**Зависимости:** стабильный walk-режим.
**Причина отсрочки:** типовая квартира небольшая, ориентация не проблема. Актуально когда появится multi-floor / большие дома.

### Пресеты камер (закладки ракурсов)

**Источник:** обсуждение планера (2026-08-15).
**Ценность:** юзер сохраняет текущий ракурс камеры под именем («вид с кухни», «вид на диван»), потом одним кликом возвращается к нему. Полезно для профи, презентующих клиенту.
**Стоимость (оценка):** S. Работа: кнопка «сохранить ракурс», UI-список пресетов, применение по клику, сериализация в проект. Roomtodo имеет событие `UPDATE_CAMERA_VIEWS`, но реализация во внешнем бандле.
**Зависимости:** стабильный orbit/walk. Хранение пресетов в save-формате.
**Причина отсрочки:** power-user фича. Не нужна обывателю; юзеру хватает автовосстановления последней позиции камеры между сессиями.

**Sub-questions to resolve when activating:**

- Именование пресетов и UI-список (боковая панель / контекстное меню камеры).

### ГОСТ-штриховка полупрозрачных материалов в 2D

**Источник:** обсуждение планера (2026-08-15). В MVP полупрозрачные материалы (стекло, тюль) в 2D показываются простой alpha 0.5 заливкой.
**Ценность:** стандартное чертёжное обозначение (штриховка для стекла, точки для тюля и т.п.) — важно для профи-архитекторов, которые печатают план для клиента.
**Стоимость (оценка):** S-M. Работа: библиотека hatching-паттернов, отрисовка через canvas-pattern, мэппинг тип материала → паттерн.
**Зависимости:** стабильный 2D-рендерер материалов.
**Причина отсрочки:** обыватель не отличает штриховку от alpha; profi-целевая аудитория. Активируем если пойдёт критика от архитекторов.

**Sub-questions to resolve when activating:**

- Правильная ГОСТ-штриховка полупрозрачных материалов в 2D (мэппинг тип материала → паттерн).

### Cloud version history: автоверсии проекта

**Источник:** обсуждение блокера undo при проектировании планера (2026-08-14) — рассматривался как вариант вместо persistent undo, отложен.
**Ценность:** пользователь может откатиться на предыдущую версию проекта через UI галереи версий (как в Figma «Version history»). Компенсирует ограничение in-memory undo (которое сбрасывается на re-open).
**Стоимость (оценка):** M (1–2 недели). Автосохранение periodic snapshots в БД + retention policy + UI галереи версий + возможность «restore this version» + опционально дифф между версиями.
**Зависимости:**

- Автосохранение планера уже есть (раз в 30 сек по dirty-flag).
- Хранилище версий (можно тем же save endpoint с версионированием — или отдельная таблица).
- Решение по retention (хранить N последних? за X дней? бесконечно с явным удалением?).

**Причина отсрочки:** не блокер MVP. Появляется как отдельная value-add фича, когда пользователи начнут жаловаться на потерянные правки.

**Sub-questions to resolve when activating:**

- Персистентность истории undo между сессиями: копим ли историю в проекте на сервере, отдельными снапшотами по расписанию, чтобы undo работал после reload и между устройствами.
- UI-timeline версий проекта, откат на любой предыдущий снапшот, разница между версиями.

### Явное поле толщины стены (per-wall thickness) и настраиваемый дефолт

**Источник:** обсуждение стен при проектировании планера (2026-08-15), уточнено 2026-08-17. В v0 толщина — не атрибут: стена — «мясо» между гранями контуров, при рисовании лента откладывается на константу `DEFAULT_WALL_WIDTH=10`, «ширина» выбранной стены — сдвиг её стороны (как в reference). Разную толщину пользователь получает, двигая стороны, но числа «толщина этой стены» в панели нет.
**Ценность:** пользователь видит и вводит толщину стены числом (несущая 40, перегородка 10) и задаёт дефолт офсета для новых стен в настройках проекта.
**Стоимость (оценка):** M. Работа: поле `thickness?` на стене или пересчёт «ширины» в толщину через ось, редизайн односторонней митры под разнотолщинные стыки, UI-поле в свойствах стены, дефолт в «Настройках проекта», миграция старых проектов.
**Зависимости:** стабильный алгоритм митры (уже в MVP); «Настройки проекта» (бэклог).
**Причина отсрочки:** ломает одностороннюю митру as-is и требует отдельного дизайна алгоритма пересечения стен разной толщины; в v0 сдвига сторон достаточно.

**Sub-questions to resolve when activating:**

- Алгоритм митры на пересечении стен разной толщины (какая сторона «выигрывает»).

### Настройки проекта: дефолты и предпочтения

**Источник:** обсуждение материалов при проектировании планера (2026-08-15).
**Ценность:** пользователь задаёт для проекта дефолты (материалы по типу комнаты, единицы измерения, стиль подписей размеров) и не переопределяет их вручную для каждого объекта.
**Стоимость (оценка):** S-M. Работа: секция «Настройки проекта» в UI, сериализация в save-формат, применение дефолтов при создании новых объектов, миграция существующих значений.
**Зависимости:** стабильный save-формат.

### Шаринг проектов: публичная read-only ссылка, revoke, права доступа

**Источник:** обсуждение save/load при проектировании планера (2026-08-15); решение снять шаринг из v0 — 2026-08-17. В v0 проект открывает только владелец, публичных ссылок нет.
**Ценность:** пользователь делится проектом по ссылке (показать другу/дизайнеру/подрядчику) — единственный вирусный канал редактора. Расширение: revoke (перевыпуск hash), read-write ссылка соавтору, TTL. Получатель может «Скопировать себе».
**Стоимость (оценка):** M. Работа: публичный `hash` проекта + endpoint load-by-hash + тумблер «шаринг on/off»; **режим планера `readOnly`** (скрыть тулбар/инспектор/каталог, отключить историю и автосейв, оставить камеры/видимость) — проектировать как режим, а не набор `if`-ов, он же пригодится для mobile-просмотра; «Скопировать себе» для авторизованного получателя; далее revoke, права, TTL.
**Зависимости:** стабильный save/load; галерея проектов.
**Причина отсрочки:** тянет за собой отдельный read-only режим UI и класс edge-кейсов (гость на чужом проекте, черновики); в v0 фокус на редактировании владельцем. В reference read-only ссылка есть, но платная (pro).

**Sub-questions to resolve when activating:**

- Кто может открыть ссылку (все / только авторизованные), доступность «Скопировать себе» гостю.
- Отзыв share-ссылки (revoke, перевыпуск hash), UX инвалидации ранее выданного публичного URL.

### Debounce/Worker для пересборки геометрии на больших планах

**Источник:** разбор вопросов автору (2026-08-17, Q23). В v0 — полный синхронный пересчёт на каждый коммит (как у reference), с разделением «2D-контурный цикл на коммит / тяжёлая 3D-проекция реже».
