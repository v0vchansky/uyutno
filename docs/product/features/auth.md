# Аутентификация

- Статус: В разработке (v0)
- Ответственный: @v0vchansky
- Handoff: [`docs/ui/handoffs/auth/`](../../ui/handoffs/auth/) — макеты, тема, ассеты.
- Ключевые ADR: [0005 — модель аутентификации](../../adr/0005-model-autentifikatsii.md), [0006 — схема БД](../../adr/0006-shema-bd-v0.md), [0007 — модули и registry](../../adr/0007-arhitektura-proekta-moduli.md).

## Обзор

Фича закрывает вход, регистрацию, восстановление и смену пароля, а также вход через Yandex ID и VK ID. Без аутентификации пользователь не может создать свой проект — гостевого режима в v0 нет (см. [release-v0.md, «Аутентификация»](../release-v0.md)). Демо-проект (`/demo`) доступен без входа, но при попытке сохранить открывает модалку авторизации прямо в редакторе (решение автора 2026-08-19: не редирект на регистрацию — кнопка «Сохранить» и Ctrl+S остаются активны); после успешного входа копия демо-проекта попадает в проекты пользователя. Роут `/project/:id` при этом закрыт `RequireAuth` — гостя в редакторе своего проекта не бывает.

Скоуп продуктовый: как это выглядит и ведёт себя для пользователя. Технические детали (хеширование, флаги cookie, схема БД) — в ADR 0005 и 0006, здесь на них ссылки.

## Роуты

Публичные страницы (Header + Footer, адаптивные):

| Роут                       | Что                       | Гость | Залогинен               |
| -------------------------- | ------------------------- | ----- | ----------------------- |
| `/login`                   | Форма входа               | ✅    | Редирект на `/projects` |
| `/register`                | Форма регистрации         | ✅    | Редирект на `/projects` |
| `/forgot-password`         | Запрос ссылки на сброс    | ✅    | Редирект на `/projects` |
| `/reset-password?token=…`  | Установка нового пароля   | ✅    | Редирект на `/projects` |
| `/auth/callback/:provider` | OAuth-колбэк (yandex, vk) | ✅    | ✅ (сценарий привязки)  |

API:

| Метод и путь                                      | Что                                                     |
| ------------------------------------------------- | ------------------------------------------------------- |
| `POST /api/v1/auth/register`                      | Регистрация email/пароль. Успех — создаёт сессию        |
| `POST /api/v1/auth/login`                         | Вход email/пароль. Успех — создаёт сессию               |
| `POST /api/v1/auth/logout`                        | Удаляет текущую сессию и cookie                         |
| `GET  /api/v1/auth/me`                            | Текущий пользователь либо `null`                        |
| `POST /api/v1/auth/password-reset/request`        | Запросить письмо со ссылкой сброса                      |
| `GET  /api/v1/auth/password-reset/verify?token=…` | Проверка токена перед показом формы                     |
| `POST /api/v1/auth/password-reset/confirm`        | Установка нового пароля по токену                       |
| `GET  /api/v1/auth/oauth/:provider/start`         | Редирект на страницу авторизации провайдера             |
| `GET  /auth/callback/:provider`                   | Обмен кода, вход или регистрация, редирект в приложение |

## Сценарии

### Регистрация email/пароль

1. Пользователь открывает `/register` (сам или по кнопке «Создать проект»).
2. Вводит email и пароль (правила — ниже, в «Валидация»). Соглашается с условиями (правовая строка со ссылками на `/terms` и `/privacy` под кнопкой).
3. Жмёт «Создать аккаунт».
4. Успех — учётка создана, сессия установлена, редирект на `?from` (если задан и валиден) или `/projects`.

Ошибка «email занят» — сообщение прямо в форме, курсор возвращается в поле email.

### Вход email/пароль

1. Пользователь открывает `/login`.
2. Вводит email и пароль, жмёт «Войти».
3. Успех — сессия установлена, редирект на `?from` или `/projects`.

Ошибка «неверная пара логин-пароль» — плашка над кнопкой (не подсказывает, что именно не так — email или пароль).

### Восстановление пароля

1. Пользователь открывает `/forgot-password` по ссылке из `/login`.
2. Вводит email, жмёт «Отправить ссылку».
3. Форма остаётся на месте, под кнопкой появляется плашка успеха: «Если такая почта у нас есть, письмо придёт в течение минуты. Ссылка действует час.» Формулировка намеренно не раскрывает, зарегистрирован ли адрес.
4. Кнопка «Отправить ссылку» блокируется на 60 секунд с обратным отсчётом («Отправить ещё раз через 45 с»).
5. Из письма — переход на `/reset-password?token=…`.
6. Страница `/reset-password` при загрузке проверяет токен. Если валиден — форма «Новый пароль» + «Повторите пароль». Если истёк или неизвестен — вместо формы сообщение и кнопка «Запросить новую ссылку» → `/forgot-password`.
7. После установки нового пароля — редирект на `/login`. Все ранее активные сессии этого юзера инвалидированы (ADR 0005).

Пользователь без пароля (OAuth-only) тоже может пройти этот флоу — так он «получит» пароль впервые.

### Вход/регистрация через Yandex ID и VK ID

Одни и те же кнопки на `/login` и `/register` — сервер сам понимает, нужно логинить существующего пользователя или создавать нового.

1. Клик по кнопке «Yandex ID» / «VK ID» → редирект на `GET /api/v1/auth/oauth/:provider/start`, оттуда — на страницу авторизации провайдера.
2. Провайдер возвращает на `/auth/callback/:provider?code=…&state=…`.
3. Сервер обменивает `code` на профиль (получает `email` + `provider_user_id`), дальше:
   - если `(provider, provider_user_id)` уже привязан — вход;
   - если нет, но `email` не занят — создаём нового пользователя с пустым `password_hash`, привязываем OAuth, входим;
   - если `email` занят локальной учёткой — **отказ** с сообщением «Этот email уже зарегистрирован. Войдите паролем и привяжите Yandex/VK из настроек» (см. ADR 0005 «Коллизия email»). Пользователь редиректится на `/login` с этой плашкой.
4. Успех — сессия установлена, редирект на `?from` (см. ниже про сохранение) или `/projects`.

Токены провайдера не сохраняются — используются только внутри колбэка.

## Гарды и редиректы (`?from` поведение)

Публичные страницы не требуют сессии. Защищённые (в v0 — `/projects`, `/project/:id`) — требуют.

### Захват попытки

- **SSR-переход на защищённый роут без сессии** → сервер редиректит на `/login?from=<encoded pathname+search>`.
- **API-запрос без сессии на защищённый эндпоинт** → сервер отвечает `401 Unauthorized`. Клиентский axios-interceptor ловит `401`, читает `location.pathname + location.search`, редиректит на `/login?from=<encoded>`.

`from` содержит только `pathname + search` (не полный URL), сервер и клиент валидируют, что это относительный путь внутри своего домена — иначе игнорируют (защита от open redirect).

### Сохранение при переключении между экранами auth

Параметр `from` не должен теряться, пока пользователь ходит внутри auth-экранов:

- Ссылка «Зарегистрироваться» на `/login` ведёт на `/register?from=…` (значение подставляется из текущего query).
- Ссылка «Войти» на `/register` ведёт на `/login?from=…`.
- Ссылка «Забыли пароль?» на `/login` ведёт на `/forgot-password?from=…`.
- Ссылка «Вернуться ко входу» на `/forgot-password` и `/reset-password` ведёт на `/login?from=…`.
- OAuth-старт получает `from` из query и прокидывает его через собственный state/cookie (детали — в задаче реализации OAuth), чтобы после callback сработал тот же редирект.

### Использование при успехе

После успешного `POST /auth/register`, `POST /auth/login` или OAuth-колбэка — редирект:

- на `from`, если он есть и валиден (относительный путь);
- иначе — на `/projects`.

После `POST /auth/password-reset/confirm` пользователя редиректит на `/login?from=…` (сессия ещё не создана, `from` сохраняется на будущий логин).

### Уже залогинен

Если залогиненный пользователь открывает `/login`, `/register`, `/forgot-password` или `/reset-password` — сервер редиректит его на `/projects` (или на `from`, если он валиден). Это верно и для SSR, и для клиентской навигации.

## Валидация

- **Email.** Простой regex формата + trim, max 254 символа. Нормализация (lowercase + trim) — в коде, единая для регистрации, входа, восстановления (ADR 0006).
- **Пароль.** Минимум 8 символов, обязательно и буквы, и цифры (подсказка в поле — «Буквы и цифры, минимум 8 символов»). Проверка на клиенте и сервере.
- **Повтор пароля** (только на `/reset-password`). Совпадение с основным полем. Ошибка — красная рамка на втором поле + текст «Пароли не совпадают».

Валидация срабатывает на сабмите, не на каждый ввод. Ошибки конкретных полей — рамка + подпись под полем. Ошибка уровня формы (неверный логин-пароль, expired-token и т.п.) — плашка над кнопкой.

## Состояния форм

- **idle** — обычное состояние.
- **submitting** — кнопка `disabled`, текст меняется: «Входим…» / «Создаём…» / «Отправляем…» / «Сохраняем…».
- **error** — плашка/подпись с ошибкой; форма снова редактируема.
- **success** — только у `/forgot-password`: показывается плашка успеха под кнопкой, форма остаётся на месте, кнопка блокируется на 60 секунд с обратным отсчётом.

Enter в любом поле отправляет форму.

## Rate limiting

Ограничения per-IP и per-email — in-memory (`express-rate-limit`, стандартный store в v0). Стартовые лимиты:

| Эндпоинт                                   | Лимит                                           |
| ------------------------------------------ | ----------------------------------------------- |
| `POST /api/v1/auth/login`                  | 5 запросов / 15 мин на IP + 5 / 15 мин на email |
| `POST /api/v1/auth/register`               | 10 запросов / час на IP                         |
| `POST /api/v1/auth/password-reset/request` | 3 запроса / час на email + 10 / час на IP       |
| `POST /api/v1/auth/password-reset/confirm` | 10 запросов / час на IP                         |
| `GET  /api/v1/auth/oauth/:provider/start`  | 20 запросов / час на IP                         |

Ответ при исчерпании — `429 Too Many Requests`, форма показывает нейтральную плашку «Слишком много попыток, попробуйте позже».

Второй инстанс сервера ломает in-memory rate limit — при масштабировании перейдём на shared store (Redis) отдельным ADR.

## Ошибки — маппинг сообщений

| Ситуация                                      | Что видит пользователь                                                |
| --------------------------------------------- | --------------------------------------------------------------------- |
| `/login` — неверная пара                      | Плашка «Неверная почта или пароль»                                    |
| `/register` — email уже занят                 | Подпись под полем email: «Этот email уже зарегистрирован»             |
| `/register` — пароль не проходит правила      | Подпись под полем пароля с конкретным правилом                        |
| `/forgot-password` — email в неверном формате | Подпись под полем email                                               |
| `/reset-password` — пароли не совпадают       | Красная рамка на втором поле + «Пароли не совпадают»                  |
| `/reset-password` — токен истёк/неизвестен    | Вместо формы: «Ссылка недействительна» + кнопка «Запросить новую»     |
| OAuth — коллизия email                        | Плашка на `/login`: «Этот email уже зарегистрирован. Войдите паролем» |
| `429` от сервера                              | Нейтральная плашка «Слишком много попыток, попробуйте позже»          |
| `5xx` от сервера                              | Нейтральная плашка «Что-то пошло не так, попробуйте ещё раз»          |

Никакие ошибки не раскрывают, зарегистрирован ли конкретный email (кроме явных сценариев: попытка зарегистрировать занятый email в `/register` и коллизия при OAuth).

## Сессия

Cookie `session_id`, opaque строка, `HttpOnly` + `Secure` + `SameSite=Lax` + `Path=/`. TTL 30 дней, rolling refresh — при активности продлеваем. Один пользователь может иметь несколько активных сессий. Логаут удаляет только текущую сессию; успешный `password-reset/confirm` — все.

Детали хранения и обоснование — в ADR 0005 и 0006.

## Что не в скоупе фичи (в v0)

- **Подтверждение email** — поле `email_verified_at` есть в схеме, но в v0 не заполняется (ADR 0005).
- **Кнопка выхода и залогиненный Header** — макетов нет, откладываем.
- **Личный кабинет и настройки безопасности** (смена пароля из ЛК, привязка/отвязка OAuth, список активных сессий) — v1+.
- **Двухфакторная аутентификация** — v1+.
- **Magic link для входа** — не рассматривается.
- **Импорт демо-проекта в аккаунт после регистрации** — относится к фиче демо, не сюда.

## OAuth-провайдеры: используемые эндпоинты

### Yandex ID

Стандартный OAuth 2.0 authorization code flow, без PKCE (клиент — server-side, `client_secret` хранится на сервере).

| Шаг       | Метод/URL                                                                                     | Комментарий                                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| authorize | `GET https://oauth.yandex.ru/authorize?response_type=code&client_id=…&redirect_uri=…&state=…` | Scope наследуется из настроек приложения в кабинете (email — обязателен, чтобы работал сценарий регистрации нового пользователя) |
| token     | `POST https://oauth.yandex.ru/token` (`application/x-www-form-urlencoded`)                    | Тело: `grant_type=authorization_code&code=…&client_id=…&client_secret=…&redirect_uri=…`                                          |
| userinfo  | `GET https://login.yandex.ru/info?format=json`                                                | Заголовок `Authorization: OAuth <access_token>`. Читаем `id` → `provider_user_id`, `default_email` → `email`                     |

`redirect_uri` строится из `PUBLIC_BASE_URL` (см. `apps/platform/README.md`, раздел «Переменные окружения»): `${PUBLIC_BASE_URL}/auth/callback/yandex`.

Токены (`access_token`, `refresh_token`) в БД не сохраняются — сразу после userinfo забываются (ADR 0005).

### VK ID

Пока не реализовано — см. задачу 0022. Кнопка на `/login` и `/register` до 0022 отсутствует в UI, чтобы не вести пользователя в 404.

## Открытые вопросы

- **SMTP-провайдер** — выбор откладывается на отдельную задачу (см. `release-v0.md`, «Открытые вопросы»). До её решения `/forgot-password` и `/reset-password` заблокированы.
- **OAuth-приложение VK ID** — регистрация в кабинете VK, получение `client_id`/`client_secret`, настройка redirect URI — задача 0021. До её решения задача 0022 (сам VK-flow) заблокирована.
