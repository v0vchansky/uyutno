# Механика редактора RoomToDo — обзор и индекс

> **Что это.** Реверс-инжиниринг поведенческой логики редактора-конкурента [roomtodo.com](https://roomtodo.com) по его **не минифицированному** исходнику (`plannercore.js` ~81k строк с оригинальными именами и комментариями; `user.js` — API/сохранение). Цель — иметь готовую к реализации спеку _механики_ нашего будущего редактора, а не описывать её с нуля.
>
> **Статус источника.** Это **референс чужой механики**, а не наши продуктовые решения. Из него мы выведем собственные feature-спеки в `docs/product/features/`. Код конкурента не копируем — здесь описано поведение/правила своими словами, с ссылками на реальные имена классов/функций и номера строк как доказательство, что это из живого кода.
>
> **Важно про доверие.** У каждой секции есть блок «Confidence & gaps»: что точно вычитано из кода, что додумано (inferred), чего не нашли. Перед тем как закладывать что-то в архитектуру — свериться с этим блоком.

## Единицы и система координат

- Все внутренние расстояния — **сантиметры**. Экранные пороги — **пиксели**, переводятся в мир делением на текущий зум `WC.wallsEditor.scale`.
- Координаты округляются до **0.001 см** на каждом снапе (`TR.roundCoord`).
- Плоскость плана: `+X` → мир `+X`; план `+Y` (см) → мир `−Z`; мир `+Y` — высота/верх.

## Архитектура (сквозная для всех секций)

- **Движок отделён от UI.** Ядро (`R2D` / `WC` / `TR`) владеет сценой, геометрией, историей; React-часть — тонкий контроллер поверх фасада (`R2D.createPlannerAPI` → `apiScene`/`apiConstr` и т.д.).
- **Две-слойная модель конструкции:**
  - _Топология_ (`WC.WallsCore`): граф `CPoint`(x,y,type,children,parent,contour) / `CWall`(point1,point2,data) / `CRoom`(points[],outer,triangles[]).
  - _Атрибуты_ (`WC.WallsData`): `DataWall`/`DataCut`/`DataFrame`/`DataPlug`/`DataCover`/`DataCeiling`/`DataPlinth`/`DataArea` — материалы, высоты, видимость; у каждого dirty-флаг и свой `build3D()`.
- **Одна 3D-сцена, много камер:** 2D-план — это НЕ отдельная отрисовка, а та же 3D-сцена сверху через ортокамеру; отдельный Canvas-2D только под черчение стен.
- **⚠️ Контур-first, а не стена-first.** Пользователь рисует замкнутые контуры, а стены/комнаты/полы **регенерируются** из них на каждый чих (`rebuildWallsAndCovers` → триангуляция → трассировка контуров). Комнаты выводятся, а не хранятся. Это фундаментальная развилка (контур-first vs стена-first) — выбрать осознанно.
- **Render-on-demand:** нет постоянного цикла — правка запускает N кадров и стоп (десктоп/мобайл разное число). Один общий `THREE.WebGLRenderer`.

## Сводная карта уверенности и пробелов

> Читать перед тем, как закладывать что-то в архитектуру. «High» — вычитано из кода дословно; остальное — под проверку.

**Сквозные пробелы (повторяются в нескольких секциях):**

1. **Литералы URL эндпоинтов** (`R2D.URL.URL_SAVE_PLAN` и пр.) — в этих файлах их нет, они в отдельном бутстрап/конфиг-бандле. Подтверждены имена констант + метод/тело запроса, но не пути. Нужен конфиг-скрипт, если понадобятся точные URL. (секции 10, 12, 08)
2. **Глубокая 3D-математика вершин/UV** — `findTriWall`/`findTriCover`/`findPlinthSegment`, митринг в `blocksFromContour`, ядро Делоне `TR.triangulate`/`imported_*`, `imported_clean_graph` — **чёрные ящики**: известны контракты, не внутренности. Для пиксель-точного паритета их пришлось бы трассировать или вывести заново. (секции 01, 03, 06)
3. **Заявленный, но спящий код** — `maxActions=100` (лимит истории **не форсится**, надо добавлять trim самим), label `productSizes` (нигде не вызывается в этой сборке), тип-5 `PLINTH` (объявлен, парсера/писателя нет). Не считать это рабочим — это намерение, а не факт. (секции 09, 12)
4. **Порт на современный three.js** — их sRGB/тонмаппинг **легаси и непоследовательны** (энкодинг только на glTF-картах, в конструкторе рендерера не задан). При переносе на r185 цветовое пространство надо решать явно — см. [`../../architecture/threejs-r185-migration.md`](../../architecture/threejs-r185-migration.md). (секции 06, 08)

**Подтверждённые «этого у них нет»** (полезно — не тратить силы, если не нужно):

- Регулярной **сетки-снапа для мебели** нет — снап только к стенам/боксам предметов/углам (04).
- **Коллизий стен в режиме обхода** нет — свободный полёт на фикс-высоте, сквозь стены (08).
- **360°-захвата** нет — панорамы это каталожные ассеты на вывернутой сфере (08).
- **Авто-подписей углов** и внешних размерных цепочек нет (07).
- `private_material` как флага нет — владение через `isOwner()`/`user_key` (06).
- **CSG нет** — дырки проёмов вычитаются триангуляцией грани вокруг них (01, 02).

**Домены с высокой уверенностью (можно опираться):** модель данных и формат сохранения (10), детекция комнат-пайплайн (03), снаппинг стен и state-машины инструментов (01), система выбора/групп/копипейст (05), бинарный формат ассетов и пулы (12), undo-архитектура (09), константы камер/видов (08). Числовые пороги во всех секциях вычитаны из кода.

## Deep-dives — вскрытые «чёрные ящики» (`deep-dives/`)

Низкоуровневые геометрические ядра, вскрытые отдельными глубокими проходами. Главный вопрос каждого — **стандарт или кастом**, чтобы понять, где брать готовую либу, а где переносить их 5-летний опыт.

| Файл                                  | Ядро                  | Вердикт      | Где живёт 5-летний опыт / что делаем                                                                                                                                                                                                                                              |
| ------------------------------------- | --------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deep-dives/01-triangulation-core.md` | Триангуляция (CDT)    | **Стандарт** | Готовая `cdt2d` + `clean-pslg`. Опыт — в **обвязке**: `roundCoord` 0.001, дедуп рёбер, `resplitSegments` (T-стыки), классификация fill/hole по центроиду, отбраковка слайверов. Берём либу, обвязку воспроизводим; чиним O(n²)-дедуп.                                             |
| `deep-dives/02-wall-mitering.md`      | Митринг углов / офсет | **Кастом**   | Самописный per-segment офсет + пересечение линий, band **односторонний**. Несущие правила: ре-митр `0.75π` + тест на переброс спайка, near-parallel `0.05 рад`, `maxConnectorLength=40`. Готовая polygon-offset либа результат **не** повторит — три правила переносим осознанно. |
| `deep-dives/03-contour-tracing.md`    | «Что есть комната»    | **Кастом**   | Flood-fill групп треугольников через не-стеновые рёбра → обход границы по углам поворота (флип обмотки для дырок) → ре-привязка комнат по нечёткому 10×10 перекрытию площадей. Пайплайн переносим; рекурсию → явный стек.                                                         |
| `deep-dives/04-3d-mesh-uv.md`         | 2D→3D меши + UV       | **Кастом**   | Не `ExtrudeGeometry` — ручная сборка вершин/UV в `BufferGeometry` per-triangle. UV = функция (вдоль-стены/высота)/`pixPerMeter=100`, непрерывны за проёмами; части-материалы на ±0.1 см против z-fight. Переписываем сами; риск порта — `texture.encoding`→`colorSpace` (r185).   |

**Итог по ящикам: 1 стандарт, 3 кастома.** Настоящий «ров» конкурента — не сложная CS (Делоне — это библиотека), а накопленная **политика/обвязка вокруг неё**: квантование и чистка входа, правила митров, нечёткая ре-привязка комнат, непрерывность UV за проёмами. Теперь это зафиксировано с номерами строк — можно переносить точечно, а не переоткрывать на граблях.
