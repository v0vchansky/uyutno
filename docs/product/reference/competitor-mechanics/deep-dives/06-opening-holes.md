# Deep-dive 06 — Проёмы: модель на оси → дырка в стене → лутка

Реверс из неминифицированного `plannercore.js`; все номера строк — по этому файлу.
Верхнеуровневое поведение (дроп, снап, Axis/model-представление, сериализация) — в
`../02-doors-windows.md`; здесь — алгоритмические внутренности пайплайна:

```
модель на оси (Axis.models[i], contour + scale + flip + elevation + positions[i])
   │
   ├─ getHoles()            (52990) — проекция силуэта в локальный фрейм КАЖДОЙ из двух граней
   │     └─ triangulateContours(..., inner ∪ holes)  (53147, 53185) — грань триангулируется вокруг дыр
   │           └─ findContourWall (54755) — 2D-контуры граней/дыр → 3D-точки на плоскости стены
   │
   └─ createFramesForAxis() (55677) — те же силуэты в y-down фрейме оси
         ├─ compareAndRebuildContours (54944) — слияние перекрывающихся силуэтов в один
         └─ createFrame3D   (54606) — экструзия контура поперёк стены = лутка (top/bottom)
```

Ключевая асимметрия: **дырки считаются per-грань** (каждая `DataWall` сама
опрашивает касающиеся её оси), а **лутки — per-ось** (одна на группу
перекрывающихся моделей, общая для обеих граней).

---

## Вердикт: standard-or-custom

**Полностью кастомная проективная геометрия + переиспользование их же
cdt2d-обёртки.** Никакого CSG/буля мешей: дырка — это 2D inner-контур, поданный
в `TR.triangulateContours` (обёртка над vendored `cdt2d`+`clean-pslg`, см.
deep-dive 01), а лутка — ручная экструзия контура поперёк толщины стены
(54606). Слияние перекрывающихся проёмов — тоже не полигон-буль библиотекой, а
«триангулируй всё вместе → flood-fill → обведи внешний контур»
(`TR.rebuildContours`, 51094, — тот же механизм, что у комнат, deep-dive 03).

## 1. `getHoles` построчно (52990–53050): силуэт → локальный фрейм грани

Контекст: `me` — это `WC.DataWall` (одна **грань** стены, не стена целиком).
Локальный фрейм грани: `x` — расстояние вдоль грани от `me.point1` (0..длина),
`y` — высота от пола (0..height). Именно в нём построен прямоугольник грани
`A(0,0) B(len,0) C(len,h) D(0,h)` (53111–53114), и в нём же должны оказаться
дырки.

Обход: по всем осям, касающимся этой грани (`me.axes`, 52994; ось попадает в
`DataWall.axes` при `findAxes` → `DW1.axes.push(axis)`, 55386–55387), по всем
моделям оси (53002).

**Шаг 1 — ориентация грани относительно оси (52998–52999):**

```
parallel = dist(wall.point1, axis.point1) < dist(wall.point1, axis.point2)
```

Ось — центральная линия между двумя гранями; её `point1/point2` фиксированы.
Грань «сонаправлена» оси (`parallel = true`), если её начало ближе к началу
оси. Вторая грань той же оси идёт в противоположном направлении обхода (грани
комнаты обходятся по контуру), поэтому для неё тест даёт `false` — это и есть
переключатель «ближняя/дальняя грань».

**Шаг 2 — привязка начала оси к фрейму грани.** Ось короче грани (грань может
тянуться дальше угла), поэтому нужен сдвиг:

- сонаправленная ветка: `proj = projectionPointOnLine(axis.point1, wall.point1,
  wall.point2, false)`; `axisShift = dist(wall.point1, proj)` (53014–53015) —
  где на грани начинается ось;
- встречная ветка: то же самое, но проецируется `axis.point2` (53030–53031) —
  потому что в системе этой грани ось «начинается» со своего конца.

**Шаг 3 — проекция точек силуэта.** Для каждой точки каталожного контура
(`flipX = ±1`, 53008–53010):

сонаправленная грань (53017–53026):

```
P.x = contourX * scaleX * flipX  +  positions[i] * axisLength  +  axisShift
P.y = elevation − contourY * scaleY
```

встречная грань (53029–53043):

```
P.x = contourX * scaleX * (−flipX)  +  (1 − positions[i]) * axisLength  +  axisShift
P.y = elevation − contourY * scaleY          // вертикаль одинакова для обеих граней
```

Т.е. зеркалирование дальней грани — это **два** приёма сразу: знак X у контура
(`−flipX`) и инверсия нормализованной позиции (`1 − pos`). Вертикаль: каталожный
контур хранится в y-down системе (y растёт вниз), `elevation` — высота
подоконника (`sceneObject.y`, 14773), поэтому `P.y = elevation − contourY*scaleY`
даёт мировую высоту. Заметьте: контур уже один раз отзеркален по X при дропе —
`GEOM.P.scalePoints(-1, 1, contourFromString(...))` (55194) — так что «каталожная»
ориентация до этого была ещё и x-инвертирована.

Каждая модель даёт один полигон `holes.push(holePoints)` (53045). Направление
обхода дырки нигде не нормализуется: у дальней грани оно автоматически
обратное (зеркало), и это никому не мешает — `addSeg` в `triangulateContours`
хранит рёбра ненаправленно с дедупом обоих направлений (50932–50965), cdt2d к
winding нечувствителен.

**Когда дырки не строятся вовсе:** `if (! me.solid) holes = getHoles()`
(53119). `solid = true` выставляется на время интерактивного вращения/движения
материала (`startRotateMaterial` 53216–53219, `startMoveMaterial`), т.е. во
время драга текстуры грань пересобирается **без дыр** (дешевле), а
`stopRotateMaterial` (53247–53251) возвращает `solid = false` и делает финальный
`build3D` с дырками.

## 2. Вшивание дырок в грань: `findContourWall` + триангуляция (53093–53211)

`build3D` у `DataWall` собирает:

1. 3D-углы грани `v1..v4` (53093–53096) и её прямоугольный контур в
   `me.contours[0]` (53105–53108).
2. Для каждой дырки — её 3D-контур: `me.contours.push(WC.findContourWall(holes[i],
   me.v1, me.v2, me.faceRight))` (53121–53124). Это **не** для триангуляции — в
   `me.contours` лежат 3D-полилинии для обводки/пикинга; триангуляция получает
   те же 2D-массивы.
3. Триангуляция с дырками как inner-контурами, двумя путями:
   - грань с раскладкой плитки/секций: `TR.triangulateContours(tile.outerContours,
     tile.innerContours.concat(holes), tile.boundContours, [], [])` (53147) — дырки
     подмешиваются к inner-контурам **каждого** тайла;
   - остаточная часть грани (part id = −1): `TR.triangulateContours([[A,B,C,D]],
     partContours.concat(holes), [], [], [])` (53185) — внешний прямоугольник грани,
     внутри — контуры уже занятых частей плюс дырки.

   Классификация «треугольник в дырке → выкинуть» делает flood-fill в обёртке
   (deep-dive 01); UV каждого выжившего треугольника — `WC.findTriWall` (53170,
   разобран в deep-dive 04). `part.area` накапливается по фактическим
   треугольникам (53155) — т.е. площадь для сметы уже за вычетом проёмов.

**`WC.findContourWall(cont2d, v1, v2, reverse)` (54755–54777) построчно.** Это
не «вшиватель дырок», а маппер локальной 2D-точки грани на 3D-плоскость стены:

```
angle = π/2 − azimuth(v1.x, v1.z, v2.x, v2.z)       // 54759
X = v1.x + p.x·sin(angle)                            // 54770
Y = p.y                                              // высота как есть
Z = v1.z + p.x·cos(angle)                            // 54772
```

`p.x` откладывается вдоль направления `v1→v2` в плоскости XZ, `p.y` — мировая
высота. Плюс нюанс: `if (reverse) cont2d.reverse()` (54762) **мутирует входной
массив in place** — для граней `faceRight` дырки к моменту триангуляции уже
перевёрнуты по порядку обхода. На результат триангуляции это не влияет (см.
выше про ненаправленные рёбра), но это скрытая связь по side-effect: порядок
вызовов в `build3D` (сначала 53123, потом 53147/53185) менять нельзя.

Отдельного «вшивания» дырок в контур (bridge/keyhole-разрезов) нет — outer и
inner контуры уходят в cdt2d одним графом рёбер; `TR.resplitSegments` (вызов на
50981) дорезает пересекающиеся рёбра, так что дырка, налезшая на край грани,
просто клипуется триангулятором, а не отвергается.

## 3. `compareAndRebuildContours` построчно (54944–54996): два окна внахлёст → один контур

Вызывается из `createFramesForAxis` (55707) со списком сдвинутых силуэтов всех
моделей оси. Задача — чтобы у двух перекрывающихся проёмов была **одна общая
лутка** по объединённому контуру, а не две пересекающиеся коробки.

**Фаза 1 — группировка (54949–54971), транзитивное замыкание:**

```
пока есть контуры:
    group = [contours.shift()]                      // 54951
    для каждого члена group (включая добавляемых):  // 54954 — i растёт вместе с group
        для каждого оставшегося контура cont:
            comp = TR.compareContours(member, cont) // 54960
            если comp != TR.OUTSIDE:                // 54962
                group.push(cont); удалить из contours
```

Порог слияния — «всё, что не строго врозь»: `INTERSECT`, `CONTAIN`/`BELONG`
(один внутри другого), `COINCIDE`, и даже `CONTACT` (касание по границе) —
любой из них группирует. `TR.compareContours` (50001–50127): AABB-reject →
`OUTSIDE` (50009); любое пересечение пар рёбер (`lineIntersectLine` в режиме
сегментов, 50019) → `INTERSECT`; иначе классификация вершин **и середин рёбер**
как in/out (точки на границе исключаются `pointOnContour`) с ранним выходом
`INTERSECT`, плюс `checkContact` (49942) для различения `CONTACT_*`-вариантов.

**Фаза 2 — соответствие групп исходным индексам (54973–54981):** `corresp[i]` —
массив индексов `inputContours` для группы `i` (через `indexOf`; квирк:
`new Array(contourGroups)` вместо `contourGroups.length`, безвредно —
элементы тут же перезаписываются).

**Фаза 3 — объединение (54983–54992):**

```
remade = TR.rebuildContours(group, [], [], [], [], false, filter)  // 54987
remade = remade[0][0]              // ПЕРВЫЙ внешний контур           54989
resContours.push(indicesToPoints(remade))                        // 54991
```

Все контуры группы подаются как **outer**-контуры; `rebuildContours` (51094)
триангулирует их одним графом, flood-fill'ом собирает заполненные группы
треугольников и обводит внешний контур (`contoursFromGroup`) — это юнион
«триангуляцией», без полигон-буля. `filter = false` (проброшен из 55707) —
без предочистки `filterContours`.

Edge cases, вытекающие из `remade[0][0]`:

- если объединение дало **несколько** несвязных внешних контуров — берётся
  только первый (по построению групп такого быть не должно: в группе всё
  попарно-транзитивно касается);
- **внутренние дыры юниона отбрасываются**: два контура, сложившиеся в кольцо
  (бублик), дадут лутку по внешнему контуру без внутренней;
- контуры, слившиеся из-за простого **касания** (`CONTACT`), тоже становятся
  одной луткой — два окна впритык получат общий контур и общий материал.

Важно: слияние действует **только на лутки**. Дырки в грани (`getHoles`) не
проходят через `compareAndRebuildContours` — перекрывающиеся силуэты уходят в
триангулятор как есть, и там их объединяет сама триангуляция (пересечения
дорезаются `resplitSegments`, внутренность выкидывается flood-fill'ом).

## 4. Лутка: `createFramesForAxis` (55677–55729) + `createFrame3D` (54606–54754)

### Подготовка контуров (55686–55705)

Старые рамы оси удаляются событиями `ELEMENT_DELETE` (55679–55684). Для каждой
модели строится сдвинутый контур **в y-down фрейме оси** (в отличие от
getHoles!):

```
shiftX = axisLength · positions[i]                       // 55689
x' = round((cx·scaleX·flipX + shiftX)·100)/100           // 55698
y' = round((cy·scaleY − elevation)·100)/100              // 55699 — y растёт ВНИЗ
```

`y' = −P.y` из getHoles (там `P.y = elevation − cy·scaleY`). Округление до
0.01 см — стабилизация ключей для дедупа точек в триангуляторе слияния.
`axisShift` тут не нужен: фрейм привязан к `axis.point1`, а не к грани.

Затем слияние (55707) и на каждую группу — один вызов
`WC.createFrame3D(newContours[i], axis.point1, axis.point2, axis.depth,
axis.models[corresp[i][0]])` (55714): **материалы объединённой лутки берутся у
первой модели группы**. Обе половины (`frames[0]` top, `frames[1]` bottom)
получают `modelIDs` всех моделей группы (55716–55718) — так пикинг лутки знает
все проёмы под ней. `axis.finalContours = shiftedContours` (55728) — сырые (не
слитые) контуры остаются на оси и позже читаются в `findPlinthGaps` (53287,
цикл по `me.axes[i].finalContours` на 53293/53297) для детекта разрывов
плинтуса под проёмами.

### `createFrame3D(inpContour, point1, point2, depth, model)` построчно

Константы: `bottomHeight = 2`, `pixPerMeter = 100` (54608–54609).

**1. Поиск стартового угла и низа (54617–54631).** Один проход: `maxY` — max y
в y-down фрейме = **самая нижняя точка проёма в мире** (подоконник/порог);
`iCorner` — индекс точки с максимальным running-`maxX` (условие
`inpContour[i].y > maxY || inpContour[i].x > maxX` после апдейта `maxY` на
предыдущей строке почти всегда решается по `x`; выглядит как недописанный
«правый-нижний угол», фактически — «самая правая»). Контур циклически
сдвигается, чтобы обход начинался с этого угла (54631) — туда ложится **шов
UV-ленты**, т.е. стык текстуры оказывается в углу проёма, а не посреди косяка.

**2. Рамка = экструзия контура поперёк стены (54634–54713).** Ориентация:
`ang = azimuth(point1.x, −point1.y, point2.x, −point2.y)` — направление оси в
мировом XZ (54635); `center = (point1.x, 0, −point1.y)` (54636). Контур
замыкается дублированием первой точки (54638). Для каждого сегмента `P1→P2`:

```
dV = |P1P2| (в 2D-фрейме)                                // 54651
V1,V2 = точки P1,P2 на стороне −depth/2                  // 54653–54662
V3,V4 = точки P2,P1 на стороне +depth/2                  // 54664–54672
    V.x = center.x + P.x·cos(ang) ∓ (depth/2)·sin(−ang)
    V.y = −P.y                                            // y-down → мировая высота
    V.z = center.z + P.x·sin(ang) ∓ (depth/2)·cos(−ang)
два треугольника: (V3,V2,V1) и (V1,V4,V3)                // 54685/54698
```

Каждый сегмент контура становится полосой шириной `depth` — вместе они образуют
«трубу» откосов сквозь стену. Торцевых крышек нет — торцы закрывают сами грани
стены (дырка в грани совпадает с контуром лутки).

**3. UV-лента (54675–54678).** `u ∈ {0, depth/pixPerMeter}` — поперёк стены;
`v` — накопленная длина периметра: `coordV/pixPerMeter → (coordV+dV)/pixPerMeter`,
`coordV += dV` в конце итерации (54712). `pixPerMeter = 100` — это перевод
сантиметров сцены в метры текстуры (1 текстурный юнит = 1 м). Лента непрерывна
вдоль всего контура — текстура откоса «течёт» вокруг проёма без швов, кроме
стартового угла из шага 1.

**4. Split top/bottom (54681–54710).** Сегмент уходит в **bottom**-геометрию,
если **обе** его точки лежат в пределах 2 см от самого низа проёма:
`P1.y > maxY − bottomHeight && P2.y > maxY − bottomHeight` (54681). Для окна это
горизонталь подоконника, для двери — порог; всё остальное (косяки + перемычка)
— **top**. Параллельно копятся `cont3d*1/2` (полилинии обеих кромок рамы, для
обводки) и площадь `d1·d2` (длина сегмента × толщина, 54694/54707) — площадь
откосов для сметы.

**5. Упаковка (54716–54753).** Две `WC.DataFrame` (51889): bottom с
`materialBottom/addMaterialBottom/materialBottomRotation/X/Y` (54716–54717),
top с `materialFrame*` (54725–54726); тип — `'topFrame'`/`'bottomFrame'` по
булеву первому аргументу (51902–51908). Каждой — vertices/uvs/`uvsDef`
(копия для сброса смещений материала)/indices/contours/area, затем `build3D`.
`frameB.dirX/dirY` — орты вдоль/поперёк оси (54741–54752) для драга материала
по подоконнику. Возврат `[frameT, frameB]` (54753).

## 5. Судьба дырок при редактировании стен

Дырка нигде не хранится — она каждый раз выводится из `axis.models` при
`build3D` грани. Поэтому «инвалидация дырок» = «выживет ли модель на оси».

**Live-операции** (дроп/удаление проёма): `dropElement` (55172) и `pickElement`
(55241) синхронно пересобирают рамы оси + обе грани + плинтусы обеих граней
(55219–55238 / 55255–55270). Квирк: в `dropElement` строка
`axis.wall1.changed = true` продублирована (55223–55224), а `wall2.changed` не
выставляется (в `pickElement` — корректно, 55259–55260); компенсируется тем,
что `createWall3D`/`dispatchUpdate` для wall2 всё равно зовутся.

**Редактирование стен (длина/толщина/снос) — путь пере-дропа.** Правка стен
идёт в отдельном 2D-редакторе (`WC.SubEditor`); на выходе:

1. `SubEditor.getStructure` (61611) собирает новую структуру; выжившие стены —
   в `savedWalls` (61629/61682). Затем цикл по **старым** осям (61975–62001):
   - ось выбрасывается, если хотя бы одна из её граней не выжила
     (`savedWalls.indexOf(...) == -1`, 61978) или на ней нет моделей (61979);
   - пара граней заново прогоняется через `boxFromWalls` + `boxCenterSeg`
     (61981–61984) → новые `axis.point1/point2` (и новая толщина бокса);
   - **позиция модели сохраняется по абсолютному `axisPos`** (расстояние от
     `axis.point1`, зафиксировано при дропе, 55209), не по нормализованному
     `pos`: новые мировые координаты `x = point1.x + axisPos·cos(ang)`
     (61997–61998). Удлинение стены не растягивает расстановку проёмов —
     они остаются на месте относительно начала оси;
   - **краевой отсев**: `if (model.axisPos > newAxisLength − 5) continue`
     (61995) — модель, оказавшаяся ближе 5 см к дальнему концу укороченной оси
     (или вовсе за ним), в `newModelsData` не попадает.
2. При выходе из редактора (`disable`, 62345–62348): `wallsData.setStructure(...)`
   пересобирает весь конструктор (оси создаются заново, пустыми), затем
   `dispatchModelsReset()` (62348 → 55797–55800) шлёт `RESET_MODELS` с
   `newModelsData`.
3. Обработчик на стороне сцены (13254–13258 → `updatePositionObjectsForWall`,
   ~13189): для каждой записи находит sceneObject по id (13211), подменяет его
   `x/y` пересчитанными (13215–13216) и прогоняет через **обычный**
   `constructor.dropElement(dataForWall, radiusDropElement = 10)` (13218,
   константа 13092). Неудачный дроп → `scope.remove(sceneObject)` (13227) —
   **проём физически удаляется из сцены**. Объекты-на-стене, не попавшие в
   `newModelsData` (модель отсеяна на шаге 1 или ось умерла), добираются вторым
   циклом (13242–13251): пере-дроп по их **старым** координатам; если рядом
   (в пределах 10 см) больше нет оси — тоже `remove`.

Итого судьба проёма при правке стены решается двумя порогами: 5 см до дальнего
конца новой оси (61995) и 10 см снап-радиуса пере-дропа (13092). Изменение
**толщины** стены проходит бесплатно: `axis.depth` пересчитывается из нового
бокса (`findAxes`, 55383), при пере-дропе модель получает новый `depth`
(55197), а сцене возвращается `setDepth(depth + 1)` (14796) — 3D-модель
двери растягивается на толщину стены +1 см напуска.

Отдельный live-путь: правка параметров самого объекта (scale/flip/elevation) —
`sceneObjectHistoryUpdate` (13259–13270): `pickElement` + повторный
`dropElement` того же объекта, т.е. тот же цикл «снять-надеть».

## Пороги и константы

| Значение | Символ / строка                         | Роль                                                                    |
| -------- | --------------------------------------- | ----------------------------------------------------------------------- |
| `2`      | `bottomHeight` (54608)                  | сегменты в пределах 2 см от низа проёма → `bottomFrame` (подоконник/порог) |
| `100`    | `pixPerMeter` (54609)                   | см → м для UV лутки (1 текстурный юнит = 1 м)                            |
| `0.01`   | округление (55698–55699)                | стабилизация координат контуров лутки перед слиянием                     |
| `5`      | краевой отступ (61995)                  | модель ближе 5 см к дальнему концу пересчитанной оси — не пере-дропается  |
| `10`     | `radiusDropElement` (13092), snapDist (55174) | снап-радиус (пере)дропа к оси; провал → удаление проёма             |
| `+1`     | `setDepth(depth + 1)` (14796)           | напуск 3D-модели проёма по толщине стены                                 |
| `≠ OUTSIDE` | порог слияния (54962)                | любые пересечение/вложение/касание силуэтов → одна лутка                 |

## Что переиспользуем vs реплицируем

- **Дырки без CSG — переносить как есть.** Схема «2D inner-контур в
  триангулятор per-грань» тривиально ложится на earcut/cdt2d в TS и на порядок
  дешевле булевых операций над мешами. Формулы проекции (§1) — 6 строк на
  грань, с готовым тестом «ближняя/дальняя грань» через сравнение расстояний.
- **Лутку строить своей экструзией (§4)** — UV-лента с накоплением периметра и
  сплит по `maxY − 2` дают правильный визуал подоконника из коробки; стартовый
  угол для шва стоит выбрать явно (правый-нижний), а не наследовать их
  полусломанный `iCorner`.
- **Слияние перекрытий** у нас можно сделать честным полигон-булем (Clipper2
  union) вместо «триангулируй-и-обведи» — но тогда воспроизвести их политику:
  группировать и по касанию (`CONTACT`), материалы объединённой лутки — от
  первой модели группы, внутренние дыры юниона — отбрасывать.
- **Пере-дроп вместо инвалидации** — главный дизайн-урок: не хранить дырку как
  геометрию и не «чинить» её при правке стены, а хранить `axisPos` + прогонять
  модель через тот же dropElement-гейт; провал гейта = честное удаление проёма.
  Оба порога (5 см от конца, 10 см снапа) переносить как явные константы.
- **Не копировать**: in-place `reverse()` в `findContourWall` (скрытый
  side-effect), дубль `wall1.changed` (55223–55224), `remade[0][0]` без
  проверки числа контуров.

## Confidence & gaps

**Высокая уверенность** (прочитано построчно по исходнику): формулы обеих веток
`getHoles` и смысл `parallel`/`axisShift`; подача дырок inner-контурами в
`triangulateContours` (53147, 53185) и отсутствие CSG; полный алгоритм
`compareAndRebuildContours` (группировка «≠ OUTSIDE», юнион через
`rebuildContours`, `remade[0][0]`, `filter=false`); y-down фрейм контуров лутки
и округление до 0.01; вся геометрия/UV/сплит `createFrame3D`; материалы
объединённой лутки от первой модели группы; цепочка пере-дропа
`getStructure → newModelsData (отсев >len−5) → RESET_MODELS →
updatePositionObjectsForWall → dropElement(10) → remove при провале`.

**Пробелы / ниже уверенность:**

1. Ориентация каталожного контура (`contourCut`) до `scalePoints(-1,1)` —
   вывод «y-down, x зеркалится при дропе» сделан из согласованности формул
   getHoles/createFramesForAxis/createFrame3D, сами каталожные данные (JSON
   моделей) в файле отсутствуют.
2. `iCorner` в `createFrame3D` (54617–54628): условие с `y > maxY` после
   апдейта `maxY` мёртвое — описал фактическое поведение («последняя точка,
   увеличившая maxX»), задумку автора («правый-нижний угол»?) утверждать не
   берусь.
3. Не прослежено до конца, как ведёт себя дырка, чей силуэт вылезает за
   прямоугольник грани (проём у самого угла): по коду её клипует
   `resplitSegments`+flood-fill, но граничные артефакты (совпадение ребра дырки
   с ребром грани) не проверял.
4. `flipY` модели нигде в этом пайплайне не читается (только `flipX`,
   53008/55693) — вертикальный флип, судя по всему, применяется на уровне
   3D-модели, не силуэта; не подтверждал.
5. Путь `sceneObjectHistoryUpdate` (13259) прочитан локально; полный
   undo/redo-цикл проёмов (история сцены) не трассировал.
