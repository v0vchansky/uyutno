# Deep-dive 05 — Cover / Ceiling / Area build3D: генерация 3D-мешей покрытий

Реверс-анализ неминифицированного `plannercore.js` конкурента. Все номера строк —
по этому файлу. UV-формулы `findTriWall` / `findTriCover` / `findTriWallTile`
разобраны в [dd04](04-3d-mesh-uv.md) и здесь не пересказываются; 2D-пайплайн
вывода покрытий (rebuildCovers → findAutoCovers → findCoverHoles →
findAllCoverTriangles) описан в [03-rooms-floors-structure.md](../03-rooms-floors-structure.md) §3 —
здесь только то, что происходит **после** него: путь от готовых 2D-контуров до
`BufferGeometry` в сцене Three.js.

---

## Общая картина: две модели и один полный пересбор

Покрытия существуют в **двух параллельных моделях**:

1. **2D-ядро** (`WC.core`): `WC.CCover` (56965), `WC.CArea` (57027) — наследники
   `WC.CContour` (56890). Хранят `points/holes/triangles` + персистентный `data`
   (материалы, ceiling-блок). Их треугольники считает 2D-пайплайн
   (`findCoverTriangles`, 60458, триангуляция `TR.triangulateContours([cover.points],
holeContours, [], [], [])` @60466 — только outer-контур + дырки, без bound/subtract).
2. **3D-модель** (`WC.WallsData`, 55010): `WC.DataCover` (51725), `WC.DataCeiling`
   (51789), `WC.DataArea` (51617), `WC.DataCap` (51838) — наследники `WC.DataObject`
   (51212). Именно их `build3D()` заполняет `parts[0].vertices/uvs/indices/area`,
   из которых рендер строит `THREE.BufferGeometry`.

Мост между ними — `SubEditor.getStructure()` (61616): на каждом коммите 2D-редактора
он **с нуля** создаёт свежие `DataCover`/`DataCeiling`/`DataArea` из `WC.core.arrCovers`
/ `arrAreas` (ковры: 61757–61810; зоны: 61812–61936), копируя точки, материалы,
`mx/my/mr` и ceiling-блок. Результат уходит в `WallsData.setStructure(struct)`
(55088–55106): `removeAll()` (полный teardown, 55107) → копирование полей → `findAxes()`
→ `createPlinths()` → `build3D()` (внутренний, 55475) → `findRoomsForCovers()` (55324 —
каждому cover присваивается room, в чей контур попадает его `points[0]`).
Вызовы `setStructure`: выход из 2D-редактора (`me.disable`, 62344), явный
`setStructureToWallsData` (62325–62328), включение 3D (15578, 39926, 62767).

**Вывод: инкрементальности для геометрии покрытий нет вообще** — любой
геометрический эдит порождает новые Data-объекты и полный ребилд всех мешей.

## Диспатч: внутренний `build3D()` WallsData (55475)

Порядок сборки (важен — cover перед ceiling, cap после зон):

1. Стены (`createWall3D`), cuts, плинтусы (55477–55498).
2. `me.ceilings = []` (55500); цикл по `me.covers` (55502–55509): для каждой пары
   «пол + его потолок» — `WC.createCover3D(me.covers[i], me.innerCoverConts)` (55505),
   затем два `ELEMENT_CREATE` (cover 55506, cover.ceiling 55507) и
   `checkCeilingVisible(ceiling, true)` (55508).
3. Cap и зоны: сброс `areas[i].triangles = []` (55516), сбор `cutPairs` из всех
   `DataCut` (55519–55520), **общая триангуляция всего плана**
   `TR.triangulateContours(me.outerRoomConts, me.innerRoomConts, [], [], cutPairs)`
   (55522). `trs[0]` — плоский список fill-треугольников (возврат `[fillTrs, holeTrs]`,
   см. dd01).
4. Раздача треугольников (55527–55553): для **каждого** треугольника считается
   `TR.triangleCenter` (55537) и проверяется `TR.pointInContour(center, areas[j].points)`
   (55543): попал — треугольник уходит в `areas[j].triangles` **и** в
   `areas[j].ceiling.triangles`, иначе — в `me.cap.triangles`. Заметное отличие от
   2D-ядра: там `findAreasTriangles` (60072–60100, тест первого треугольника 60081, забор группы 60087) тестирует центр только **первого**
   треугольника fill-группы и забирает группу целиком — в 3D гранулярность
   по-треугольная, потому что cut-рёбра зоны уже входят в `cutPairs` и режут план.
5. `areas[i].build3D(); areas[i].ceiling.build3D()` (55564–55565) + line-контуры через
   `findContourCover` (55567–55568); `me.cap.build3D()` (55571) + `ELEMENT_CREATE`
   (cap только если есть вершины, 55573; зоны — 55575–55587, ceiling зоны только при
   `exists`).
6. Дальше — соседства стен, `createConnectors` → plugs (55611–55658, см. dd02).

## `WC.createCover3D(cover, innerContours)` (54529) — пол + потолок комнаты

Вход: свежий `DataCover` и `me.innerCoverConts` — список контуров **внутренних**
(не-outer) ковров, собранный в `getStructure` (61779–61785: не-outer CCover →
`res.coverHoles` + его `points` в `res.innerCoverConts`).

1. **Отбор дырок** (54533–54540): из всех innerContours берутся те, для которых
   `TR.compareContours(cover.points, innerContours[i]) == TR.CONTAIN`. Т.е. дырка
   пола (вырез под лестницу, комната-в-комнате) на 3D-уровне — это просто
   внутренний ковёр, чей контур целиком лежит внутри данного.
2. **Триангуляция** (outer-ветка, 54544–54548):
   `trs = TR.triangulateContours([cover.points], holes, [], [], [])` (54546) — контур
   пола как outer, дырки как inner, без bound/subtract и без cutPairs. Плюс
   line-контуры для рёбер: `cover.contours = [WC.findContourCover(cover.points, 0, false)]`
   (54547) и `ceiling.contours = [WC.findContourCover(cover.points, ceiling.height, true)]`
   (54548). Для не-outer ковра (ветка else, 54550–54555) — триангуляция без дырок и
   пустые contours; такой объект в `me.covers` не попадает и мешом не становится
   (дырка «рендерится» отсутствием геометрии родителя).
3. **Копирование треугольников** (54557–54571): из глобального пула `TR.points`
   по `pointIndices` строятся `TR.Point`-тройки; **один и тот же массив троек**
   кладётся и в `cover.triangles[i]`, и в `ceiling.triangles[i]` — пол и потолок
   всегда имеют идентичную 2D-триангуляцию.
4. `cover.build3D(); ceiling.build3D(); cover.addNullData(); ceiling.addNullData()`
   (54573–54576). `addNullData` (51397) — если вершин нет, подставляется вырожденный
   треугольник `[-1,-1,-1]×3`, чтобы пустой элемент имел валидные буферы.

**Квирк — реверс точек in place.** `WC.findContourCover(cont2d, elevation, reverse)`
(54779) при `reverse=true` делает `cont2d.reverse()` (54783) — **мутирует сам массив**
`cover.points`. Т.е. после строки 54548 порядок точек ковра инвертирован (то же для
зон на 55568). Ни на треугольники (уже скопированы), ни на `findRoomsForCovers`
(смотрит только `points[0]`) это не влияет, но повторный вызов снова перевернёт
массив — типичная «работает, потому что вызывается один раз» деталь.

## `DataCover.build3D()` (51742) — пол

Псевдокод (51742–51785):

```
parts[0].{materialID, addMaterialID, materialRotation, materialX, materialY} ← поля me
parts[0].vertices = []; uvs = []; area = 0
for (tri of parts[0].triangles):                        // 51755
    area += TR.triangleArea(a,b,c)                      // 51761
    tr = WC.findTriCover(a, b, c, /*elevation*/ 0, /*reverse*/ false,
                         mx, my, mr, rotatingCenter.x, rotatingCenter.y)   // 51763
    vertices ⧺ tr[0]; uvs ⧺ tr[1]
parts[0].indices = WC.generateIndices(vertices.length / 3)                 // 51768
rotatingCenter = центр bbox по me.points                // 51770–51781
if (ceiling) ceiling.rotatingCenter = rotatingCenter    // 51782
me.area = parts[0].area                                 // 51784
```

Ключевые факты:

- **Вершины**: плоскость `y = 0`, маппинг плана `(x, y) → (x, 0, -y)` — внутри
  `findTriCover` (52659–52676). Никакой высоты пола/толщины — пол это один
  односторонний лист.
- **Индексы тривиальны**: `WC.generateIndices(n)` (52311) — просто `[0,1,2,…,n-1]`,
  вершины не шарятся между треугольниками (каждый треугольник — свои 3 вершины,
  «triangle soup» с индексом-заглушкой).
- **Направление обхода** задаётся не триангулятором, а самим `findTriCover`: три
  точки каждого треугольника сортируются **по азимуту вокруг центроида**
  (`_currPoints.sort(sortByAngle)`, 52584) — канонический CCW в координатах плана;
  `reverse=true` делает `.reverse()` (52585) → CW. Поэтому у пола все треугольники
  гарантированно однонаправлены независимо от порядка, который выдал cdt. Никакого
  `faceRight` у покрытий нет — это чисто стеновое понятие.
- **Нормалей в данных нет вообще**: `findTriCover` возвращает только
  `[vertices, uvs]`. Нормали появляются на стороне рендера (см. ниже).
- **UV**: формула — dd04 («Cover/ceiling UV», 52593–52657): `u = x, v = y` плана,
  rotate-about-center на `-mr` с вычетом `mx/my`, деление на `pixPerMeter = 100`
  (52574, т.е. 1 UV-юнит = 1 м). Cover-специфика — про `rotatingCenter` см. раздел
  «Материальные трансформы».

## `DataCeiling.build3D()` (51806) — потолок

Отличия от пола (51806–51834), всё остальное идентично:

|                | Пол (51763)                       | Потолок (51826)                                                                                                                                      |
| -------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| elevation      | `0`                               | `me.height` (дефолт `WC.DEFAULT_WALLS_HEIGHT = 280`, 59320; фактическое значение копируется из `ccover.data.ceiling.height` в `getStructure`, 61803) |
| reverse        | `false` → CCW, нормаль +Y (вверх) | `true` → обход инвертирован (52585), нормаль −Y (вниз)                                                                                               |
| U-координата   | `u = x`                           | `u = -x` (52606) — зеркалирование, чтобы текстура снизу не читалась в зеркале; знак `kr = -1` (52616–52617) зеркалит и `mx`-сдвиг с центром вращения |
| rotatingCenter | считает сам по bbox               | **не считает** — получает копию от пола (51782) / зоны (51677)                                                                                       |
| Дырки          | из `innerCoverConts`              | те же — треугольники общие с полом (54563–54570)                                                                                                     |

Потолок не имеет собственного контура-полигона: он «висит» на cover (поле
`cover.ceiling`, создаётся в `getStructure` @61764–61766) или на зоне. Видимость
рулится камерой: `checkCeilingVisible` (55763–55778) скрывает потолок, когда
`cameraFrom.z >= cap.wallsHeight` (вид сверху), и показывает внутри, с уважением к
`isHiddenByInstrument`.

## `DataArea.build3D()` (51635) — зоны и `DataCap` (51855) — верх стен

Зона (area) — участок плана с пониженной высотой (`CArea.height = 100` @57033,
`WC.DEFAULT_AREA_HEIGHT = 100` @59321). Её меш — **горизонтальная крышка на высоте
`me.height`**, а не пол:

- Треугольники зона получает не от собственной триангуляции, а из общей
  триангуляции плана с `cutPairs` (55522) — по-треугольным тестом центра (55537–55550,
  см. диспатч выше). Границы зоны при этом обязаны быть fixed-рёбрами: её отрезки
  попали в `cutPairs` через `DataCut`-ы, созданные в `getStructure` из
  `cArea.getCutWallPairs()` (61824–61906) — поэтому ни один треугольник не пересекает
  границу зоны, и «резка по границе» выходит бесплатно.
- `findTriCover(a, b, c, me.height, false, mx, my, mr)` (51657) — **без**
  `centerX/centerY` (в отличие от cover/ceiling), т.е. центр вращения материала
  всегда `(0,0)` (дефолты 52570–52571). При этом `me.rotatingCenter` зона всё-таки
  считает (51665–51676) — но использует его только чтобы отдать своему потолку
  (51677); сам построитель его игнорирует. `DataCap.build3D` (51855–51885) устроен
  так же: `findTriCover(..., me.wallsHeight, false, mx, my, mr)` без центра (51878).
- Побочный эффект зон на стены: в `getStructure` стены, совпадающие с рёбрами зоны
  или лежащие внутри неё, получают `height = DA.height` и теряют верхний плинтус
  (61833–61864) — «низкие стены» зоны.
- Потолок зоны — обычный `DataCeiling` с треугольниками зоны (55548) и высотой
  `cArea.data.ceiling.height` (61925), строится на 55565.
- `DataCap` — крышка **тел стен** на высоте `wallsHeight`: треугольники = весь план
  между outer- и inner-контурами комнат минус зоны (остаток из шага раздачи, 55553).
  Это то, что видно сверху в dollhouse-виде.

**Z-fight-сдвигов нет.** Никаких эпсилон-смещений по высоте в этом пути не найдено:
cap лежит ровно на `wallsHeight = 280`, потолки комнат по умолчанию на той же
высоте, нормали у них противоположные (cap — вверх, ceiling — вниз). Разводятся они
не смещением, а видимостью/односторонностью: сверху потолки принудительно скрыты
(`checkCeilingVisible`), изнутри cap не виден. В 2D-topview зоны и cap вообще
рисуются на фиксированной высоте `y = 690 - bbox.min.y` (47385, 47396).

## Рендер: от `parts[0]` до `BufferGeometry`

Консьюмер `ELEMENT_CREATE` — `R2D.ConstructorSceneHelper` (подписка 40980), который
заводит `R2D.ObjectConstructor3D` (31040) на каждый Data-объект:

1. `updateGeometry` (31119–31141): для каждого `parts[i]` —
   `R2D.Tool.flipGeometryByZ(part)` (29079): `z → -z` у вершин (и нормалей, если бы
   они были) **плюс** свап индексов `[i, i+2, i+1]` (29108–29117), чтобы после
   зеркала сохранить ориентацию. Итог: план-Y, который `findTriCover` записал как
   `-y`, в сцене снова становится `+z`; пол остаётся нормалью вверх, потолок — вниз.
2. `R2D.Tool.makeBufferGeometry(indices, vertices, uvs)` (28984): атрибуты
   `position`/`uv` из Float32Array; параметр `normal` не передаётся → ветка
   `geometry.computeVertexNormals()` (28999) — **нормали покрытий всегда считает
   Three.js по winding'у**, в данных их нет.
3. `updateMaterial` (31093–31118): материал берётся по `parts[i].materialID` через
   `R2D.PoolMaterials`; пустой/нулевой ID подменяется дефолтом по типу —
   `__checkMaterialId` (31288–31308): cover → "cover", cap/area → "cap"/"wall",
   и т.д. (ср. дефолты классов: `DataCover` → "cover" @51730, `DataCeiling` и
   `DataArea` → "wall" @51794 / 51623, `CCover.data.ceiling` → "ceiling" @56994,
   `CArea.data` → "cap" @57040).
4. Материальные правки без смены геометрии идут через `ELEMENT_UPDATE`
   (`dispatchUpdate`, 51345) → `elementUpdateEventHandler` (31142–31151) →
   `updateGeometry + updateMaterial` заново.

## Материальные трансформы: `rotatingCenter`, `mx/my`, `mr`

Формула применения — в dd04; здесь cover-специфика:

- Активная версия трансформа (52631–52641):
  `u' = rotate(u − kr·(mx + cx), v − my − cy, −mr) + kr·cx (+cy)` — вращение вокруг
  точки, зависящей и от сдвига, и от центра, с возвратом центра. Старая версия без
  `centerX/centerY` закомментирована рядом (52619–52629) — центр вращения дописали
  позже.
- `rotatingCenter` пола = **центр bbox его точек**, пересчитывается в конце build3D
  (51770–51781) и зеркалится потолку (51782). Потолок и потолок зоны поэтому всегда
  вращают текстуру вокруг центра родителя.
- **Квирк порядка вычислений**: build3D сначала использует `me.rotatingCenter` в
  цикле (51763), и только потом его пересчитывает. У свежесозданного `DataCover`
  центр = `(0,0)` (инициализация в DataObject, 51224), а `getStructure` его не
  копирует — значит **первый** билд после любого пересбора структуры применяет
  сохранённый `mr` вокруг начала координат, а не вокруг bbox-центра. Стабильным
  bbox-центр становится только со второго вызова build3D того же объекта
  (интерактивные `rotateMaterial`/`moveMaterial`, 51355–51394, каждый раз зовут
  `build3D()` повторно). Для бесшовных текстур смена пивота — лишь сдвиг паттерна,
  поэтому визуально это малозаметно, но детерминизм UV между сессиями не строгий.
- Зоны и cap центра не передают вовсе (51657, 51878) — их `mr` всегда вокруг (0,0).
- Коммит трансформа: `stopRotateMaterial`/`stopMoveMaterial` только ставят
  `changed = true` (51366–51394); в 2D-`CCover.data` значения возвращает история
  сцены / панель материалов, при следующем `getStructure` они приедут обратно.

## Дырки и комнаты-в-комнате: полный маршрут

1. **2D**: внутренние ковры возникают из hole-контуров `rebuildContours`
   (`findAutoCovers` @59714, `new WC.CCover(false)` для дырок — см. 03 §3).
   `findCoverHoles` (60406–60447) привязывает их к outer-коврам: outer-ковры
   сортируются `sortByArea` (59492–59521: по **убыванию** |area| с tie-break eps=10
   в пользу inner) и `.reverse()` (60425) → итерация **от меньших к большим**;
   каждый outer забирает через `TR.compareContoursOnePoint == CONTAIN` (60436) ещё
   не занятые внутренние ковры. Благодаря порядку «меньшие первыми» дырка внутри
   комнаты-в-комнате достаётся внутреннему ковру, а не внешнему. Осиротевшие
   внутренние ковры удаляются (60444–60446).
2. **2D-треугольники**: `findAllCoverTriangles` (60450) → на каждый ковёр
   `triangulateContours([points], holes.points, …)` (60466).
3. **3D**: `getStructure` кладёт контуры всех не-outer ковров в `innerCoverConts`
   (61779–61785); `createCover3D` заново отбирает дырки для каждого пола по
   `CONTAIN` (54536) — привязка из `findCoverHoles` на 3D-уровне не переиспользуется,
   а честно пересчитывается. Комната-в-комнате даёт и дырку в полу внешней комнаты
   (через её inner-ковёр), и собственный пол — обе геометрии строятся независимо.

## Инкрементальность и changed-флаг

- **Геометрия**: только полный пересбор. `rebuildWallsAndCovers` (59533) в 2D-ядре +
  `setStructure` (55088) в 3D — всё пересоздаётся, никакого diff'а по коврам.
- **`changed`** у Data-объектов ставится сеттерами материалов
  (`setMaterial`/`setAddMaterial`/`clearMaterial`/`stop*Material`, 51285–51394), но
  читается историей сцены только для стен и frames (`wasChanged`, 12923 / 12990);
  для covers/ceilings/areas история хранит просто снапшот материала (12929–12955).
  `setAllElementsChanged` (55055) тоже трогает только walls+frames. Т.е. для
  покрытий флаг — мёртвый груз.
- **Материальный fast-path без ретриангуляции существует**: применение стиля комнаты
  (56174–56185) делает `copyCoverData` → `cover.build3D()` + `dispatchUpdate()` —
  build3D переиспользует кэшированные `parts[0].triangles` и пересчитывает только
  vertices/uvs. Так же работают интерактивные rotate/move материала.

## Что берём себе / что не копируем

- **Хорошая идея**: одна 2D-триангуляция на пару пол+потолок (54563–54570) и
  канонизация winding'а сортировкой по азимуту вместо доверия триангулятору —
  дёшево и устойчиво. В нашем редакторе тот же эффект даст явная нормализация
  ориентации контура + shared IndexBuffer (их `generateIndices` — заглушка, вершины
  дублируются; нам стоит шарить вершины по-настоящему).
- **Повторять не стоит**: пересчёт `rotatingCenter` после его использования
  (нестабильный пивот UV между сессиями), мутация `points.reverse()` внутри
  `findContourCover`, «нормали через computeVertexNormals» вместо явной константной
  нормали для плоского листа, и двойная (2D и 3D) независимая триангуляция одного
  и того же ковра — у нас источником должна быть одна.
- **Порт policy-логики**: по-треугольная раздача план-триангуляции между зонами и
  cap с фиксацией границ зоны как constraint-рёбер — простой и надёжный паттерн,
  берём как есть; разводка coplanar cap/ceiling видимостью, а не эпсилоном — тоже
  рабочий выбор для односторонних материалов.

## Confidence & gaps

**Высокая уверенность** (прочитано построчно): полный маршрут
`getStructure → setStructure → build3D → createCover3D → Data*.build3D →
ObjectConstructor3D → makeBufferGeometry`; сигнатура и все ветки `findTriCover`
(52564–52681, включая azimuth-сорт, `reverse`, `kr`, активный и закомментированный
варианты center-трансформа); отсутствие нормалей в данных и `computeVertexNormals`
на рендере (28999); flip-by-Z со свапом индексов (29079–29118); отбор дырок по
`CONTAIN` в createCover3D (54536); общий массив треугольников пола и потолка;
раздача cap/area по центрам треугольников (55527–55553) против first-triangle-of-group
в 2D (60072–60100, first-tri 60081, group-concat 60087); отсутствие z-эпсилонов; квирки `rotatingCenter`-после-цикла и
`cont2d.reverse()` in place; мёртвый `changed` для покрытий.

**Пробелы / ниже уверенность:**

1. **Сторона материалов** — `R2D.ObjectConstructor3D.__defaultMaterial` (31265–31273)
   форсит `material.side = THREE.DoubleSide` (31270), т.е. и cap, и ceiling по
   умолчанию двусторонние. Это ослабляет «разводку нормалью+видимостью»: сама по
   себе нормаль их не разводит, единственный реальный барьер — `checkCeilingVisible`
   (сверху потолки скрыты). Пул материалов из библиотеки не изучал, но дефолтная
   ветка гарантированно даёт DoubleSide.
2. `TR.compareContours` / `compareContoursOnePoint` внутренности не перечитывал
   (полагаюсь на 03/dd03); для этого дока важен только контракт CONTAIN.
3. В load-пути `shortToStructure` `res.ceilings.push(dCeil)` (54055) пушит
   `dCeil`, созданный в **этом же** цикле по коврам на 53806 и присвоенный
   `DC.ceiling` на 53821 — никакого cross-loop-hoisting нет (второй `var dCeil`
   объявлен в цикле зон @53987, но полностью локален по значению для того цикла).
   Верифицировано: 53806, 53821, 54055 — все внутри covers-loop; 53987 — внутри
   zones-loop. Прошлое утверждение о «баге» — снято.
4. Утверждение про «первый билд с центром (0,0)» подтверждено статически:
   `DataObject.rotatingCenter = new TR.Point(0, 0)` (51224), `getStructure`
   не копирует это поле (61757–61810 — ни одна строка не трогает
   `dataCover.rotatingCenter`), а `build3D` использует `me.rotatingCenter` в цикле
   на 51763 до пересчёта на 51770–51781. Runtime не проверял, но по коду цепочка
   однозначная.
5. `checkCeilingVisible` сравнивает `cameraFrom.z` с высотой — подтверждено, что
   `z` это высота, а не 3D-ось Y сцены. `me.setCameraPosition` принимает `camFrom`
   с сигнатурой `{x, y, h}` (55734), и вызывающие места (47292, 48001) конструируют
   вектор как `new GEOM.Vector(cPos.x, cPos.z, cPos.y)` — т.е. поле `.z` в
   план-координатах есть высота. `cameraFrom.z >= wallsHeight` = «камера над
   потолком» — консистентно с логикой скрытия потолков в top-view.
