# Deep-dive 12 — Вес сохранённого плана: замер по живому документу

Не разбор исходника, а **замер**. [10-serialization-save-format.md](../10-serialization-save-format.md)
описывает **структуру** формата сохранения roomtodo (по коду `structureToShort` /
`makeSceneObjectData` / `SceneParser`); здесь — **вес** этой структуры на одном реальном
документе, снятом с публичного эндпоинта расшаренного плана.

Файл нужен **шагу 3** (где и как хранить документ планера): до этого замера цифр веса плана
не было ни у нас, ни в реверсе, и порядок величины приходилось угадывать.

Все числа ниже **пересчитаны по сырому ответу** заново, скриптом, а не переписаны из чужой
сводки. Метод счёта описан в §1 явно, потому что от него зависят проценты. Непроверенное и
неизмеримое по этому плану собрано в §9 и помечено.

> **В файле только агрегаты.** Идентификаторы плана и владельца, хеши, имена, пути превью,
> координаты и содержимое чужого документа сюда не переносятся и в репозитории не хранятся.

---

## 1. Что мерили и чем

**Объект замера** — тело ответа на чтение одного расшаренного плана: конверт
`{status, plan, viewOnly, userPlan}`, где `plan` — ровно тот конверт проекта, который описан в
[10-serialization-save-format.md](../10-serialization-save-format.md) §«Top-level plan envelope».

**Два разных размера, которые нельзя путать:**

| Размер                              | Байт        | Что это                                                                                    |
| ----------------------------------- | ----------- | ------------------------------------------------------------------------------------------ |
| Сырое тело ответа, как отдал сервер | **358 902** | pretty-printed JSON с отступами — **артефакт транспорта**, а не размер данных              |
| Тот же JSON, минифицированный       | **120 676** | весь конверт ответа                                                                        |
| Из него `plan` — сам документ       | **120 613** | **117.8 КБ** — вот это и есть сопоставимая с БД цифра (JSON/JSONB-колонка, файл в S3, LWW) |

Раздувание **×2.974** (358 902 / 120 676) — это отступы pretty-print. Мерить хранилище по
сырому ответу — ошибка порядка в три раза.

**Два способа счёта секции, оба используются ниже и всегда подписаны:**

- **«Вес значения»** — `Buffer.byteLength(JSON.stringify(value))`, без имени ключа. Так посчитана
  таблица §2: суммы вложенных секций сходятся с родителем с точностью до имён ключей и запятых.
- **«Дельта удаления»** — на сколько похудеет минифицированный документ, если поле выкинуть
  (значение **плюс** имя ключа плюс разделители). Так посчитан §7: там вопрос «сколько стоит
  избыточность», и имя ключа — часть цены.

Разница между способами не косметическая: `materials[]` весит 42 322 Б как значения и 43 843 Б
как дельта удаления — 1 521 Б это 117 раз повторённое имя ключа `"materials":` с запятой.

**Сжатие** считалось Node 22 `zlib` по минифицированному `plan`:

| Кодек                                | Байт       | КБ       | Коэффициент к 120 613 |
| ------------------------------------ | ---------- | -------- | --------------------- |
| без сжатия                           | 120 613    | 117.8    | 1.00                  |
| gzip, уровень 9                      | **14 791** | **14.4** | **8.15**              |
| brotli, качество 11 (дефолт `zlib`)  | **11 656** | **11.4** | **10.35**             |
| brotli, качество 5 (типовой рантайм) | 13 649     | 13.3     | 8.84                  |

_Оговорка по инструменту:_ системный BSD `gzip -9` на том же файле даёт 15 135 Б — на 2.3%
больше, чем `zlib` из Node. Расхождение реализаций deflate, не ошибка замера; порядок величины
один. В доке везде используются числа `zlib`.

Вывод по сжатию: **документ этого формата жмётся в 8–10 раз.** JSON из коротких повторяющихся
ключей — идеальный корм для словарных кодеков, и это меняет расчёт хранения: 117.8 КБ на диске
и ~12–15 КБ по проводу — разные бюджеты.

## 3. Масштаб замеренного плана

Чтобы цифры §1–2 можно было к чему-то приложить:

| Что                      | Сколько                                                                     |
| ------------------------ | --------------------------------------------------------------------------- |
| Точек (`points[]`)       | **105** — из них `type: "rp"` 55, `type: "cp"` 50                           |
| Стен (`walls[]`)         | **55**                                                                      |
| Комнат (`rooms[]`)       | **5** — из них одна с `outer: 1` (внешний контур оболочки)                  |
| Полов (`covers[]`)       | **5** (контуры по 4, 6, 4, 30, 6 точек)                                     |
| Зон (`areas[]`)          | **2**                                                                       |
| Вырезов (`cuts[]`)       | **3**                                                                       |
| Предметов (`products[]`) | **125** — `type: 2` (MODEL) 117, `type: 3` (POSTER) 5, `type: 4` (CARPET) 3 |
| Групп (`groups[]`)       | **0** — массив пустой                                                       |
| Скрытых элементов        | **0** — все 11 массивов `hiddenElements` пустые                             |

Расшифровка `type` — по [10-serialization-save-format.md](../10-serialization-save-format.md)
§`products[]`: `MATERIAL=1, MODEL=2, POSTER=3, CARPET=4, PLINTH=5`.

**Это полноценная жилая квартира, а не студия и не тестовая коробка.** 55 стен на 105 точках,
пять контуров комнат (четыре внутренних плюс оболочка), пять отдельных полов с потолками, две
зоны с собственной высотой стен и 125 расставленных предметов — это меблированный многокомнатный
план, доведённый до состояния «показать». Цифры §1 не занижены масштабом.

Отдельно: контуры комнат — 7, 34, 6, 4 и 4 точки. Комната на 34 точки — сложный
многоугольник с нишами, а не прямоугольник; формат такое держит без специальной цены (комната
хранит только id-ссылки, 102.6 Б в среднем).

## 4. Проёмы: маркера `forWall` в ответе нет, но проёмы в плане есть

Требует аккуратности, потому что «дверей и окон нет» — соблазнительный, но неверный вывод.

**Подтверждено замером:**

- Ключа `forWall` в документе **нет ни у одного из 125 продуктов** (0 вхождений).
- Ключей `addMf` и `addMb` в документе тоже **нет ни у одного продукта**.
- При этом **ровно 5 продуктов** (все `type: 2`, MODEL) несут блок из восьми полей
  `mf, mfr, mfx, mfy, mb, mbr, mbx, mby`. У остальных 120 продуктов этих полей нет.

**Подтверждено по исходнику:** писатель эмитит эти восемь полей **только** внутри
`if (sceneObject.forWall)` (`plannercore.js:14961`) и первым делом в этом же блоке пишет
`data['forWall'] = true` (`14962`), `addMf` (`14964`) и `addMb` (`14970`).

**Вывод (наш, не факт из исходника): в плане пять проёмов.** Восемь полей рамы и низа проёма
не могут появиться у продукта иначе как через ветку `forWall`, а сам маркер и два поля
`addM*` в прочитанном ответе отсутствуют — то есть **читающий эндпоинт отдаёт не побайтово то,
что писал `makeSceneObjectData`**. Габариты пяти кандидатов подтверждают трактовку: три
шириной 95–97 см при высоте 208–210 см (типовой дверной проём) и два шириной 265–268 см при
высоте 250 см (широкий портал), все пять с `y = 0`, то есть от уровня пола.

Практические следствия для нашего замера:

- **Вес проёмов в цифры §1–2 входит**: пять таких продуктов весят 4 186 Б (3.5% документа),
  в среднем 837 Б против 680 Б у обычного продукта. Блок из восьми `mf/mb`-полей стоит 350 Б
  на пять проёмов — 70 Б на проём.
- **Окон в этом плане нет**: все пять проёмов стоят на полу (`y = 0`). Вес окна как отдельного
  случая замером не подтверждён; структурно окно — тот же MODEL-продукт, так что отличий по
  весу от двери ждать неоткуда, но это рассуждение, а не измерение.
- **Расхождение «писатель эмитит `forWall`, читатель его не отдаёт» — открытый вопрос**, см. §9.

## 5. Base64 в документе нет — подтверждённый негативный факт

Ожидание перед замером было, что вес плана раздувают встроенные картинки. **Не подтвердилось.**

Метод проверки (три независимых прохода по `plan`):

1. **Обход всех строк дерева.** Строк в документе 2 740, **самая длинная — 64 символа**.
   Строк длиннее 200 символов — **ноль**, длиннее 100 — тоже **ноль**. Base64-блоб в 64 символа
   не помещается физически.
2. **Поиск подстроки `data:` по всему минифицированному `plan`** — **0 вхождений**.
   Подстрока `base64` в любом регистре — **0 вхождений**.
3. **Сходимость сумм** (§2): секции складываются в 120 613 Б без «лишнего» веса, который
   пришлось бы объяснять скрытым блобом.

Итого: **весь вес документа — это структура и идентификаторы, ни одного встроенного бинарника.**
Картинки в этом формате живут ссылками: `preview` — путь (59 Б), `skybox` — шесть URL по 64
символа (454 Б вместе с полем поворота).

### 5.1. Превью: чтение и запись несимметричны

Здесь важно не поймать ложное противоречие с существующим разбором.

- **На запись** ([10-serialization-save-format.md:92](../10-serialization-save-format.md)):
  `preview` — «base64 **JPEG** thumbnail (data-URI prefix stripped)», все вьюеры кодируют
  `toDataURL("image/jpeg")` (якоря `46737`, `47738`, `48324`, `61031`). Цитата перепроверена по
  месту при написании этого файла.
- **На чтение** (замер): `preview` — строка из 57 символов, путь вида `/files/plans/….jpg`,
  59 Б в JSON.

**Это не противоречие, а асимметрия чтения и записи.** Напрашивающаяся трактовка (не проверялась):
клиент отправляет картинку телом base64, сервер сохраняет её файлом и на чтении возвращает уже
путь к нему. Независимо от трактовки, сам факт расхождения измерен. Тот же почерк виден
в двух других местах ответа: верхнеуровневый `skybox` с шестью готовыми URL текстур кубмапы,
которого нет в схеме сохранения вовсе (в сохраняемом `scene.skybox` лежат только `{id, r, tags}`,
25 Б), и пропажа `forWall`/`addMf`/`addMb` из §4.

Что из этого следует для наших цифр: **117.8 КБ — это вес документа на чтении.** Тело
сохранения того же плана содержало бы вместо 59-байтового пути base64-JPEG превью, и было бы
на размер этого превью больше. Насколько именно — **замером не установлено** (§9): превью
в снятом ответе нет, только ссылка.

## 6. `floorplan = null` — вес подложки не замерен

У этого плана **подложки нет**: `floorplan` в документе присутствует и равен `null` (4 Б).

По схеме ([10-serialization-save-format.md](../10-serialization-save-format.md) §envelope)
`floorplan` — «uploaded floor-plan tracing image + display state (`drawing.source` base64,
`drawing.display`)», то есть при наличии подложки в документе лежал бы **base64 растра**.

Отсюда два аккуратных утверждения:

- Негативный факт §5 («base64 в документе нет») **строго верен только для планов без подложки**.
  Для плана с подложкой он не проверялся.
- **Вес плана с подложкой замером не подтверждён и не опровергнут.** Единственное, что можно
  сказать не гадая: base64 растёт как ×4/3 от размера файла, и растровый план на несколько
  сотен КБ перевесил бы всю остальную структуру документа в разы. Это арифметика кодировки,
  а не наш замер — числа для конкретного плана мы не видели. Помечено в §9.

## 7. Наблюдения по избыточности формата

Ниже — то, где формат конкурента платит байтами за удобство. Это **наблюдения по чужому
формату**, а не вердикты: «повторять / не повторять» решается в
[`competitor-practices-audit.md`](../../../architecture/competitor-practices-audit.md), не здесь.

Все цифры этого параграфа — **дельты удаления** (§1): значение + имя ключа + разделители.

### 7.1. Хеш слота материала — 11.4% всего документа

`materials[]` есть у 117 продуктов из 125 (у всех MODEL), суммарно **328 слотов**, средний
слот — **129.0 Б**. Форма слота: `{current, default, hash, name, source, addMaterial}`
(+ `setId` у двух).

| Что                                 | Дельта удаления | % плана   | % продуктов |
| ----------------------------------- | --------------- | --------- | ----------- |
| Весь `materials[]` целиком          | **43 843**      | 36.4%     | **51.1%**   |
| Только поле `hash` во всех слотах   | **13 776**      | **11.4%** | 16.1%       |
| Только поле `name` во всех слотах   | 5 297           | 4.4%      | 6.2%        |
| Только поле `source` во всех слотах | 5 202           | 4.3%      | 6.1%        |

`hash` — **строка ровно 32 символа** во всех 328 слотах без исключения; по разбору
([10-serialization-save-format.md](../10-serialization-save-format.md) §`products[]`) он
«matches the slot to its mesh UV», то есть служит ключом сопоставления слота с мешем.
Уникальных значений среди 328 — **230**: 98 слотов повторяют хеш, уже встречавшийся в документе.

Наблюдение: **половина веса продуктов и треть веса документа — это назначения материалов, а
внутри них 11.4% всего документа занимает один-единственный 32-символьный ключ**, дублируемый
в каждом слоте каждого экземпляра, включая 125 экземпляров одного и того же каталожного меша.

### 7.2. Поля плинтусов пишутся всегда — половина веса конструктива

У стены **ровно 37 полей, одинаковый набор у всех 55** — ни одно поле не опускается.
Из них:

- 13 полей собственно стены: `id, name, partialVisible, visible, exists, pa, pb, pm, m, mr, mx, my, conf`;
- **12 полей верхнего плинтуса** (`pltv, pltvisible, pltpv, plthbi, pltm, pltAddm, pltmr, pltmx, pltmy, plth, pltd, pltsh`);
- **12 полей нижнего плинтуса** (те же с префиксом `plb`).

| Что                                    | Дельта удаления | % стен    | % конструктива | % плана   |
| -------------------------------------- | --------------- | --------- | -------------- | --------- |
| Все 24 поля `plt*`/`plb*` на 55 стенах | **16 333**      | **68.6%** | **48.7%**      | **13.5%** |

То есть **две трети веса массива стен и почти половина веса всего конструктива — это плинтусы**,
при том что сами значения в этих полях занимают лишь 4 013 Б: остальные 12 320 Б — имена ключей
и пунктуация, 24 ключа × 55 стен.

Поля пишутся безусловно, даже когда плинтуса нет: у **9 стен из 55** `pltv = 0` (верхнего
плинтуса не существует), и всё равно все 12 полей `plt*` у них присутствуют — 1 340 Б на пустоту.

Попутно замечено: `pltsh` и `plbsh` — **пятизначные каталожные id**, а не индексы `0…15` из
захардкоженного банка профилей ([11-plinth-profile-bank.md](./11-plinth-profile-bank.md) §1).
Одно и то же значение у всех 55 стен для каждого из двух плинтусов. Это согласуется с рантайм-
перезаписью `PoolPlinthShape[id]` каталожными SVG (`createPlinthShape`, `56701`–`56778`), а не с
выбором из 16 констант.

### 7.3. `construction.list[]` — денормализованный манифест

`list` — 174 элемента (173 уникальных, 1 повтор), 91 число и 83 строки, **983 Б** дельты
удаления. По разбору ([10-serialization-save-format.md:95](../10-serialization-save-format.md))
это «a flattened manifest list of all product+material ids referenced (used to pre-fetch the
catalog)».

Замер это подтверждает и уточняет: **172 из 173 уникальных значений `list` встречаются в
документе где-то ещё** — 90 совпадают с `scene.products[].id`, 73 с
`scene.products[].materials[].current`, 47 с `…materials[].default`, остальные с материалами
стен, полов, зон и плинтусов. Значение, не найденное больше нигде, — **одно**.

Наблюдение: `list` — **чистая денормализация**, почти целиком выводимая обходом документа;
формат платит 983 Б (0.8%) за то, чтобы загрузчик не обходил дерево перед префетчем каталога.
Заметно, что `list` **не** содержит id конструктивных сущностей: `points/walls/rooms/covers/
areas/cuts` нумеруются независимо и с единицы (105 точек — id 1…105, 55 стен — id 1…55), их
id в манифест не попадают.

### 7.4. Мелочи, которые видно только на 125 продуктах

Дельты удаления по всему документу:

| Поле                         | Дельта | % плана | Что видно                                               |
| ---------------------------- | ------ | ------- | ------------------------------------------------------- |
| `products[].userKey`         | 5 625  | 4.7%    | одно и то же значение у всех 125 продуктов (34 Б × 125) |

Суммарно эти девять полей — **21 105 Б, 17.5% документа**. Восемь из девяти (все, кроме `plan`,

## 8. Экстраполяция на «трёшку» — это расчёт, а не замер

> **Всё в этом параграфе — арифметика по удельным стоимостям §2, а не измерение.**
> Замерен один план (§3). Второго плана мы не мерили. Числа ниже — оценка порядка величины,
> ссылаться на них как на факт нельзя.

Удельные стоимости берутся из §2 (вес значения / число элементов). Состав гипотетической
трёшки — наше допущение: три спальни, гостиная, кухня, два санузла, коридор.

| Слагаемое                                                        | Штук (допущение) | × Б/шт | = Б          |
| ---------------------------------------------------------------- | ---------------- | ------ | ------------ |
| Точки                                                            | 160              | 51.0   | 8 160        |
| Стены                                                            | 80               | 432.7  | 34 616       |
| Полы                                                             | 8                | 423.8  | 3 390        |
| Комнаты                                                          | 9                | 102.6  | 923          |
| Зоны                                                             | 3                | 225.0  | 675          |
| Вырезы                                                           | 5                | 53.7   | 269          |
| Продукты                                                         | 200              | 686.7  | 137 340      |
| `list[]`                                                         | ×1.6 от 975      | —      | 1 560        |
| Прочее (конверт, `cap`, `viewState`, `skybox`, `hiddenElements`) | как есть         | —      | ~830         |
| **Итого**                                                        |                  |        | **~187 800** |

**~187 800 Б ≈ 183 КБ** минифицированного JSON. При коэффициентах сжатия из §1 это
**~23 КБ gzip** (187 800 / 8.15) и **~18 КБ brotli** (187 800 / 10.35).

Что из этой арифметики устойчиво, а что нет:

- **Устойчиво:** доминирует мебель. Даже если ошибиться в числе стен вдвое, продукты остаются
  ~70% документа — при 200 предметах это 137 КБ из 183 КБ.
- **Устойчиво:** порядок величины. План жилой квартиры в формате такого рода — **сотни
  килобайт несжатыми, десятки килобайт сжатыми**, а не мегабайты и не единицы килобайт.
- **Неустойчиво:** число предметов. 200 — допущение; меблировка «под ключ» легко даёт 300–400,
  и тогда документ уходит к 250–300 КБ.
- **Не покрыто вовсе:** подложка (§6). Одна растровая подложка способна перевесить весь
  расчёт выше.

## 9. Чего этот замер не показал

Явный список, чтобы никто не додумал:

- **Вес плана с подложкой** — не замерен. У снятого плана `floorplan = null` (§6). Ни
  подтверждено, ни опровергнуто.
- **Вес тела сохранения** — не замерен. Мерилось **чтение**; на записи как минимум `preview`
  уходит base64-JPEG (§5.1), а `skybox` и `forWall`/`addM*` ведут себя иначе. Насколько тело
  POST тяжелее прочитанного документа — неизвестно.
- **Вес окна** — не замерен: все пять проёмов плана стоят на полу (§4). Ожидание «окно весит
  как дверь» — рассуждение по структуре, не измерение.
- **Вес групп** — не замерен: `groups[]` пуст (§3). По схеме
  [10-serialization-save-format.md](../10-serialization-save-format.md) §`groups[]` каждая
  группа **повторяет форму продукта** в `objectsData[i]`, то есть группировка почти удваивает
  вес сгруппированных предметов. На этом плане это не проверено.
- **Вес истории/автосейва** — не замерен. Мерился один документ, не поток сохранений.
- **Второго плана нет.** Все удельные стоимости §2 выведены из одной выборки; разброс между
  планами неизвестен.
- **Открытый вопрос (не разрешён):** почему прочитанный ответ несёт восемь полей `mf/mb`, но
  не несёт `forWall`, `addMf`, `addMb`, которые писатель эмитит в том же блоке
  (`plannercore.js:14961`–`14972`), и как такой документ загружается обратно, если парсер
  опирается на `product.hasOwnProperty('forWall')` (`plannercore.js:26093`). Вариантов два —
  серверная санитизация ответа для публичного чтения или иная версия писателя, — но по одному
  замеру они не различимы. Проверять отдельно, если понадобится.
- **Динамика непрозрачных полей** не исследована: `viewState.state` — строка (144 Б вместе с
  `camera: {px, py, pz, tilt, pan, zoom}`), `extraData` — `{materialReplaced}` (25 Б). На этом
  плане оба малы; от чего они растут — неизвестно.
