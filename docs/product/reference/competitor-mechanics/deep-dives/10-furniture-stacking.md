# Deep-dive 10 — «Умное» перемещение и стекинг мебели (smart-move / посадка на поверхность)

Реверс по неминифицированному `plannercore.js` конкурента; все номера строк — по
этому файлу. Закрывает пробел из `04-furniture-placement.md` (§ smart-move):
здесь построчно разобраны `G.shiftVectors` и `getVectorsSides`.

Драг мебели живёт в двух состояниях MIH (mouse interaction helper):

- **`R2D.MIH.StateDraggingProduct`** (строка 43774) — перетаскивание объекта,
  уже стоящего на сцене;
- **`R2D.MIH.StateDraggingProdFromCatalog`** (44260) — перетаскивание нового
  объекта из каталога.

Внутри каждого состояния три режима движения, выбираемые **на каждый
mousemove** заново (`moveProduct`, 43922 / 44358):

| Режим              | Функция                                | Когда                                                                    |
| ------------------ | -------------------------------------- | ------------------------------------------------------------------------ |
| smart (стекинг)    | `moveObjectSmart` (44036 / 44465)      | `POSTER` или «маленький» объект (`checkAsSmartMoving`, 43940–43947)      |
| smart-from-catalog | `moveObjectSmartFromCatalog` (44502)   | только в catalog-состоянии: `MODEL && !forWall`                          |
| horizontal         | `moveObjectHorizontal` (43952 / 44390) | всё остальное (крупная мебель, настенные)                                |
| straight (Shift)   | `moveObjectStraight` (44076)           | Shift зажат и `!forWall` (только в состоянии drag со сцены, 43927–43929) |

## Verdict: standard-or-custom

**Полностью самописный, без физики и без коллизий.** Ядро стекинга — один
рейкаст по всей интерактивной сцене + «опорная функция» OBB (min-проекция
восьми углов бокса на нормаль пересечённой грани). Нет `THREE.Box3`, нет
пересечений боксов, нет разрешения проникновений: объект просто телепортируется
так, чтобы его ближайший по нормали угол коснулся плоскости попадания. Из
THREE используются только `Raycaster.setFromCamera` + `intersectObjects` (36505,
36510–36512), `intersect.point` и `intersect.face.normal`; вся остальная
математика — свой `GEOM` (`G.V`, `rotateByY`).

## Ядро: `G.shiftVectors` + `getVectorsSides`

### `GEOM.shiftVectors(center, normal, vectors)` — строка 9280

```js
GEOM.shiftVectors = function (center, normal, vectors) {
  var minProj = Infinity;
  for (var i = 0; i < vectors.length; i++) {
    var cVec = new G.V(vectors[i].x, vectors[i].y, vectors[i].z);
    var proj = cVec.x * normal.x + cVec.y * normal.y + cVec.z * normal.z;
    if (proj < minProj) minProj = proj;
  }
  return new G.V(-normal.x * minProj, -normal.y * minProj, -normal.z * minProj);
};
```

Построчно (9282–9294):

1. `vectors` — 8 углов OBB перетаскиваемого объекта **в локальной системе
   объекта-относительно-его-origin** (см. `getVectorsSides` ниже): origin в
   центре подошвы, углы уже повёрнуты на rotationY.
2. Для каждого угла считается скалярное произведение `proj = cᵢ · n` —
   подписанная проекция угла на нормаль опорной грани.
3. Берётся минимум `minProj = min_i (cᵢ · n)` — «глубина» самого дальнего
   против нормали угла (support function OBB в направлении `−n`).
4. Возвращается `shift = −n · minProj`.

Параметр **`center` не используется вообще** — мёртвый аргумент (в вызовах
туда передают точку пересечения, 44052, но внутри она не читается).

Свойство результата: позиция объекта ставится в `pos = hitPoint + shift`
(`G.V.sum`, 44053; `sum` определён на 8966). Тогда для любого угла `c`:

```
(pos + c − hitPoint) · n = c·n − minProj ≥ 0,   равенство — для опорного угла
```

т.е. весь бокс оказывается по положительную сторону касательной плоскости
(проходящей через точку попадания с нормалью грани), касаясь её опорным
углом. Это классическая посадка выпуклого тела на опорную гиперплоскость.

Частные случаи (origin объекта — центр **подошвы**, y углов ∈ {0, h}):

- **Верхняя грань (пол, столешница, комод), n = (0,1,0):**
  `minProj = min(0, h) = 0` → `shift = 0` → `sceneObject.y = hit.y` — подошва
  ровно на поверхности. Стекинг «ваза на комод» — именно это.
- **Боковая грань (стена, бок шкафа), n горизонтальна:**
  `minProj = −(w/2·|n·ux| + d/2·|n·uz|)` (полуразмеры повёрнутого следа) →
  объект отодвигается наружу на свою полуширину вдоль n — встаёт вплотную,
  не проваливаясь в грань.
- **Нижняя грань (потолок), n = (0,−1,0):** `minProj = min(0, −h) = −h` →
  `shift = (0,−h,0)` → `pos.y = hit.y − h` — объект подвешивается **верхом** к
  потолку. Отдельного «ceiling»-режима не существует, это следствие той же
  формулы.

Важно, чего формула **не** делает: не проверяет, помещается ли след объекта на
опорной грани (можно свесить вазу за край комода — центр держится на точке
курсора), и не проверяет пересечения с другими объектами.

### `R2D.ObjectViewer3D.prototype.getVectorsSides()` — строка 31685

```js
var w2 = w/2, d2 = d/2;                    // w,h,d = размеры С УЧЁТОМ scale (11343–11353)
var positions = [ (-w2,0,-d2), (w2,0,-d2), (w2,0,d2), (-w2,0,d2),
                  (-w2,h,-d2), (w2,h,-d2), (w2,h,d2), (-w2,h,d2) ];  // 31692–31701
var ry = G.toRad(sceneObject.rotationY);   // 31702
for (...) p.rotateByY(ry);                 // 31704–31708
```

Никакой классификации «сторон» тут нет, несмотря на имя: функция просто отдаёт
**8 углов OBB в локальных координатах относительно origin (центр подошвы, y от
0 до h), повёрнутых на текущий rotationY объекта**. Размеры берутся через
геттеры `width/height/depth` (умножены на scale, 11343–11353), так что
half-extents реальные. `rotateByY` (8945) крутит пару (z,x) через
`GEOM.rotatePosition` (8649) — по знаку совпадает с THREE-поворотом `+ry`
вокруг Y (у view3d `object3d.rotation.set(rx, ry, rz)` из тех же градусов,
31553–31559), поэтому углы и нормали живут в одной конвенции.

Рядом есть `getVectorsBoundsPositions` (31714) — то же самое, но со сдвигом на
мировую позицию и **без** поворота; в стекинге не используется.

## Полный флоу smart-move (`moveObjectSmart`, 44036–44074)

1. **NDC мыши:** `R2D.Renderer3D.getMousePointForPicker(canvas, mx, my)`
   (36929) — обычный перевод в [−1..1] по `getBoundingClientRect`.
2. **Рейкаст по всей сцене:** `objectUnderCursor(interactiveObjects, camera,
u, v, view3DObject.object3d)` (44039). `interactiveObjects` собирается на
   38041–38046: `terrain` (пол-«земля», плоскость 50000×50000 на y=−0.2,
   37895–37915) + `productObjects` + `constructorObjects` + `constructorWalls`
   - `view2DObjects` + `coversTitleObjects`. Внутри (36505–36538) —
     `raycaster.intersectObjects(children, true)`, берётся первый видимый хит,
     **исключая сам таскаемый объект**: `exclude == obj ||
exclude.children.includes(obj)` (36521) — фильтр только на один уровень
     вложенности.
3. **Нормаль:** `intersect.face.normal` (локальная нормаль геометрии) →
   `rotateByY(intersectSceneObjectRotationY)` (44050), где угол — rotationY
   **пересечённого продукта** (`findObjectView3DByObject3D`, 44044); если
   попали в стену/пол конструктора, продукт не найден и угол = 0 (44045) —
   предположение, что геометрия конструктора запечена в мировых координатах.
   Полной матрицей мира нормаль **не** трансформируется.
4. **Позиция:** `shift = G.shiftVectors(hit, n, getVectorsSides())`;
   `pos = hit + shift`; `sceneObject.x/y/z = pos` (44051–44057). Позиция
   **абсолютная** — объект прыгает опорным углом в точку под курсором (в
   отличие от дельта-формулы horizontal-режима, см. ниже).
5. **POSTER-ветка** (44059–44063): `rotationY = radToDeg(atan2(n.x, n.z))` —
   лицом от стены (44061); `y = y − pointIntersect.y + oldPosition.y` (44062) —
   постер сохраняет высоту хвата (`oldPosition` — позиция объекта на старте
   драга, 43845–43849; `pointIntersect` — первая точка попадания, 44047). Для
   MODEL авто-поворот к нормали закомментирован (44066).
6. `sceneObject.update()` (44069) → `checkValues()` (11446–11447): клампы
   `y < −3` → сброс на дефолтную высоту продукта; `−3 ≤ y < 0` → `y = 0`;
   `y > OBJECT_Y_MAX = 1000` → сброс на дефолт (11294–11300, константы
   11468–11469).
7. Событие `OBJECT_SMART_MOVE {elevation: y}` (44073) — наружу в UI.

**Переход smart↔пол («слезание» с комода).** Отдельного перехода нет: режим
перевыбирается каждый mousemove (43922–43948), а smart-режим каждый кадр
пересчитывает y абсолютно от текущей поверхности. Утащил курсор с комода —
рейкаст попадает в terrain (y = −0.2, n = (0,1,0)) → `y = −0.2` → кламп
`checkValues` поднимает до 0. Обратно на комод — y снова равен высоте
столешницы. Крупная мебель (не-smart) в horizontal-режиме y вообще не трогает —
её элевация во время драга неизменна.

**Критерий «маленького» объекта** (`checkAsSmartMoving`, 43940–43947 и
44378–44385, одинаковый):

```js
if (sceneObject.forWall) return false;
max / min < 15 && sceneObject.volume < 30000; // volume = w*h*d, геттер 11356–11361, см³
```

т.е. не настенный, не «плоский лист» (соотношение сторон < 15) и объём меньше
30 000 см³ (куб ~31 см; декор, вазы, книги, светильники).

### `moveObjectSmartFromCatalog` (44502–44547) — драг нового MODEL из каталога

Рейкаст **только по `constructorWalls`** (44505). Попали в стену → та же пара
`getVectorsSides` + `shiftVectors` (44521–44523), но применяются только
`x`/`z`; строка `sceneObject.y = positionPoint.y` **закомментирована** (44527) —
высота остаётся дефолтной для продукта. Затем `rotationY = atan2(n.x, n.z)`
(44530) — лицом от стены, и поверх — 2D-снап `snapPolygon` (44532–44539).
Промахнулись мимо стен → `setDefaultRotation` (44549–44576: поворот на
0/−90/−180/−270 по квадранту азимута камеры) и обычный `moveObjectHorizontal`
(44508–44510).

## Horizontal- и straight-режимы (для контраста)

`moveObjectHorizontal` (43952–44035, дубль 44390–44464):

- Рейкаст в **невидимую горизонтальную плоскость** `_object3DMoving`
  (`intersectWithObject`, 43955; сам метод — 36557–36563, нерекурсивный
  `intersectObject`). Плоскость создаётся в CommonSceneObject как
  `moving` (37940–37957): `PlaneBufferGeometry(50000, 50000)`, повёрнута
  горизонтально, `opacity: 0`, `depthWrite: false`, паркуется на `y = −100`;
  в MIH прокинута как `_object3DMoving` (41568), в рейкаст-контейнеры не
  входит (отдельный `scene3d.add(moving, "top")`, 38049).
- **Высота плоскости выставляется на mouseDown** в `StateSelectedProduct`:
  `mih._object3DMoving.position.setY(downObjectData.point.y)` (44750;
  для групп — 45349) — плоскость поднимается на высоту точки хвата, поэтому
  объект, стоящий на комоде, при горизонтальном драге не «ныряет» (курсор
  скользит по плоскости на его высоте). При старте из каталога —
  `setY(position.y + height/2)` (42034–42036).
- **Дельта-формула** (43978–43985): первая итерация запоминает
  `pointIntersect` (43975), дальше
  `position = {x: hit.x + oldPosition.x − pointIntersect.x, y: hit.z +
oldPosition.z − pointIntersect.z}` (43983–43984) — перенос без прыжка,
  `oldPosition` = позиция объекта на старте драга (43845–43849). Меняются
  только `x`/`z`.
- **Настенные MODEL** (`forWall`): рейкаст стен приоритетнее плоскости
  (43957–43963); позиция скармливается конструктору
  `moveElement(position, 20)` (43989) — захват к оси стены в радиусе 20 см
  (реализация `getAxis`, 55338–55357); если снап-стена сменила угол
  (`snapObject.rotation != oldSnapObj.rotation`), позиция пересчитывается «от
  чистой» точки пересечения без дельты (43991–43995) — чтобы объект не
  улетал при перескоке на перпендикулярную стену. Успех →
  `setDropDataToWallElement` (44002), провал → свободные координаты + возврат
  `defaultDepth` (44004–44006). На mouseUp — `dropElement(dropData, 10)`
  (43890): не нашлось стены в 10 см → объект удаляется со сцены и летит
  событие `OBJECT_DRAG_OUT_OF_WALL` (43903–43908).
- **Обычные MODEL**: 2D-снап `snapPolygon` (44008–44016), см. ниже.

`moveObjectStraight` (Shift, 44076–44151): та же плоскость, но дельта полная
3D (44109–44113), и движение **зажимается к доминирующей оси**: для
MODEL/CARPET — x против z (44119–44127), для POSTER — x против y (44128–44139).

Вертикальная элевация отдельно от драга: `setCurrentModelElevation(v,
isMouseDown)` (42878–42886) пишет `y` напрямую, `saveState` только когда
`!isMouseDown` (42885); инкрементальная `changeCurrentModelElevation` (42993)
без сохранения, фиксация — `stopChangingModelSizes` → `saveState` (43001–43004).
В драг-состояниях `saveState` тоже только на mouseUp (43917).

## Взаимодействие со Snap2D

- Снап-таблица строится в `updateSnap2d` (41626–41672), вызывается на входе в
  драг-состояние (`me.start`, 43785): линии — стены конструктора (41633–41641),
  боксы — 2D-следы **других** продуктов; исключаются текущий объект, любой
  объект в группе и объект, таскаемый из каталога (41645–41647); группы
  добавляются целиком как боксы, кроме текущей (41657–41664). Радиус снапа —
  `updateDistance(15)` (41668), т.е. 15 см (дефолт конструктора Snap2D — 10,
  9477).
- **В smart-режиме снапа нет вообще** — `moveObjectSmart` не вызывает
  `snapPolygon`. Конфликт «снап против посадки по нормали» исключён выбором
  режима: маленькие объекты только стекуются, крупные только снапятся.
- В horizontal-режиме порядок: дельта-позиция → `snapPolygon(objectPoints,
shift, height)` (44013, реализация 10007–10036: сначала к ближайшей линии,
  потом перпендикулярное доснапливание или к боксу) → снап-сдвиг вычитается из
  `x`/`z` (44014–44015). Ctrl/⌘ отключает снап (43936).
- В catalog-wall-режиме порядок: сначала `shiftVectors` от стены, потом снап
  поверх (44523 → 44532–44539) — снап корректирует только `x`/`z` и может
  сдвинуть объект вдоль стены; контакт по нормали при снапе к самой этой стене
  сохраняется, но формально снап последний и «сильнее».
- `SNAP.Snap2D.moveInFrontOfLines` (10038–10092) и
  `findFreeSpace` (`margin = 1.5`, 10096) к стекингу отношения не имеют — это
  соседний SNAP-неймспейс (автопоиск свободного места), проверено. При этом
  `moveInFrontOfLines` — dead code: по всей roomtodo-src единственное
  вхождение — строка определения, вызовов нет; локальная `deltaAngle = π·0.2`
  (10046) внутри не используется (рабочий порог в теле — `π·0.4`, 10068), так
  что «порогом» её считать нельзя.

## Настенные и потолочные объекты

- Единственные значения `appointment` — `"scene"` и `"wall"`
  (`APPOINTMENT_SCENE`/`APPOINTMENT_WALL`, 11473–11474); `forWall` — просто
  `appointment == "wall"` (11597–11600). **Константы `CEILING` в кодовой базе
  нет** (grep по "ceiling" даёт только конструктор потолков помещения).
- `forWall` жёстко выключает smart (43941 / 44379) — настенные ходят только
  horizontal-путём через конструктор (`moveElement`/`dropElement`, выше).
- Потолочная посадка существует только как побочный эффект `shiftVectors` на
  грани с n=(0,−1,0) для smart-объектов (люстра «прилипает» верхом), плюс
  кламп `OBJECT_Y_MAX = 1000`.
- POSTER — гибрид: идёт smart-путём всегда (43930), но с выравниванием по
  нормали и сохранением высоты хвата (44060–44062); при добавлении из каталога
  постер рейкастится по `interactiveObjects`, остальные — по terrain (14352).

## Спека для порта

Вход/выход одного кадра smart-move:

- **Вход:** позиция курсора (px), камера, дерево интерактивных объектов,
  таскаемый объект: `w,h,d` (с учётом scale), `rotationY`, тип, `forWall`.
- **Выход:** новые `x,y,z` (origin — центр подошвы), опционально `rotationY`
  (POSTER), событие с новой элевацией.

```
onMouseMove(mx, my):
  mode = pick_mode(obj)                       # каждый кадр заново!
  if mode == SMART:
      ndc  = to_ndc(mx, my)
      hit  = raycast(interactive, ndc, exclude = dragged.object3d)   # первый видимый
      if !hit: return
      n    = rotateY(hit.face.normal_local, rotY(hit.product) or 0)  # только Y!
      C    = obb_corners_local(obj)           # (±w/2, {0,h}, ±d/2) повёрнутые на rotY(obj)
      s    = min_i(C_i · n)                   # support в направлении −n
      pos  = hit.point − n * s
      obj.position = pos                      # затем clamp y к [0..1000]
```

Эквивалентная замкнутая форма вместо перебора 8 углов (для порта):
`s = −(w/2)·|n·ux| − (d/2)·|n·uz| + min(0, h·n_y)`, где `ux,uz` — оси объекта,
повёрнутые на rotationY. Несимметричный последний член — потому что origin в
подошве, а не в центре бокса.

THREE-примитивы у конкурента: `Raycaster.setFromCamera` +
`intersectObjects(children, true)` (36510–36512), `intersect.point`,
`intersect.face.normal` (локальная!), невидимая `PlaneBufferGeometry` для
horizontal-плоскости (37940). `Box3` не используется. Для нашего порта
правильнее брать `face.normal`, трансформированную `normalMatrix` мировой
матрицы хита (см. gaps), и держать те же три политики: (1) выбор режима по
`max/min < 15 && volume < 30000`, (2) плоскость драга на высоте точки хвата,
(3) отсутствие снапа в smart-режиме.

## Edge cases & thresholds

| Значение                  | Где                                    | Роль                                                  |
| ------------------------- | -------------------------------------- | ----------------------------------------------------- |
| `15` (ratio), `30000` см³ | 43944–43946 / 44382–44384              | порог «маленького» smart-объекта                      |
| `15` см                   | `updateDistance(15)`, 41668            | радиус 2D-снапа при драге                             |

## Confidence & gaps

**Высокая уверенность:** формула `shiftVectors` (min-проекция 8 углов, сдвиг
`−n·minProj`) и то, что `getVectorsSides` — это углы OBB с origin в подошве,
повёрнутые на rotationY (обе функции прочитаны целиком, 9280–9294 /
31685–31710); критерий smart-объекта; отсутствие снапа и коллизий в
smart-режиме; абсолютная (не дельта) посадка в smart против дельта-формулы
horizontal (43983–43984); механика невидимой плоскости и её подъём на высоту
хвата (44750); клампы y в `checkValues`; wall-флоу через
`moveElement(20)`/`dropElement(10)`; порядок «shift → snap» в catalog-wall
ветке; согласованность знаков `rotateByY` с THREE (8649/8945 против 31553–31558).

**Gaps / ниже уверенность:**

1. **Нормаль трансформируется только поворотом Y пересечённого продукта**
   (44050): для вложенных GLTF-узлов с собственными поворотами/масштабами и
   для продуктов с rotationX/Z локальная `face.normal` даст неверный мир —
   в коде это не обрабатывается; не проверял на живом приложении, ломается ли
   посадка на повёрнутые не по Y объекты.
2. Исключение таскаемого объекта из рейкаста — на один уровень детей (36521);
   не проверял, не «самопересекается» ли многоузловой GLTF (возможно, у всех
   продуктов ровно один меш-контейнер).
3. Брифовое «appointment WALL/CEILING @11473–11474» не подтвердилось: там
   `APPOINTMENT_SCENE`/`APPOINTMENT_WALL`; потолочного appointment не нашёл
   вовсе (утверждение «нет CEILING» — по grep, не по вычитке всех 81k строк).
4. Групповой драг (`45645` регион) не вычитывал — судя по вызовам, группы
   ходят только horizontal-путём со `snapPolygon` (45671–45683), smart для
   групп не видел.
5. Потребителей `OBJECT_SMART_MOVE` (UI-индикатор элевации) не трассировал
   дальше диспатча (44073, 838).
6. Как именно у POSTER выставляется глубина прижатия к стене при smart
   (нет явного `shiftVectors`-подобного офсета по глубине постера, кроме общего
   алгоритма) — не разбирал постерную геометрию отдельно.
