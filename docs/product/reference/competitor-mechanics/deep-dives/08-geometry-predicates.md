# Deep-dive 08 — Базовые геометрические предикаты 2D-ядра (namespace TR)

Реверс-инжиниринг неминифицированного `plannercore.js` конкурента. Все номера
строк — по этому файлу. Ядро предикатов живёт компактным блоком: `function TR()`
объявлен на строке 49468, весь «математический» слой — примерно 49470–50600.
Это справочник для нашей TS-реализации: каждая функция описана с формулой,
эпсилоном и граничными случаями.

## 2. Точечные предикаты

### 2.1 pointsMatch / Point.match — тождество точек

`TR.pointsMatch(A, B, accuracy)` @49560 и метод `me.match(P, accuracy)` у
`TR.Point` @49554: покомпонентное сравнение
`|A.x−B.x| < acc && |A.y−B.y| < acc`, **дефолт acc = L_EPS** (чебышёвская
метрика, не евклидова). Это самый строгий предикат в ядре — им склеиваются
вершины при триангуляции (`addSeg` @50939–50940 дедуплицирует точки тем же
L_EPS) и снапятся концы в `lineIntersectLine`.

### 2.2 distanceBetweenPointAndLine — знаковое расстояние до прямой

@49567: строит прямую `ax + by + c = 0` через две точки и возвращает
`(a·px + b·py + c) / sqrt(a² + b²)`. **Знаковое** (без `abs`), знак зависит от
порядка `pointLineA → pointLineB`. Деление на ноль при совпадающих точках
прямой — не защищено (NaN). Вызывающие (`pointOnLine` @49596,
`segmentsOverlay` @49921–49922) всегда берут `Math.abs`; как ориентационный
тест знак нигде в ядре не используется (ориентация делается отдельными
cross-product'ами, напр. `WC.rightOriented` @54929).

### 2.3 pointOnLine — точка на отрезке

@49576, дефолт `accuracy = B_EPS`. Алгоритм:

1. bbox-отсечка со слаком `accuracy` (49581–49585);
2. если точка ближе `accuracy` к любому концу — сразу `true` (49587–49591);
3. `if (distA >= AB && distB >= AB) return false` (49594) — точка «за обоими
   концами» одновременно;
4. иначе `|distanceBetweenPointAndLine| < accuracy` (49596–49598).

Граничные случаи: расстояние в шаге 4 — до **бесконечной прямой**, отсечение
вдоль отрезка держится только на bbox шага 1, поэтому точка чуть «за» концом
(в пределах B_EPS по обеим осям) считается лежащей на отрезке. Для почти
осевого отрезка bbox по одной из осей тонкий, и слак B_EPS фактически задаёт
поперечный коридор. Вырожденный отрезок (A≈B): шаг 2 спасает вблизи, дальше
шаг 4 даст NaN-сравнение → `false`. При `!point || !a || !b` — `undefined`
(49578), трактуется как false.

Внимание на call site @54427: `pointOnLine(P, A, B, true)` — в `accuracy`
приезжает `true`, который в сравнениях коэрцируется в `1` (т.е. допуск 1 см).
Похоже на случайность, но поведенчески это «грубый» допуск.

### 2.4 pointOnContour — точка на границе контура

@49603, дефолт `B_EPS`: перебор всех рёбер контура (включая замыкающее
`last→first` @49612) через `pointOnLine`. Контур принимается **незамкнутым**
массивом (без дублирования первой точки).

### 2.5 pointInBounds — точка в bbox отрезка

@50167, дефолт `acc = L_EPS` @50169: точка внутри прямоугольника, натянутого на
`A`, `B` (порядок углов любой — оба варианта неравенств проверяются), со слаком
`acc` по каждой оси. Используется как пост-фильтр после проекций
(напр. @53309–53310).

### 2.6 projectionPointOnLine — проекция точки на прямую/отрезок

@50128, сигнатура `(point, la, lb, as_seg = true, vertices = true)`.
Проекция считается аналитически (50135–50137), но с **хаком для почти
горизонтальных прямых**: если `|dy| < B_EPS`, то `px = point.x` (50139–50142)
вместо честного вычисления — при `dy` порядка 1e-5 и большом `dx` это даёт
ощутимую ошибку вдоль прямой. `as_seg` — обрезка по bbox отрезка со слаком
L_EPS (50151–50155); `vertices = false` — отбраковка проекций, попавших в конец
отрезка ближе L_EPS по манхэттену (50157–50161). При отсутствии `la`/`lb` —
`undefined` @50130.

### 2.7 perpendicularPoint — смещение по нормали

@50196: `perpendicularPoint(A, B, d)` возвращает точку `A`, смещённую на
расстояние `d` перпендикулярно направлению `A→B`. Реализация через наклон
нормали `k = −(Bx−Ax)/(By−Ay)` (50208), `cos = sqrt(1/(1+k²))`, `sin = k·cos`,
плюс два разворота знака: при `A.y > B.y` и при `A.y == B.y && A.x < B.x`
(50213–50221); горизонтальный случай `B.y == A.y` захардкожен `cos=0, sin=1`
(50201–50206). Проверка на конкретных векторах:

- направление `+Y` (A=(0,0), B=(0,1)) → смещение `(+d, 0)`;
- направление `+X` (A=(0,0), B=(1,0)) → смещение `(0, −d)`;
- направление `−Y` (A=(0,1), B=(0,0)) → смещение `(−d, 0)`.

То есть при `d > 0` смещение всегда **в одну и ту же сторону от направления
A→B**: вправо в математической ориентации (y вверх), влево — в экранной
(y вниз). Следствие: `perpendicularPoint(A, B, d)` и `perpendicularPoint(B, A, d)`
смещают в противоположные стороны — поэтому в mitering оба конца сегмента
офсетятся с разными знаками `d`/`−d` (см. deep-dive 02, блоки @58031–58033,
@55441–55452). Вырожденный случай A==B не защищён (k = 0/0 → NaN).

### 2.8 Прочие мелкие

- `euclDist`/`euclDistP` @49485/49495 — евклид (P-версия optional-chain'ит
  аргументы, при null даст NaN); `manhDist`/`manhDistP` @49490/49500 — манхэттен.
- `bisectorPoint(O, A, B)` @50175 — точка на биссектрисе угла AOB на расстоянии
  ~1 от O (среднее двух единичных ортов); `null`, если орты противоположны
  (расстояние до середины < L_EPS @50191).
- `pointAtAngle(A, B, phi, r)` @50230 — точка на расстоянии `r` от `A` под
  углом `phi` к направлению `A→B` (через `atan(k)` с поправкой `+π` при
  `B.x < A.x`).
- `rotateXY` @50260, `triangleCenter` @49734 (центроид),
  `triangleArea` @49739 (знаковая, cross/2).

## 3. pointInContour — луч влево с обработкой вершин

@49629. Ray casting горизонтальным лучом из `P` в направлении **−X**. Контур —
незамкнутый массив; `< 3` точек → `false` @49631. Локальный `EPS = 1e-6`
@49633 — только для захвата вершин на луче.

Алгоритм двухфазный:

**Фаза 1 — вершины, лежащие на луче** (49636–49702). Собираются индексы вершин
с `x < P.x + EPS` и `|y − P.y| < EPS` (49639) — т.е. вершины левее точки (и
саму точку в пределах EPS), попавшие на горизонталь луча. Последовательные
индексы группируются в «пробеги» `[start, end]` (49649–49668), пробег через
стык конца/начала массива склеивается (49670–49675). Для каждого пробега
берутся `y` соседей до и после (с заворотом по модулю длины, 49677–49696) и
пересечение засчитывается, только если сосед до и сосед после лежат **по
разные стороны** от `P.y` (49698–49699: `y0 < P.y < y1` или `y0 > P.y > y1`).
Это классическое правило «вершина/горизонтальное ребро на луче считается одним
пересечением, только если контур реально переходит через горизонталь».

**Фаза 2 — обычные рёбра** (49704–49730). Контур замыкается `cont.push(cont[0])`
@49704; рёбра, инцидентные вершинам из фазы 1, пропускаются (49707–49708).
Далее отсечки: оба конца правее `P.x` — скип; оба выше или оба ниже `P.y` —
скип; оба левее `P.x` (и y-straddle) — пересечение засчитывается без вычислений
(49715–49722). Смешанный случай (один конец левее, другой правее): вычисляется
`k = (by−ay)/(bx−ax)` и `ly` — ордината ребра при `x = P.x` (49724–49725);
пересечение левее точки ⇔ `(k > 0 && ly > P.y) || (k < 0 && ly < P.y)`
(49727–49728). Результат — чётность (49731).

Граничные случаи:

- **Точка на границе — результат не специфицирован** (зависит от стороны и
  направления обхода). Поэтому все вызывающие сначала фильтруют границу через
  `pointOnContour` (см. `compareContours` @50032, `compareContoursOnePoint`
  @49815) — контракт «сначала boundary-тест, потом in/out».
- Вертикальное ребро в смешанной ветке дало бы `k = ±Infinity`, но смешанная
  ветка для строго вертикального ребра недостижима (оба `x` равны →
  сработает одна из отсечек); ребро с `bx == ax` точно на `P.x` — деление
  0-подобного на 0, риск NaN — практически исключён фазой 1 (вершины на луче
  выфильтрованы, но вершины на вертикали `x = P.x` при `y ≠ P.y` — нет; см.
  gaps).
- `EPS = 1e-6` мельче B_EPS: точка, «почти» лежащая на вершине с ошибкой
  1e-5, обеими фазами обрабатывается как generic-случай.

`pointInContours(P, contours, one)` @49616 — счётчик: возвращает **число**
контуров, содержащих точку; при `one = true` — ранний выход `1`. Счётчик (а не
булево) важен: в `triangulateContours` группа треугольников классифицируется
сравнением `inside > outside` и `pointInContours(center, bound) >=
pointInContours(center, subtr)` (51021–51026) — фактически чётно-ненулевая
логика вложенности.

## 4. Пересечения и наложения отрезков

### 4.1 segmentsIntersected — строгий тест «крест-накрест»

@49864: четыре знаковых площади (cross products) `v1..v4`, пересечение ⇔
`v1·v2 < 0 && v3·v4 < 0`. **Только трансверсальные пересечения**: касание
концом, T-стык и коллинеарное наложение дают `0` в произведении → `false`.
Единственный клиент — `contourSelfIntersected` @49845 (O(n²) перебор пар рёбер
замкнутого контура), т.е. самопересечение «внахлёст» через общую вершину не
детектится — для проверки пользовательского ввода этого достаточно.

### 4.2 lineIntersectLine — главный солвер пересечений

@49874, сигнатура `(A, B, E, F, as_seg = true, vertices = true, accuracy = 0)`.

1. При `as_seg` — bbox-отсечка со слаком `accuracy` (49880–49887).
2. Обе прямые в форме `ax + by + c = 0` (49890–49895); `denom = a1·b2 − a2·b1`
   @49897; **`|denom| < L_EPS` → `null`** @49898 — параллельность/вырожденность.
   Важно: `denom` здесь — это cross-product направлений, масштабируется как
   длина², т.е. порог 1e-8 для коротких отрезков (мм) заметно грубее, чем для
   длинных (метры).
3. Точка пересечения по Крамеру @49900.
4. **Снап к вершинам**: если `A` совпадает (pointsMatch, L_EPS) с `E` или `F` —
   `ip = A`; аналогично `B` (49902–49903). Общая вершина двух отрезков
   возвращается бит-в-бит, без float-дрейфа.
5. При `as_seg` — проверка принадлежности `ip` обоим отрезкам **по манхэттену**:
   `manhDist(ip, конец) <= manhDist(концы) + accuracy` для всех четырёх концов
   (49907–49910). Манхэттен вместо евклида — анизотропный слак (по диагонали
   допуск в √2 раза больше в евклидовой мере).
6. При `vertices = false` — если `ip` совпадает (L_EPS) с любым из четырёх
   концов → `null` @49912. Это режим «только внутренние пересечения», им
   пользуется `compareContours` @50015.

### 4.3 segmentsOverlay — коллинеарное наложение

@49917, `dist = L_EPS` по умолчанию. Два условия:

1. оба конца `A`, `B` лежат на прямой `EF` ближе `dist` (49921–49924) — при
   дефолте 1e-8 это фактически **точная коллинеарность** (работает потому, что
   после rebuild смежные стены делят вершины бит-в-бит);
2. 1D-перекрытие диапазонов: ось выбирается по наклону — если хоть один отрезок
   почти горизонтален (`|Δy| < B_EPS`), сравниваются `x`, иначе `y`
   (49928–49938). Внутренний `eps = −L_EPS` @49926: отрицательный слак делает
   отсечку чуть строже, так что **касание только общим концом наложением не
   считается** — нужен реальный 1D-нахлёст.

Замечание: в 49921–49922 функция передаёт `distanceBetweenPointAndLine` 4-й
аргумент `false` — тот принимает три параметра, аргумент игнорируется
(артефакт рефакторинга).

### 4.4 checkContact — «контуры делят кусок границы»

@49942: O(n·m) перебор пар рёбер двух контуров, рёбра короче B_EPS по
манхэттену пропускаются (49947, 49954), пересечение → `segmentsOverlay` с
дефолтным L_EPS. Семантика: **контакт = коллинеарный нахлёст рёбер ненулевой
длины**, точечное касание углами контактом не является. Единственный вызов —
из `compareContours` @50062 (упоминание в доке 03 — это оно и есть).

## 5. angleBetweenLines — ориентированный угол (критично для mitering и трассировки)

@49754:

```js
angAB = atan2(Bx - Ax, By - Ay);   // ВНИМАНИЕ: atan2(dx, dy), не (dy, dx)
angCD = atan2(Dx - Cx, Dy - Cy);
ang = angAB - angCD;
if (ang < 0) ang += 2π;  if (ang >= 2π) ang -= 2π;
```

Свойства (проверено по формуле):

- Аргументы `atan2` переставлены — угол каждого направления меряется **от оси
  +Y**, с ростом в сторону +X (в математической ориентации это по часовой; в
  экранной y-вниз — против часовой). На разности это даёт: `ang` — угол
  **поворота от направления CD к направлению AB**, положительный в ту же
  сторону.
- **Диапазон — [0, 2π)**, не [0, π]: функция ориентированная,
  `angle(AB, CD) = 2π − angle(CD, AB)` (кроме 0). `0` — сонаправленные, `π` —
  противонаправленные.
- Нулевые векторы (`A == B`) дают `atan2(0,0) = 0` — угол меряется как от +Y,
  без ошибки.

Кто и как использует (это и фиксирует контракт ориентированности):

- **Mitering** @58044/58104 (deep-dive 02): угол в вершине `P1` между
  `P0→P1` и `P1→P2`; сравнение с `recalcAng = 0.75π` идёт по обе стороны
  (`ang > recalcAng && ang < 2π − recalcAng` @58046) — т.е. mitering
  фактически использует симметризованную величину, но через полный диапазон.
- **Трассировка контуров из триангуляции** — `contoursFromGroup`, `nextPt`
  @50892 (и клон на point-объектах @52160): для текущей вершины перебираются
  соседи, угол считается между «входящим» направлением `prev→targ` и
  направлением `neighb→targ` (оба вектора **входят** в вершину); при обходе
  CW берётся сосед с **максимальным** углом, при CCW — с **минимальным**
  (50907–50909). Это классический выбор «самого левого/правого поворота» —
  работает только потому, что угол ориентированный и полный [0, 2π).
  Первый шаг обхода использует фиктивный prev слева: `[x−10, y]` @50875.
- **parallelLines** @50252: параллельность ⇔ `ang` в пределах `maxAngle=0.05`
  от 0, π или 2π (сонаправленность и противонаправленность равнозначны).
  Через неё — спаривание стен `WC.boxFromWalls` @54826.
- **WC.rightOriented** @54922: `parallel = ang < π/2 || ang > 3π/2`
  (грубая сонаправленность) + знаковый cross для лево/право @54929 — выбор
  корректной пары «лицевых» сторон стен.
- **Снап при рисовании** @66154–66196: выбор ближайшего по углу выравнивателя
  (range-check `ang < recalcAng || ang > 2π − recalcAng` @66156, где
  `recalcAng = Math.PI * 0.75` @66147 — т.е. угол должен быть близок к 0 или 2π,
  что через ориентированный [0, 2π) даёт «почти сонаправлено» в любую сторону).
- Прочее: видимость стен из камеры @55938–55943, ортогональность проёмов
  @66036–66037.

Для порта: **нельзя заменять на `acos(dot/…)` ([0, π], без ориентации)** —
сломаются трассировка (выбор min/max соседа) и все места, где различают
«слева/справа». Эквивалент в привычной записи: `ang = normalize2pi(atan2(dABx,
dABy) − atan2(dCDx, dCDy))`, что равно углу от CD к AB по часовой стрелке в
y-up системе.

## 6. compareContours — классификация пары контуров (8 исходов)

@50001. Вход — два незамкнутых контура; семантика исходов: `BELONG` — A внутри
B, `CONTAIN` — B внутри A, приставка `CONTACT_` — то же + общий кусок границы.
Полный алгоритм:

1. **Замыкание копий**: `contourA/B = [].concat(input)` + `push(first.clone())`
   (50003–50007). NB: при пустом входе `inputContourA[0]` бросит исключение —
   защиты нет.
2. **bbox-предфильтр** — `checkMinMaxOutside` @49767: min/max обоих контуров
   (null-точки пропускаются @49778, 49793), разнесённость bbox'ов со слаком
   L_EPS (проверки @49802–49805) → сразу `OUTSIDE` (вызов @50009).
3. **Поиск рёберных пересечений** (50011–50024): все пары рёбер через
   `lineIntersectLine(…, as_seg = true, vertices = false)` @50019 — общие
   вершины и T-стыки в вершину не считаются; любое внутреннее пересечение →
   `INTERSECT`. Коллинеарные наложения этот шаг **не** ловит (denom≈0 → null)
   — они уходят в `checkContact`.
4. **Классификация точек A против B** (50026–50060): для каждой вершины `A[i]`
   (@50031) и каждой **середины ребра** `midPt` (@50045–50047): если точка не на границе B
   (`pointOnContour`, B_EPS) — то `pointInContour` раскладывает её в
   `ptsAInB` / `ptsAOutB`. Как только замечены и внутренняя, и внешняя —
   `INTERSECT` (возможно при коллинеарном частичном наложении, которое шаг 3
   пропустил). Середины рёбер нужны, чтобы поймать ребро, у которого обе
   вершины на границе B, а середина — внутри/снаружи.
5. `contact = checkContact(A, B)` @50062 — один раз, до ветвления.
6. Если `ptsAInB` (и не было `ptsAOutB`) → `CONTACT_BELONG` при контакте,
   иначе `BELONG` (50064–50069).
7. Симметричная классификация B против A (50071–50104): вершины + середины,
   смешанность → `INTERSECT`.
8. Если `ptsBInA` → `CONTACT_CONTAIN` / `CONTAIN` (50106–50111).
9. Если `ptsAOutB && ptsBOutA` → `CONTACT` / `OUTSIDE` (50115–50120).
10. Если **все** точки обоих контуров легли на границу другого (все четыре
    флага false) → `COINCIDE` @50123.
11. Иначе (асимметричный остаток, напр. `ptsAOutB` без `ptsBOutA`) →
    `INTERSECT` @50125.

Замечания для порта:

- Сложность O(n·m) на рёберных парах + O((n+m)·m) на point-in-contour; грида
  и ускоряющих структур нет — контуры комнат маленькие.
- Все «на границе»-решения зависят от B_EPS, все «внутри»-решения — от
  ray casting без эпсилона: узкий зазор < B_EPS между контурами даст
  `COINCIDE`/`CONTACT_*` вместо `OUTSIDE` — для ядра это фича (склейка
  примыкающих комнат).
- Главные call sites: сборка дерева room→cover/outer-room
  (`comp == CONTAIN || CONTACT_CONTAIN || COINCIDE` @52254–52266), дыры в
  перекрытиях @54536, группировка связанных контуров (`comp != OUTSIDE` @54960),
  пересечение areas @59593, зон/чернового контура @65245, определение комнаты
  объекта @67414–67424.

### 6.1 compareContoursOnePoint — дешёвая аппроксимация

@49810 (комментарий в коде: «checks one point, returns BELONG, CONTAIN or
OUTSIDE»). Идёт по вершинам A до первой, **не лежащей** на границе B: если она
внутри — `BELONG`, иначе — break и симметричный проход по B: первая свободная
вершина B внутри A → `CONTAIN`, снаружи → `OUTSIDE`. Корректна только когда
уже известно, что контуры не пересекаются рёбрами (typical: дыры после
триангуляции). Если **все** вершины лежат на границах друг друга — функция
доходит до конца без `return` → **`undefined`** (совпадающие контуры). Call
sites: раскладка дыр по перекрытиям @60435, вложенность контуров зон @65308.

### 6.2 compareContoursByArea — вероятностный тест «а не пересекаются ли»

@49963. Несмотря на имя, возвращает только `INTERSECT` или `OUTSIDE`. Грид
10×10 по **bbox контура A** (`setSize = 10` @49965, точки
`minX + adx·i/10`, i = 0..9 — правая/верхняя кромки bbox не семплируются,
@49984); каждая точка классифицируется `pointInContour` по обоим контурам;
**хоть одна точка в обоих → `INTERSECT`** (49999). Это грубый area-overlap
тест: перекрытие мельче ~1% bbox или узкие «языки» между узлами сетки —
пропустит. Используется там, где ошибка не фатальна: сопоставление
старых/новых комнат и перекрытий при перестройке для переноса материалов
(@59695, @59862, @59983).

## 7. Контурные метрики и утилиты

- **contourArea** @49515: знаковая площадь трапецеидальной формулой
  `Σ (y_i + y_{i+1})/2 · (x_{i+1} − x_i)` (это ∮y dx). Знак: положительна при
  обходе **по часовой в y-up** (эквивалентно — против часовой в экранной y-down
  системе); большинство клиентов берут `Math.abs` (`contourValid` @50527,
  `sortByArea` @59495–59496).
- **contourPerim** @49528 — сумма евклидовых длин + замыкающее ребро.
- **contourValid** @50525: `|area| >= 50 && |area|/perim >= 1`
  (MIN_CONTOUR_AREA / MIN_SP_RATIO) — двойной анти-сливер: и абсолютный
  минимум площади, и «толщина» (для длинного узкого контура отношение S/P
  стремится к полуширине). Применяется в `clearContour` @50400 — контуры,
  не прошедшие фильтр, выбрасываются из результата триангуляции
  (`filterContours` @50913).
- **findMinMax** @50533 — bbox контура (без null-защиты, в отличие от
  `checkMinMaxOutside`).
- **roundCoord** @50554 — квантование координат до 0.001 (третий знак),
  закомментированные варианты показывают, что пробовали 1 и 0.1.
- **triangleIsNarrow** @49744: любая из трёх сторон короче `minLen = 0.1`
  **по манхэттену** → «узкий». Вместе с **triangleCenter** @49734 (центроид)
  используется при классификации групп триангуляции: центр берётся у первого
  не-узкого треугольника группы @51001–51016, чтобы `pointInContours` не
  ошибся на центроиде вырожденного треугольника, лежащем в B_EPS-зоне границы.
- **sortByArea** @59492–59521 (внутри `WC.Core`, не TR): компаратор по
  **убыванию** `|area|`; при разнице площадей < 10 tie-break — контур с
  флагом `outer` считается «меньше» (уходит в конец). Используется в
  `sortRooms` @59523 и (с `reverse()` — по возрастанию, комментарий «o -> O»)
  при раздаче дыр перекрытиям @60424–60426: маленькие контуры-обёртки
  обрабатываются раньше больших, чтобы дыра досталась ближайшему контейнеру.

## 9. Рекомендации для нашего порта (TS)

1. **Ориентационный тест — заменить на robust `orient2d`.**
   `segmentsIntersected` (голые float cross-products, порог 0),
   `lineIntersectLine` (порог `|denom| < L_EPS` не масштабируется с длиной
   отрезков) и LR-тест в `WC.rightOriented` @54929 — все сводимы к одному
   предикату ориентации. Брать `robust-predicates` (Shewchuk adaptive) вместо
   самописного — это единственное место, где точная арифметика реально нужна.
2. **Не терять двухуровневую систему эпсилонов.** L_EPS-identity работает
   только в связке с политикой «общие вершины делятся бит-в-бит» (снап в
   `lineIntersectLine` @49902–49903, дедуп @50939, `roundCoord` @50554).
   Если в порте вершины будут пересчитываться независимо — L_EPS = 1e-8
   начнёт «мигать», и первым сломается `checkContact` (коллинеарность с
   допуском 1e-8). Либо повторить снап-дисциплину, либо поднять допуск
   коллинеарности до B_EPS-уровня.
3. **`angleBetweenLines` портировать с точным сохранением контракта**
   (ориентированный, [0, 2π), от второй линии к первой, ноль — сонаправленность):
   на нём держатся выбор соседа в трассировке контуров (min/max угол) и
   mitering. Юнит-тесты на все четыре квадранта обязательны.
4. **`pointInContour`: заменить на стандартный robust ray casting** (например,
   чётность с полуоткрытыми рёбрами `[min, max)` по y) — но сохранить внешний
   контракт «граница отфильтровывается снаружи через `pointOnContour`».
   Текущая реализация имеет невылеченный риск деления `0/0` для вершин на
   вертикали `x = P.x` (см. §3) и три разных эпсилона в одной задаче.
5. **`compareContours` переносить как есть (структуру), но детерминированно:**
   шаг с серединами рёбер и порядок ветвления (INTERSECT → BELONG → CONTAIN →
   OUTSIDE/CONTACT → COINCIDE) — рабочая, проверенная временем машина; главное
   — не «оптимизировать» её в булеву алгебру на полигонах, потому что
   downstream-код (сборка дерева комнат) опирается именно на 8 исходов, включая
   CONTACT_*.
6. **Явные float-риски текущего кода, которые в порте надо закрыть:**
   - манхэттен-проверка принадлежности отрезку в `lineIntersectLine`
     @49907–49910 — анизотропна, заменить на параметрическую (t ∈ [0,1]);
   - хак `px = point.x` при `|dy| < B_EPS` в `projectionPointOnLine`
     @50139–50142 — заменить честной формулой проекции через dot product;
   - `perpendicularPoint` через наклон `k` — NaN при A==B и потеря точности
     при почти вертикальных рёбрах; заменить нормализованной нормалью
     `(dy, −dx)/len` с явным контрактом стороны;
   - `distanceBetweenPointAndLine` — NaN при вырожденной прямой;
   - `compareContoursByArea` — сетка 10×10 пропускает малые пересечения;
     если понадобится в порте, брать честный полигон-клиппинг для площади
     пересечения, а этот вариант оставить только для «best effort» переноса
     материалов.
7. **Единицы.** MIN_CONTOUR_AREA=50 и sortByArea eps=10 — абсолютные величины
   в единицах планировщика (см. deep-dive по координатной системе); при смене
   единиц в порте их нужно пересчитать, это не «магические» безразмерные
   константы.

## Confidence & gaps

**Высокая уверенность** (код прочитан построчно, формулы проверены руками):
все функции §2–§7, полный алгоритм `compareContours`, ориентированность и
диапазон `angleBetweenLines` (проверено подстановкой конкретных векторов),
сторона смещения `perpendicularPoint` (проверено на трёх направлениях),
знак `contourArea`.

**Gaps / что не проверялось:**

- **Единицы координат** предположены сантиметрами (тогда MIN_CONTOUR_AREA=50 —
  50 см², triangleIsNarrow 0.1 — 1 мм) — по этому файлу напрямую не
  верифицировал, сверять с deep-dive по координатам/масштабу.
- `pointInContour`: сценарий «ребро строго вертикально и проходит точно через
  `x = P.x`, вершины вне EPS-горизонтали луча» — теоретический риск `k = ±Inf`
  / NaN в смешанной ветке; не смог подтвердить достижимость на реальных данных
  (после `roundCoord` координаты квантованы, и совпадение `x` даёт скорее
  ветку «оба левее/правее»). Runtime-проверка не проводилась (только чтение).
- `compareContours` при вырожденных входах (контур из 1–2 точек, null внутри
  массива): `checkMinMaxOutside` null-точки терпит, но `push(first.clone())`
  и `lineIntersectLine` — нет; какие вызывающие гарантируют валидность входа —
  не прослеживал.
- Call site `pointOnLine(..., true)` @54427 с `accuracy = true` (коэрция в 1):
  намеренная «грубость» или баг — неизвестно; в порте требует явного решения.
- `compareContoursOnePoint` возвращает `undefined` для совпадающих контуров —
  оба call sites (@60435, @65308) сравнивают строго с CONTAIN/BELONG, так что
  undefined тихо трактуется как «не вложен»; последствия для UX (дыра ровно по
  контуру перекрытия) не исследовал.
- Поведение `TR.resplitSegments` @50272, `TR.clearContour` @50398 (кроме
  вызова `contourValid`) и всей триангуляционной обвязки (`TR.triangulate`
  @50632 и ниже) — вне рамок этого дока, см. deep-dive по триангуляции.
