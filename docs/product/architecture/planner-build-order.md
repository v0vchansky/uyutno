# Порядок реализации планера и карта ADR

> Часть каркаса планера. Продуктовая спека ([features/planner](../features/planner/README.md), разделы 01–12) заморожена (решение 2026-08-17): дальше идём итеративно — шаг → ADR на необратимые решения этого шага → код → тесты. Правки в спеку — только когда код доказал, что она нереализуема или противоречива, отдельным коммитом «спека ← код». Задачи заводятся на доске `docs/tasks/v0/` по одному шагу за раз.

## Принцип нарезки

Шаги идут **по слоям зависимостей и необратимости**, а не по разделам спеки: сначала то, что дорого переделать (модель документа, шина, undo, формат хранения), потом то, что на это навешивается. Каждый шаг заканчивается запускаемым результатом в пакете `packages/planner` (`@uyutno/planner`, ADR 0015), смонтированном в платформе, и зелёными слоями 1–2 из [testing-strategy](./testing-strategy.md). ADR пишется не «на шаг», а на необратимое решение внутри шага (критерии — [`docs/adr/README.md`](../../adr/README.md)); в шаге может быть 0–3 ADR.

## Правила против «замкнутого круга»

- **ADR решает ровно то, что нужно текущему шагу.** Всё, что всплывает про шаги N+1…10, — одной строкой в «Что важно знать» ADR или в список ниже, а не решается сейчас.
- **Одна сессия = один шаг** (или один ADR + его код). Бриф — строка таблицы + задача на доске.
- **DoD шага** — запускается + слои 1–2 зелёные; для шага 2 сразу golden-фикстуры.
- ADR B (модель) и ADR D (undo через снапшоты) связаны: модель обязана быть дёшево снапшотируемой — это условие фиксируется в B, детали D — во втором шаге.

## Отложенные технические вопросы

Парковка для вопросов, всплывших в ADR раньше своего шага. Формат: `- (шаг N, откуда) вопрос`.

- (шаг 2, аудит Q23) Debounce / Web Worker / инкрементальность пересборки геометрии — у roomtodo нет (полный синхронный recompute на коммит), в v0 не требуется; вернуться, если на больших планах упрёмся в производительность.
- (шаг 2/6, аудит Q2) Полигон-буль (Clipper2) — не заводим; юнион луток через общий `rebuildContours`. Вернуться, если полигон-буль понадобится ещё где-то (офсет стен по dd02).
- (шаг 3, аудит Q3/Q35) Стабильные id осей/граней между сохранениями **не требуются**: проёмы сохраняются мировыми координатами и пере-дропаются, данные комнат пере-привязываются по площади (как roomtodo). ADR B/F это не проектируют.
- (шаг 1, аудит Q17) Конструктор стен — отдельный Canvas2D-вьювер, но одна модель документа: ADR A фиксирует «вьюверы = проекции документа», без второй модели данных.
- (шаг 3, аудит Q14) Dirty-флаг автосейва — отдельный от истории; ADR D/F.
- (шаг 1, из ADR 0015) ~~Настройка пакета `packages/planner`~~ — **закрыто задачей 0047**: пакет `@uyutno/planner` заведён (`package.json`, `tsconfig`, заглушки слоёв, smoke-тест), `workspace:^` в платформе, корневой `.swcrc` + `swcRule` в webpack, SSR-allowlist `/^@uyutno\//`, свой `jest.config.mjs` поверх корневого базового, ESLint per-layer override, ADR 0007/0010/0013/0014/0015 поправлены по месту. Детали — [задача 0047](../../tasks/v0/0047-TASK-planner-package-skeleton.md).
- (шаг 1, из ADR 0015) Клиентского модуля `core` и логгера нет — DI-пропс `logger` планера нужна реализация на стороне платформы. Временно (задача 0047) — `console`-адаптер `plannerLogger` в `apps/platform/src/client/project/lib/plannerLogger.ts` с TODO; заменить на логгер `core`, когда появится.
- (шаг 2, из ADR 0015) Canvas2D-конструктор: свой render-on-demand или общий `RenderLoop`; где живут его дискретный зум/пан (в `Document.view.cameras` как вид или локально в проекции) — ADR E/G.
- (шаг 2, из ADR 0015/0016) ADR D: реализация `history` поверх замороженных immer-снимков — какие поддеревья снапшотят два контейнера (`floors[].layout` / `floors[].scene`, `Document.view` — нет), coalescing, лимит 100; удаление точки с общим id (стена+пол+зона) — проверка всех владельцев в транзакции; dirty-флаг игнорирует `view`.
- (шаг 2, из ADR 0016) ADR C: cuts — явные записи `cuts[]` `{ id, концы по id точек, материал }` (решение автора 2026-08-18, как roomtodo); правило владения записью cut на ребре, общем для двух касающихся зон, и удаление записи вместе с зоной без опоры.
- (шаг 3, из ADR 0015/0016) ADR F: форма пропа `storage: { load, save }`; zod-схема формата как контракт `load(save(x))==x`; поведение парсера при отсутствующем id (Q11); место `Document.view` (камеры) в сейве и что считается «изменением документа» для dirty-флага (Q14).
- (шаг 4, из ADR 0015/0016) ADR G: маппинг `(x,y)→(x,h,−y)` и градусы→радианы — одно место в проекции; гранулярность ребилда по `document:changed` (полный memoized diff vs payload «что изменилось»); мемоизация производного по ссылочной идентичности узлов документа; шаг 1 просто перестраивает сцену целиком.
- (шаг 5, из ADR 0015/0016) ADR H/I: схема `items` по `kind` (`model|door|window|opening|poster|carpet`), поля `scale/flip/materials`, ссылка `catalogId`; неймспейс/событие `selection` — что из state выделения живёт в фасаде, что в проекции.
- (шаг 7, из ADR 0016) ADR J: схема ключей `finishes` (`SurfaceKey`: пара id точек грани, id cover/room/area, id записи `cuts[]` для cut); наследование материала грани при разрезании ребра точкой (T-стык); углы в документе — градусы, включая поворот текстур (ADR 0016; спека 05 приведена в 0046), конвертация на границе; единица хранения смещения текстуры (спека 05: «пиксели при 100 px/м» vs «см — единственная внутренняя единица», ADR 0016 B1) — решить здесь.
- (шаг 9, из ADR 0015) Превью проекта/каталога через render target единственного `WebGLRenderer` — механика offscreen-рендера (ADR G/H).
- (шаг 10, из ADR 0016) ADR K: форма `underlay` (ссылка на blob + трансформ), что из неё входит в документ.
