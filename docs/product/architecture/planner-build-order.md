# Порядок реализации планера и карта ADR

> Часть каркаса планера. Продуктовая спека ([features/planner](../features/planner/README.md), разделы 01–12) заморожена (решение 2026-08-17): дальше идём итеративно — шаг → ADR на необратимые решения этого шага → код → тесты. Правки в спеку — только когда код доказал, что она нереализуема или противоречива, отдельным коммитом «спека ← код». Задачи заводятся на доске `docs/tasks/v0/` по одному шагу за раз.

## Принцип нарезки

Шаги идут **по слоям зависимостей и необратимости**, а не по разделам спеки: сначала то, что дорого переделать (модель документа, шина, undo, формат хранения), потом то, что на это навешивается. Каждый шаг заканчивается запускаемым результатом в пакете `packages/planner` (`@uyutno/planner`, ADR 0015), смонтированном в платформе, и зелёными слоями 1–2 из [testing-strategy](./testing-strategy.md). ADR пишется не «на шаг», а на необратимое решение внутри шага (критерии — [`docs/adr/README.md`](../../adr/README.md)); в шаге может быть 0–3 ADR.

## Правила против «замкнутого круга»

- **ADR решает ровно то, что нужно текущему шагу.** Всё, что всплывает про шаги N+1…10, — одной строкой в «Что важно знать» ADR или в список ниже, а не решается сейчас.
- **Одна сессия = один шаг** (или один ADR + его код). Бриф — строка таблицы + задача на доске.
- **DoD шага** — запускается + слои 1–2 зелёные; для шага 2 сразу golden-фикстуры.
- ADR B (модель) и ADR D (undo через снапшоты) связаны: модель обязана быть дёшево снапшотируемой — это условие фиксируется в B, детали D — во втором шаге.

## Отложенные технические вопросы

Парковка для вопросов, всплывших в ADR раньше своего шага. Формат: `- (шаг N, откуда) вопрос`.

- (шаг 3, подготовка 2026-08-20) **ADR F заведён черновиком — [ADR 0021](../../adr/0021-hranenie-dokumenta-planera-i-format-sohraneniya.md), статус `Предложено`, решения не приняты.** Внутри — 15 открытых вопросов шага 3 (хранилище документа, форма API, конверт сейва, zod-схема и её владелец, forward-compat парсера, last-write-wins, форма пропа `storage`, автосейв, лимиты, черновик и демо, превью, Save As, fit камеры, фикстуры, сироты `rooms[]`) с рекомендациями и метками срочности, плюс предлагаемая декомпозиция (эпик `0066` + задачи `0067`–`0077`, задачи ещё не заведены). Строки парковки, адресованные ADR F, закрываются его принятием, а не по одной.

- (шаг 2, аудит Q23) ~~Debounce / Web Worker / инкрементальность пересборки геометрии~~ — **закрыто ADR 0017 (C11)**: полный синхронный recompute на коммит, без индексов/debounce/worker; туда же двойная триангуляция (normalize на черновике + rebuild на снимке). Вернуться, если на больших планах упрёмся в производительность.

- (шаг 4, из задачи [0073](../../tasks/v0/0073-TASK-planner-normalize-phase1-idempotency.md)) **Идемпотентность фазы (1) держится потолком проходов, а не доказательством.** `normalize` крутит трассировку контуров до неподвижной точки с потолком `MAX_CONTOUR_PASSES = 4`; не сошлось → `warn`, хранимое остаётся как есть, то есть документ остаётся неидемпотентным ровно как до фикса (следствие для restore undo/redo — ADR 0018 D3). Сходимость не доказана, есть эмпирика: на 5000 сгенерированных сессий срывов нет, четвёртый проход не понадобился ни разу. **Тревожная кнопка — этот `warn` в реальной работе.** Та же оговорка действует для полов (`cover rebuild did not converge`), и обе ветки отказа тестами не покрыты — сконструировать вход, требующий больше проходов, не удалось.

- (шаг 4, из задачи [0073](../../tasks/v0/0073-TASK-planner-normalize-phase1-idempotency.md)) **Структурная альтернатива циклу не рассматривалась.** Корень дефекта — приблизительный предикат «вершина лежит на ребре»: промах в 3·10⁻⁵ см делает точку одновременно «на ребре» для одного прогона и «не на ребре» для другого. Кандидаты снять класс проблемы целиком: (а) квантование координат на целочисленную сетку + точные предикаты поверх неё — тогда идемпотентность становится свойством по построению (квантование числится среди решений ADR 0016, доехало ли оно до кода — проверяется); (б) не подавать упрощённый `clearContour`'ом обвод на вход следующей пересборки, чтобы круг не замыкался. Момент решать — до того, как сверху лягут меши, материалы и проёмы; после шага 7 цена вырастет на порядок. Вторая цена текущего решения: второй проход триангуляции нужен 786 документам из 800, то есть удвоение стоимости коммита — на нашем масштабе миллисекунды, мерить осмысленно на шаге 4 вместе с пересборкой мешей.
- (шаг 2/6, аудит Q2) ~~Полигон-буль (Clipper2) — не заводим; юнион луток через общий `rebuildContours`~~ — **закрыто ADR 0017 (C2/C6)**: `rebuildContours` — публичная чистая функция ядра с проверяемым числом внешних контуров. Вернуться, если полигон-буль понадобится ещё где-то.
- (шаг 2b, из ADR 0017 / эпик 0050) ~~Размещение в build-order полов, зон, cuts, плинтусов, потолков~~ — **закрыто решением автора 2026-08-19**: строка «2b» в таблице шагов между 2 и 3; инструменты «Зона» и «Рисование пола» вынесены оттуда на шаг 7 решением автора 2026-08-20 (см. «Осознанные переносы»).
- (шаг 2b, из ADR 0017) ~~Cut-пары зон — fixed-рёбра триангуляции, делят треугольники комнаты, но не порождают новых комнат: как совместить с критерием «комната = не-fill группа без ребра выпуклой оболочки»~~ — **закрыто задачей 0068**: интерьерное cut-ребро (вдоль ребра зоны и не вдоль грани контура) — не граница комнаты и не барьер группировки; разделённые только им не-fill группы склеиваются обратно, склейка — комната лишь когда критерий проходит каждая часть; в обводе такие рёбра игнорируются, ребро зоны «по стене» остаётся барьером.
