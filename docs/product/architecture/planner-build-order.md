# Порядок реализации планера и карта ADR

> Часть каркаса планера. Продуктовая спека ([features/planner](../features/planner/README.md), разделы 01–12) заморожена (решение 2026-08-17): дальше идём итеративно — шаг → ADR на необратимые решения этого шага → код → тесты. Правки в спеку — только когда код доказал, что она нереализуема или противоречива, отдельным коммитом «спека ← код». Задачи заводятся на доске `docs/tasks/v0/` по одному шагу за раз.

## Принцип нарезки

Шаги идут **по слоям зависимостей и необратимости**, а не по разделам спеки: сначала то, что дорого переделать (модель документа, шина, undo, формат хранения), потом то, что на это навешивается. Каждый шаг заканчивается запускаемым результатом в `apps/platform/src/client/planner` и зелёными слоями 1–2 из [testing-strategy](./testing-strategy.md). ADR пишется не «на шаг», а на необратимое решение внутри шага (критерии — [`docs/adr/README.md`](../../adr/README.md)); в шаге может быть 0–3 ADR.

## Правила против «замкнутого круга»

- **ADR решает ровно то, что нужно текущему шагу.** Всё, что всплывает про шаги N+1…10, — одной строкой в «Что важно знать» ADR или в список ниже, а не решается сейчас.
- **Одна сессия = один шаг** (или один ADR + его код). Бриф — строка таблицы + задача на доске.
- **DoD шага** — запускается + слои 1–2 зелёные; для шага 2 сразу golden-фикстуры.
- ADR B (модель) и ADR D (undo через снапшоты) связаны: модель обязана быть дёшево снапшотируемой — это условие фиксируется в B, детали D — во втором шаге.

## Отложенные технические вопросы

Парковка для вопросов, всплывших в ADR раньше своего шага. Формат: `- (шаг N, откуда) вопрос`.

- (шаг 2, аудит Q23) Debounce / Web Worker / инкрементальность пересборки геометрии — у roomtodo нет (полный синхронный recompute на коммит), в v0 не требуется; вернуться, если на больших планах упрёмся в производительность.
- (шаг 2/6, аудит Q2) Полигон-буль (Clipper2) — не заводим; юнион луток через общий `rebuildContours`. Вернуться, если полигон-буль понадобится ещё где-то (офсет стен по dd02).
- (шаг 3, аудит Q3/Q35) Стабильные id осей/граней между сохранениями **не требуются**: проёмы сохраняются мировыми координатами и пере-дропаются, данные комнат пере-привязываются по площади (как roomtodo). ADR B/F это не проектируют.
- (шаг 1, аудит Q17) Конструктор стен — отдельный Canvas2D-вьювер, но одна модель документа: ADR A фиксирует «вьюверы = проекции документа», без второй модели данных.
- (шаг 3, аудит Q14) Dirty-флаг автосейва — отдельный от истории; ADR D/F.
