## Описание

Написать два ADR по шагу 1 планера и открыть их на обсуждение. Кода в этой задаче нет — только `docs/adr/0015-*.md`, `docs/adr/0016-*.md`, обновление индекса ADR и парковка отложенных вопросов. Это самые дорогие для отката решения планера: от них зависит всё остальное (undo, формат сохранения, проекция в Three, каталог, материалы).

Это бриф сессии: читать целиком перед стартом, работать по нему, не расширять скоуп.

### Что решаем

**ADR 0015 — Архитектура движка планера: слои, фасад, мост с React** (кандидат A):

1. **Слои и направление импортов**: документ + чистая геометрия (plain data, без Three/DOM) → движок-фасад (команды, будущие инструменты, история, шина событий) → проекция в Three (сцена, рендер, камеры) → React-UI (панели, инспектор). Кто кого может импортировать; энфорс через `no-restricted-imports` per-directory, как в ADR 0007. Именование главного объекта — по конвенции `Manager`, не `Service` (см. `apps/platform/CLAUDE.md`).
2. **Ядро + сменный UI-скин.** Планер — ядро; React-UI — один из возможных скинов. Критерий: UI не владеет состоянием документа и общается с ядром **только** через публичный API фасада + события. Публичный API нарезать по зонам ответственности неймспейсами (например `document`, `view`, `tools`, `history`, `selection` — состав определить; конкурент нарезал `scene/view3d/view2d/viewWalk/constr/units/renders`, см. competitor-mechanics/00 «Архитектура»). Правило: React никогда не мутирует документ напрямую — только через команды фасада.
3. **Отдельный пакет — сейчас или потом.** ADR 0007 говорит «в v1 переезжает в пакет». Решить здесь: заводить `packages/planner-core` (ядро без React) физически уже сейчас или держать в `apps/platform/src/client/planner/` со структурой «как пакет» и границей на ESLint. Учесть: сборка webpack + Jest в монорепе (ADR 0002), стоимость переезда позже, «UI как скин» проще доказывается отдельным пакетом.
4. **Мост движок ↔ React**: как React читает состояние движка и подписывается на изменения. Выбрать один механизм (`useSyncExternalStore` над фасадом / zustand / только шина событий) и объяснить, почему не Redux-обвязка конкурента (competitor-mechanics/15).
5. **Шина событий**: типизированная, минимальный набор событий для шага 1 (`document:changed`, `view:changed`, …) с правилом расширения; готовая либа или `EventTarget` — обосновать.
6. **Стек зависимостей планера для шага 1** — одной таблицей: Three r185 (дано), генератор id, immutable-обновления, шина, состояние для React — что берём и почему готовое, а не своё. Геометрические либы (`cdt2d`, `clean-pslg` и т.п.) здесь **не** решаются — это ADR C, когда они реально нужны.
7. **Инициализация и жизненный цикл**: как платформа создаёт планер (фабрика/класс `PlannerManager` + React-обёртка), порядок бутстрапа (документ → движок → проекция → UI), mount/dispose (renderer, геометрии, материалы, ResizeObserver, подписки). **Render-on-demand**: `invalidate()` → конечное число кадров и сон; ровно один `WebGLRenderer` на планер. Как это проверяется perf/leak-гвардом из testing-strategy.
8. **DI-контракт с платформой**: планер не импортирует `auth`/`common`/`project` (ADR 0007). Что он получает снаружи — минимум для шага 1 (например, `logger`, идентификатор проекта, колбэки загрузки/сохранения документа как интерфейс на будущее). Не проектировать больше, чем нужно шагу 1 и очевидно шагу 3.
9. **Тестируемость как ограничение**: слои документ/геометрия/фасад тестируются в Jest без Three (testing-strategy, оговорка про ESM Three); всё, что трогает Three, — только слой проекции. Правило покрытия — «вся математика и все ветки, не только happy path» (см. testing-strategy, «Что считается покрытым»).
10. **Раскладка папок** внутри модуля/пакета — коротко, как в ADR 0007 «Layout».

**ADR 0016 — Модель документа планера** (кандидат B):

1. **Единицы и координаты**: см — единственная внутренняя единица; квантование координат до 0.001 при снапе; плоскость плана `(x, y)` → мир Three `(x, height, −y)`, `+Y` мира — вверх; углы — градусы в UI, радианы внутри (или наоборот — решить).
2. **Схема идентификаторов**: стабильные строковые id у всех хранимых сущностей (готовая либа, не свой генератор); ссылки только по id, никогда по индексу массива.
3. **Contour-first дерево документа**: `Document { version, settings, floors: Floor[] }`, что живёт во `Floor` (контуры с точками; заготовки-«места» под проёмы, мебель, материалы — только позиция в дереве и принцип привязки, без детальной схемы). Явный список: **что хранится** vs **что выводится** (стены как физические тела, комнаты, грани, оси — выводятся и не сериализуются).
4. **Стабильная адресация производных сущностей** — принцип, не детали: как проём (шаг 6) и материал (шаг 7) ссылаются на стену/грань/комнату, которые пересоздаются на каждом rebuild. Достаточно зафиксировать правило (например, детерминированные id производных из id порождающих точек контура + сторона) и записать, что детали дорешиваются в ADR C/J.
5. **Snapshot-friendly структура**: документ — plain JSON-сериализуемые данные, immutable-обновления со структурным разделением (готовая либа типа immer или ручная дисциплина — выбрать), чтобы undo (ADR D, шаг 2) мог хранить снапшот как ссылку. Требование к производному состоянию: не в документе, memoized по ссылке.
6. **Поле `version`** есть с первого дня; политика миграций — в ADR F (шаг 3), здесь только факт наличия и правило «миграция — не история».
7. **Multi-floor**: `floors[]` в модели, в UI один этаж (зафиксировано в спеке) — как это отражено (активный этаж — состояние UI/движка, не документа).

### Что уже решено и не пересматривается

- Голый Three.js r185, без react-three-fiber — ADR 0003; карта отличий r185 — `docs/product/architecture/threejs-r185-migration.md`.
- Планер — изолированный модуль без импортов из бизнес-модулей, всё внешнее через DI-пропсы, в v1 переезжает в пакет — ADR 0007.
- Jest + core без Three, слои тестов и DoD — `docs/product/architecture/testing-strategy.md`.
- Шесть принципов и единицы из `features/planner/README.md` (контур-first, одна модель, один автомат, snap-first, реалтайм-rebuild, три вида — один документ; 1 см = 1 юнит, константы `SNAP_DIST=10`, `MIN_WALL_LENGTH=15`, `DEFAULT_WALL_WIDTH=10`, `MAX_WALL_WIDTH=80`, `DEFAULT_WALL_HEIGHT=280`).
- Undo: in-memory снапшоты, coalescing по mouseUp/blur, два контейнера, глубина 100 — `features/planner/09-undo-redo.md`. Здесь это только ограничение на модель (п. B5), сам undo — ADR D.
- Save: last-write-wins, миграция формата — silent — `features/planner/10-save-load.md`. Здесь только поле `version` (п. B6).
- Custom uploads, multi-floor UI, корзина — вне v0 (спека/бэклог).

### Метод работы

- Режим оркестратора (пользователь явно просил делать через субагентов): черновики ADR 0015 и 0016 пишут два параллельных субагента по этому брифу; третий — критик на соответствие `docs/adr/README.md` (три секции, один экран, без «Альтернатив»/«Плюсов-минусов»/«Ссылок»), принципам `features/planner/README.md` и решениям аудита; оркестратор сводит и отдаёт автору список развилок. Чтение больших референсных доков — субагентам с конкретными вопросами.
- **Входы, которых не было при написании этого брифа (обязательно):** `docs/product/architecture/competitor-practices-audit.md` — блок «Сквозные архитектурные практики» и таблица «Решения автора (2026-08-17)»; парковка в `planner-build-order.md`. Ключевые решения, влияющие на A/B: конструктор стен — отдельный Canvas2D-вьювер, но **одна модель документа** (все вьюверы — проекции документа); проёмы сохраняются мировыми координатами и пере-дропаются при загрузке, стабильные id осей/граней **не требуются**; `changed`-флаги roomtodo — маркер материала для undo, не гранулярность ребилда (не проектировать «changed-флаги как у конкурента»); recompute синхронный; dirty-флаг автосейва отдельный от истории. Спорные фактические утверждения про конкурента (номера строк, поведение) — не тащить в ADR без проверки; ADR ссылается на наши доки, а не на `plannercore.js`.
- Не выдумывать альтернативы «для галочки»: в «Почему» — только реально отсечённые варианты одной строкой («X отсекается, потому что Y»).
- Библиотеки — готовые (id-генератор, immutable-обновления, шина), не самописные; выбор — с одной строкой обоснования.
- Допустим одноразовый спайк в scratchpad для проверки моста React↔движок или иммутабельного обновления — в репозиторий не коммитить.
- Если решение упирается в вопрос, на который может ответить только автор (продуктовый или архитектурный), — задать его в конце сессии списком, а не блокироваться на первом же.
