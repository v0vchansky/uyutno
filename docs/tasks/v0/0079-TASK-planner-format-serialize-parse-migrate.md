## Описание

Вторая «нижняя» задача шага 3, независимая от `0078`. Даёт формату сейва единственный источник правды — в пакете планера, **и такой, который может импортировать серверный процесс**.

Сегодня `PlannerDocument` — просто TypeScript-интерфейс: `DOCUMENT_FORMAT = 'uyutno.planner'` и `DOCUMENT_VERSION = 1` объявлены в `document/PlannerDocument.ts`, а `document.load()` проверяет только совпадение `format` и `version` — никакого разбора чужого JSON нет. Задача заводит настоящий разбор.

### Узкий вход `@uyutno/planner/format`

Новый каталог `packages/planner/src/format/` и вторая точка экспорта в `packages/planner/package.json`:

```
"exports": {
  ".": "./src/index.ts",
  "./format": "./src/format/index.ts"
}
```

**Это требование к структуре пакета, а не пожелание** (ADR 0021, «Что важно знать»): вход импортирует сервер, и если через него протечёт `three` или слой `projection`, половина редактора уедет в серверный процесс. Отсюда:

- `format/` — самый нижний слой пакета: `three`, `react`, `engine/`, `projection/`, `ui/` не импортирует **ни в каком виде**, включая транзитивный. Из `document/` берёт **только типы** (`import type`) — они стираются компилятором.
- Правило дописывается в `plannerLayerConfigs` (`eslint.config.mjs`) отдельным override для `packages/planner/src/format/**` — по образцу существующих слоёв: `plannerNoPlatform`, `plannerNoThree`, `plannerNoReact`, `plannerNoUpperLayers(['engine', 'projection', 'ui'])`.
- Линтера мало: он видит только статические импорты в исходниках. Нужен **тест-гвард**, который обходит граф реальных импортов от `src/format/index.ts` и падает, если в нём появился `three`, `react` или файл вышележащего слоя. Способ на выбор исполнителя (обход `import`-ов по AST, `madge`-подобный самописный обход, снапшот `require.cache` после изоляции модуля) — важно, что он ловит и транзитивную протечку.

### Схема, версия и цепочка миграций

- **`zod` — новая зависимость `packages/planner`** (в платформе стоит `^4.4.3`, в пакете нет). Ставить ту же мажорную версию, иначе в одном процессе окажутся два несовместимых zod.
- Схема описывает **конверт целиком**: `format` (литерал `'uyutno.planner'`), `version` (целое > 0), `settings`, `view` (с камерами `plan`/`orbit`/`walk`), `floors` (`layout` — точки, контуры, полы, зоны, cuts, комнаты; `scene` — items, rulers, hidden). Метаданных проекта (`name`, даты) в конверте нет — это колонки `projects`. Камеры конструктора нет — она в документ не пишется (ADR 0020).
- **Текущая версия выводится из длины цепочки миграций, а не пишется руками.** Шаг `i` цепочки поднимает документ с версии `i` на `i + 1`, поэтому `DOCUMENT_VERSION = MIGRATIONS.length + 1`; в v0 цепочка пуста и версия равна `1` — как сейчас. Смысл правила (ADR 0021): нельзя поднять номер, забыв шаг, и нельзя написать шаг, забыв номер. Константа переезжает в `format/` (рядом с цепочкой), `document/PlannerDocument.ts` импортирует её оттуда; `format/` из `document/` тянет только типы, так что runtime-цикла не возникает.
- `migrate(raw: unknown)` заводится **сразу, с пустой цепочкой**, и возвращает признак изменения — `{ document, changed: boolean }` или эквивалент. Признак нужен серверу (`0080`): по нему он решает, перезаписывать ли колонку. `migrate` обязана быть **детерминированной и переживать повтор** — на этом держится безвредность гонки двух одновременных чтений.
- Версия новее поддерживаемой → ошибка `unsupported-version` (клиент покажет «перезагрузите страницу», UI — `0085`). Отсутствие `format`/`version`/`floors` → `corrupt` («битый проект» спеки 10). Нечитаемый JSON → тоже `corrupt`.
- Битые id-ссылки (стена → отсутствующая точка, комната/пол → отсутствующая точка) — **не ошибка формата**: парсер их пропускает молча, дальше отрабатывает обычная пересборка. Битым проектом такое не считается (спека 10, «Ошибочные сценарии»).

### Forward-compat: незнакомые поля обязаны переживать круг `parse` → `serialize`

Внутри поддерживаемой версии старый клиент может встретить документ, записанный более новым бандлом с необязательным полем, которого он не знает. Такое поле обязано **дожить до обратной записи**: добавление необязательного поля версию не двигает (иначе цепочка забьётся пустыми шагами уже на шагах 5–7), и вся конструкция держится на сквозном пробросе. Обещание **сужено решением автора 2026-08-21**: оно распространяется на записи, которые пересборка не создаёт заново; в записи, которые `normalize` собирает литералом из известных полей, незнакомое не переносится (ADR 0021, «Что важно знать»). Эта задача отвечает за круг `parse` → `serialize` — он сужением не задет.

**Zod по умолчанию делает обратное — молча срезает неизвестные ключи** (в v4 `z.object` строгий к лишним ключам на выходе; сквозной проброс — `z.looseObject` / `.loose()`). Поэтому проброс задаётся **явно** и покрывается **отдельным тестом**, иначе обещание forward-compat не работает и старый клиент обстругивает документ нового. Тест проверяет проброс на каждом уровне конверта, где поле может появиться: корень, `settings`, `view`, `floor`, записи `layout` (точка, контур, пол, зона, комната), записи `scene`.

Отсутствующие **косметические** поля, наоборот, дефолтятся схемой (спека 10: «неизвестные/новые версии пытаются открыться в режиме совместимости»).

### `serialize` / `parse` и идемпотентность пути загрузки

- `serialize(document): string` — детерминированный JSON: одинаковый документ даёт байт в байт одинаковую строку (от этого зависит diff-guard черновика в `0083`).
- `parse(raw: unknown): Result<PlannerDocument, ParseError>` — типизированный `Result` пакета, исключений наружу нет (ADR 0015 A2).
- **Идемпотентность на пути загрузки.** Путь загрузки — наш **единственный вход без квантования** (парковка build-order, строка «(шаг 3, из разведки 2026-08-20 → ADR F)»; у конкурента этот вход квантован, `plannercore.js:53871`). Требование ADR: **квантовать и проверить**. Значит `parse` прогоняет координаты через тот же `quantize`, что и остальной документ, а тест утверждает, что `normalize` после `parse` неподвижен — `normalize(parse(serialize(x)))` равен `normalize` от него же ещё раз. Это тот же круг пересборки, который дал дефект задачи [0073](0073-TASK-planner-normalize-phase1-idempotency.md), и проверять его надо **до** того, как парсером начнут пользоваться, а не после.
- **Property-тест `load(save(x)) == x`** на `fast-check` (уже в devDependencies пакета, инфраструктуры не требует), с фиксированным seed. Генератор документов — существующий `planBuilder`/арбитрары property-тестов шага 2b, расширенные полями `view` и `scene`.

Не в задаче: эндпоинты и серверная миграция на чтении (`0080`); `storage`-проп и вызовы `parse`/`serialize` из платформы (`0081`); фикстуры в формате сейва (`0086`).

## Заметки

- **Версия формата не привязана к версии npm-пакета.** Пакет версионируется по своим причинам (рефакторинги, багфиксы, инструменты); привязка заставляла бы сервер мигрировать документы на каждом релизе, а проверку «версия не ниже сохранённой» — отвергать честные сохранения из старых вкладок. Число в системе ровно одно, клиент и сервер берут его из одного модуля.
- **Что считается несовместимым изменением:** только то, после чего старые данные нельзя прочитать правильно, не переписав их — переименование, удаление, смена смысла поля. Добавление необязательного поля версию **не двигает**.
- **Поднятие версии обязано включать переснятие golden-фикстур** (ADR 0021, «Смежное»). Это пункт чек-листа той задачи, которая двинет формат; механику фикстур в формате сейва заводит `0086`.
- **Клиентский `migrate` тоже нужен** — черновик демо живёт в `localStorage` и сервера не видит (`0083`). Код один и тот же, точек вызова две.
- **Подложку растрового плана конверт не несёт** (ADR 0021): поле зарезервировано, лимит размера считается по документу без неё. Спека 11 в нынешней редакции требует обратного — расхождение осознанное и живёт до шага 10. В схеме этой задачи подложки быть не должно.
- **Записи-сироты `rooms[]` в v0 не чистим** — запись весит сотни байт, для заметного вклада нужны тысячи циклов. Парсеру их фильтровать не надо.

### Что уточнено по ходу реализации

- **`DOCUMENT_VERSION = MIGRATIONS.length + 1` — уточнение буквы ADR 0021.** ADR формулирует правило как «текущая версия = длина цепочки»; буквально это дало бы `0` на пустой цепочке, тогда как первая версия формата — `1` (ADR 0016 B6), и именно `1` лежит во всём, что код уже пишет. Смысл правила — связать номер с цепочкой намертво — сохранён: шаг `i` мигрирует `i → i + 1`, версий на единицу больше, чем переходов между ними. Реализовано через `versionOf(migrations)`, чтобы формула была одна и проверялась тестом на фиктивной цепочке.
- **Противоречие внутри ADR 0021 по сиротам `rooms[]` — разрешено в пользу «не чистим».** В «Версиях, парсере, миграциях» ADR перечисляет «комната/пол → отсутствующая точка» среди битых ссылок, которые парсер пропускает; в «Смежном» и в «Заметках» этой задачи — прямо обратное: сироты `rooms[]` не чистим. Победило второе, и не по старшинству, а по трём причинам: `anchor` по определению устаревающая подсказка пере-привязки (ADR 0016 Q3), а не геометрия; запись несёт введённые пользователем атрибуты (имя, высота потолка), и её выброс — потеря данных; и главное — фильтрация **ломает идемпотентность пути загрузки**, что поймал property-тест `engine/loadPathIdempotency.test.ts` (`normalize` штатно оставляет запись с якорем на точках, которые сам же пересобрал). Контуры, полы, зоны и вырезы с битой ссылкой по-прежнему выбрасываются целиком. Если ADR будут править — править надо перечисление, а не «Смежное».
- **«Из `document/` только типы» и «`parse` квантует тем же `quantize`» — требования этой задачи, несовместимые буквально.** `quantize` — рантайм-функция из `document/quantize.ts`; взять её «только типом» нельзя. Выполнен смысл: `format/` тянет из `document/` ровно три модуля, и все три сами ничего не тянут (`quantize.ts` вообще без импортов, `Result.ts` без импортов, `PlannerDocument.ts` — только типы и константы). Это утверждение не на словах: гвард `format/importGraph.test.ts` фиксирует список из трёх файлов и падает на четвёртом.
- **Гвард различает рантайм-граф и граф ссылок.** `import type` стирается компилятором, поэтому в рантайм-граф не входит; на нём проверяется «ни `three`, ни `react`, ни лишних пакетов» (в рантайме вход тянет ровно `zod`). Граф ссылок включает типовые и на нём проверяется дисциплина слоёв — `engine/`/`projection/`/`ui/` нет даже в типовой ссылке. Различать пришлось не из аккуратности: `PlannerDocument.ts` типом ссылается на `document/id.ts`, а тот тянет `uuidv7`, — и записать `uuidv7` в рантайм-зависимости серверного входа было бы неправдой.
- **Квантуются координаты плана, а не всё подряд:** точки, линейки и предметы сцены (`x`, `y`, `elevation`). Углы, зумы и высоты (`wallHeight`, `ceilingHeight`, `Area.height`) координатами не являются, сетка 0.001 см к ним не относится, и движок их не квантует тоже.
- **`format/` — сосед `document/`, а не слой над ним.** `document/PlannerDocument.ts` берёт из `format/version` номер версии (как и требует задача), значит `format` **не** дописан в список вышележащих слоёв для `document/` в `eslint.config.mjs`. Runtime-цикла нет: `format/version.ts` безимпортный.

### Перестановки в пакете, которых потребовал чистый вход

Обе — механические, форму документа и публичный API пакета не меняют:

- **`engine/Result.ts` → `document/Result.ts`.** `parse` обязан возвращать `Result` пакета, а `format/` не видит `engine/` ни в каком виде. Файл безимпортный (9 строк), переезд вниз ничего не тащит; поправлены пути импорта в ~20 файлах, `src/index.ts` реэкспортирует по новому пути.
- **`createEmptyFloor`/`createEmptyDocument` → `document/createEmptyDocument.ts`.** Это единственное место формы документа, которому нужен рантайм-генератор id. Пока они лежали в `PlannerDocument.ts`, любой value-импорт констант оттуда (`UNITS`, `VIEW_KINDS`, дефолтные камеры — они нужны схеме) утягивал в серверный процесс `uuidv7`. После выноса `PlannerDocument.ts` — чистые типы и константы.

Заодно заведён `SCENE_ITEM_KINDS` (был только тип-объединение `SceneItemKind`) — схеме нужен рантайм-список, как у `UNITS`/`VIEW_KINDS`/`CONTOUR_KINDS`.

### Приёмка, которую не отметил

1. **«Импорт из платформы (и клиента, и сервера)»** — не проверено буквально: `apps/platform/**` в этот заход не трогался (там параллельно шла задача `0078`), и ни одного импорта `@uyutno/planner/format` в платформе пока не написано. Проверено то, что от этой задачи зависит: точка экспорта в `package.json` заведена, и резолвер Node из каталога платформы отдаёт `@uyutno/planner/format` → `packages/planner/src/format/index.ts`, а глубокий путь `@uyutno/planner/src/engine/rebuild` — `ERR_PACKAGE_PATH_NOT_EXPORTED`. Живой импорт из клиента и сервера появится в `0081`, там же критерий и закрывается. Оговорка про «ничего сверх»: вход экспортирует ещё и **типы** документа, `Id` и `Result` — без них вызвать `parse`/`serialize` из платформы нельзя; в рантайм они не попадают.
2. **«`version` меньше текущей (уходит в `migrate`)»** — ветки в v0 не существует: цепочка пуста, текущая версия `1`, а `version < 1` отсекается как `corrupt` ещё на конверте. Механика самого перехода покрыта на **фиктивной** цепочке (`migrateWith` в `format/migrate.test.ts`): один шаг, три шага подряд, повтор на уже мигрированном, версия новее цепочки. Остальные семь веток критерия покрыты через `parse` дословно. Критерий закроется сам, когда появится вторая версия формата.

Обе галочки, которые всё же поставил при незавершённом PR (`zod`/лок-файл и «Prettier чист; ровно один PR»), отмечены по существу работы: лок-файл обновлён, Prettier чист, изменения — ровно на одну задачу. Коммит и PR делает автор.

### Прочее

- **Тест идемпотентности пути загрузки живёт в `engine/`, а не в `format/`** (`engine/loadPathIdempotency.test.ts`): `normalize` — движковый, и override линтера запрещает его импорт в файлах `format/**`, включая тесты.
- **Golden-планы (`document/geometry/fixtures/plan-*.json`, поле `input`) — уже конверты сейва** с `format`/`version`, поэтому прогонять их через `parse`/`serialize` можно прямо сейчас, не дожидаясь `0086`. На них проверяется **неподвижность** круга, а не дословное `load(save(x)) == x`: часть фикстур писалась без необязательных секций (`covers`/`areas`/`cuts`/`rooms`), и схема их дефолтит — штатный «режим совместимости» спеки 10. Дословное равенство держит property-тест на полных документах.
- **Арбитрарий документа — `document/testing/arbDocument.ts`**, рядом с `planBuilder`: план шага 2b плюс `settings`, `view` с тремя камерами и `scene`. Общий с `engine/`, поэтому лежит в `document/`, а не в тестах формата.
- **`serialize` сортирует ключи объектов** (порядок элементов массивов — данные и сохраняется). Одного `JSON.stringify` мало: `layout.points` — `Record<Id, Point>` с порядком вставки по правкам, и diff-guard черновика (`0083`) писал бы на каждом тике простоя.
