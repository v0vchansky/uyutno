## Описание

Задача проводит границу, которую ADR 0021 формулирует одной строкой: **политика — в планере, транспорт и `localStorage` — в платформе**. Здесь заводится и то, и другое: DI-проп `storage` (платформа реализует) и неймспейс `persistence` фасада (планер владеет).

Обещание пропа висит с шага 1: ADR 0015 A8 прямо говорит, что `storage` появится в шаге 3 «тем же способом», а `createPlanner` до сих пор заводит пустой документ внутри. Планер не читает `useRegistry()`, cookies, URL и `window`-глобалы — всё внешнее приезжает пропом.

### Проп `storage`

Форма — из ADR 0021, дословно:

```ts
storage: {
  load(projectId),
  save(projectId, document, { autosave }),
  loadDraft,
  saveDraft,
  clearDraft,
}
```

- Проп **необязателен**: без него `persistence` не запускает таймеры, а ручной Save отвечает типизированной ошибкой «сохранять некуда». Это сохраняет нынешнее поведение (`/project/:id` без сохранения) на время, пока `0085` не подключит загрузку, и даёт headless-тестам движка работать без фейкового транспорта.
- **Draft-методы задействует только демо** (`loadDraft`/`saveDraft`/`clearDraft`). У обычного проекта локальной копии нет вовсе — серверный автосейв её дублирует, а взамен приносит развилку «локальное против серверного» при каждом открытии. В типе они опциональны; вызывать их `persistence` вправе только в режиме черновика.
- Проп прокидывается через `PlannerProps` → `CreatePlannerParams` → `PlannerManager`, как `logger`. Смена ссылки на `storage` **не пересоздаёт планер** (то же правило, что у `logger`): новые вызовы уходят в актуальную реализацию.
- Реализация транспорта на стороне платформы (HTTP-клиент из `core`, эндпоинты `0080`) — минимальная, ровно чтобы `persistence` было с чем разговаривать. Полноценный путь открытия проекта со всеми фазами и модалками — `0085`, черновик — `0083`.

### Неймспейс `persistence`

Ещё один неймспейс фасада рядом с `document`, `view`, `history`, `tools` — по общему правилу «неймспейс = один домен, его события — префикс `ns:` в карте шины» (ADR 0015 A2). Скоуп именно этой задачи — **механика**, без таймеров и без веток пользовательских сообщений (те — `0082`):

1. **Состояние и его чтение.** `persistence.getState()` → статус (`idle` / `saving` / `saved` / `error` / `offline`), метка времени последнего успешного сохранения, последняя ошибка, признак «есть несохранённые изменения». Событие шины на каждое изменение состояния — им живёт UI (`0084`) и `usePlannerSelector`.
2. **Точка входа сохранения.** Один метод с явной причиной (`manual` / `autosave` / `draft`) — чтобы ветки не расползлись по вызывающим. Возвращает `Result` (ADR 0015 A2): исключений наружу нет.
3. **Dirty-гейт.** Сохранение не уходит, если флаг не поднят. Флаг уже живёт в `PlannerStore` (D7): `document.isDirty()` / `markSaved()` / событие `document:dirty-changed`.
   - **Dirty ставят изменения `settings` и `floors`; `view` — нет.** Иначе пан и зум камеры дёргали бы автосейв при простом разглядывании плана; камеры доезжают на сервер попутно с ближайшей содержательной правкой. По коду это уже так (`ViewNamespace` — `history: 'none'` и вне dirty, D3/D7) — задача обязана **закрепить это тестом**, а не считать данностью: правило легко потерять при первой же правке `ViewNamespace`.
4. **Очередь запросов.** Пока один запрос в полёте, второй ждёт; в UI это единый статус «идёт сохранение» (спека 10, «Крайние случаи»). Одновременный ручной save и автосейв не должны давать двух параллельных `PUT`. Схлопывание: если в очереди уже стоит сохранение, второе не добавляется третьим — уходит один запрос с актуальным состоянием.
5. **Откладывание на drag.** Save во время активного drag/трансформации откладывается до отпускания мыши, чтобы не писать промежуточную геометрию. Если пользователь держит мышь дольше следующего тика таймера — тик **тихо пропускается**; при отпускании save запускается на ближайшем тике, **не сразу**. Ручной Ctrl+S во время drag — та же логика. Источник факта «идёт drag» — автомат инструментов (`tools`: `dragging-point`, `dragging-wall` и состояния рисования); неймспейс читает его, а не заводит свой флаг.
6. **`markSaved` по успеху** и сохранение серверного `updatedAt` рядом с состоянием — сервер возвращает его в ответе на save (ADR 0021). На этом стоит будущее предупреждение о конкурентной записи, которого в v0 нет.

Не в задаче: периоды таймеров, гейты автосейва, ветки ошибок и офлайна (`0082`); реализация черновика (`0083`); индикатор и модалки (`0084`); путь открытия проекта (`0085`).

## Приёмка

- [ ] `storage` принимается `<Planner />` и `createPlanner`, доезжает до `PlannerManager`; форма пропа совпадает с ADR 0021 дословно (`load`, `save(projectId, document, { autosave })`, `loadDraft`, `saveDraft`, `clearDraft`).
- [ ] Планер без `storage` поднимается и работает как сейчас; ручной Save отвечает типизированной ошибкой, таймеры не заводятся.
- [ ] Смена ссылки на `storage` не пересоздаёт планер (тест — по образцу теста на `logger`).
- [ ] Неймспейс `persistence` есть в публичном API пакета: состояние читается, событие шины эмитится ровно один раз на изменение состояния, типы ошибок экспортированы из `index.ts`.
- [ ] Сохранение не уходит при снятом dirty-флаге — тест.
- [ ] **`view.setCamera` и `view.setActive` dirty не поднимают**; `document.setSettings` и команды планировки — поднимают. Отдельный тест на каждую ветку.
- [ ] Очередь: два сохранения подряд дают **один** запрос в полёте, второй уходит после ответа первого; параллельных `PUT` не бывает — тест на фейковом `storage` с управляемым промисом.
- [ ] Откладывание на drag: сохранение, запрошенное в состоянии `dragging-*`, до отпускания не уходит; тик таймера в этом состоянии пропускается тихо; после отпускания сохранение уходит на ближайшем тике, а не немедленно.
- [ ] `markSaved` вызывается только по успеху; при ошибке dirty остаётся поднятым.
- [ ] `updatedAt` из ответа сервера сохраняется в состоянии неймспейса и читается наружу.
- [ ] Планер по-прежнему не читает `window`-глобалы, cookies и URL — всё внешнее через `storage` (ADR 0015 A8).
- [ ] `pnpm typecheck`, `pnpm lint`, `pnpm test` зелёные.
- [ ] Prettier чист; ровно один PR.

## Заметки

- **Почему политика в планере, а транспорт в платформе.** Планер знает, _когда_ сохранять (dirty, drag, очередь) — это часть его состояния; _куда_ и _чем_ — знает платформа (HTTP-клиент, `localStorage`, авторизация). Обратное расположение затащило бы в пакет знание об эндпоинтах и сессии.
- **Условие «текущий пользователь — владелец»** спека 10 выносит как защитный инвариант на будущее, а не как третье условие гейта: чужие проекты открыть нельзя (`0063`). В коде это не проверка, а комментарий у гейта.
- **`beforeunload` не вешаем** (ADR 0021) — ни здесь, ни в `0082`. Цена решения (закрыть вкладку в офлайне = потерять несохранённые правки) осознанная, пользователь предупреждён постоянным статусом в шапке.
