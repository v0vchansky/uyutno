## Описание

Ручки «один проект по id» в REST проектов нет. В `src/server/projects/router.ts` зарегистрированы
`GET /`, `POST /`, `PATCH /:id`, `POST /:id/duplicate`, `DELETE /:id`, `GET /:id/document`,
`PUT /:id/document` — и всё. Предпосылка задачи проверена по коду и подтвердилась.

Из-за этого первая фаза открытия проекта (`useProjectOpen`, задача 0085) и имя в шапке редактора
(`EditorHeader`, задача 0088) берутся из **списка всех проектов пользователя**: клиент делает
`GET /api/v1/projects`, ищет в ответе нужный id и считает его отсутствие признаком «проекта нет».

Что в этом плохо:

- открытие одного проекта тянет с сервера всю библиотеку планов пользователя ради одного имени —
  на десятке проектов незаметно, на сотне уже нет;
- признак «проекта не существует» — отсутствие строки в списке, а не ответ сервера. Для v0 множества
  совпадают (чужие проекты в список не попадают), но это совпадение, а не контракт.

Что в этом хорошо и **терять нельзя**: список уже загружен галереей, ключ кеша у шапки и у галереи
общий (`PROJECTS_QUERY_KEY`), поэтому переименование из редактора инвалидирует один ключ и обновляет
разом и шапку, и галерею.

ADR 0021 такую ручку прямо предполагает: «Отдельный `GET` [документа] — не стилистический выбор: он
мигрирует и пишет, поэтому не может ни жить внутри `GET /projects/:id`, **который обязан оставаться
лёгким**, ни кешироваться». То есть лёгкий `GET /projects/:id` в решении заложен, просто не заведён.

### Что делаем

**Сервер.** `GET /api/v1/projects/:id` — метаданные одного проекта владельца, тем же телом
`{ project }`, что отдают `POST /` и `PATCH /:id`. Документ и превью в ответ не попадают: они тяжёлые
и ездят своими эндпоинтами. Явная проекция колонок обязательна (`PROJECT_COLUMNS`, задача 0078),
`selectAll()` не заводить — репозиторный метод `findByIdForUser` уже есть и уже проецирует явно.

Чужой и несуществующий проект неразличимы — оба дают `404` одним и тем же телом, ровно как это
сделано для `GET …/document` задачей 0080: владение зашито в `where` выборки, «строки нет» → 404.

Рейт-лимит — **тот же экземпляр**, что у `GET …/document`: оба запроса обслуживают одно
пользовательское действие (открыть проект), и счётчик у него должен быть один. Новый экземпляр с теми
же числами удвоил бы разрешённое: счётчик живёт в замыкании `rateLimit`.

**Клиент.** Первая фаза открытия (`useProjectOpen`) переезжает на новую ручку: `not-found` становится
честным `404` от сервера, а не «не нашлось в галерее».

Связь с галереей сохраняется ключом кеша: ключ карточки — **потомок** ключа списка
(`['projects', 'detail', id]` при `PROJECTS_QUERY_KEY = ['projects']`). React Query инвалидирует по
префиксу, поэтому уже существующий `invalidateQueries({ queryKey: PROJECTS_QUERY_KEY })` в
`RenameProjectModal` продолжает обновлять и галерею, и карточку — трогать модалку не нужно.

**Чего в задаче нет.** `EditorHeader.tsx` лежит в `client/project/components/EditorShell/**` — зоне
параллельной задачи 0093, и в этой задаче не правится. Пока он не переключён на новую ручку, запрос
списка при открытии редактора остаётся (его делает шапка, не фаза загрузки). Остаток описан в
«Заметках».

## Приёмка

- [ ] `GET /api/v1/projects/:id` отдаёт владельцу `200 { project }` с `id`, `name`, `createdAt`, `updatedAt`
- [ ] документа и превью в ответе нет; выборка идёт явной проекцией колонок, без `selectAll()`
- [ ] чужой и несуществующий проект дают `404` с **одинаковым** телом
- [ ] без сессии — `401`
- [ ] маршрут висит на том же экземпляре рейт-лимитера, что `GET …/document` (общий счётчик, а не второй такой же)
- [ ] первая фаза `useProjectOpen` ходит в новую ручку; `not-found` приходит `404`-ответом сервера
- [ ] переименование по-прежнему обновляет и шапку редактора, и галерею
- [ ] тесты: серверный контур ручки + клиентский запрос; существенные написаны красными до реализации
- [ ] прогоны зелёные: typecheck, lint, test, e2e; format не сломан

## Заметки

**Бюджет рейт-лимита чтения поднят со 120 до 240.** Число назначалось задачей 0080 как «120 открытий
проекта за 10 минут» — но открытие тогда стоило один запрос (`GET …/document`), а теперь стоит два
(карточка + документ) на том же счётчике. Оставить 120 значило бы вдвое урезать потолок самого
действия, поэтому изменено число, а не число счётчиков: потолок в открытиях остался прежним.

Измерено на живом сервере: полный прогон e2e (56 тестов, ~50 открытий) тратит **101** запрос из 240 —
ровно два на открытие, лишних рефетчей нет.

**Карточке проставлены `staleTime: Infinity` и выключены `refetchOnWindowFocus`/`refetchOnReconnect`** —
та же дисциплина, что у документа. Без этого запрос карточки, в отличие от прежнего похода в
нелимитированный список, тратил бы бюджет на каждом возврате фокуса во вкладку. Переименование это не
ломает: `invalidateQueries` перечитывает активные запросы независимо от `staleTime` (проверено вживую —
после `PATCH` уходят оба запроса, и списка, и карточки).

**`repeat` в `projectsApi.test.ts` переведён с `Promise.all` на последовательный цикл**: залп из 240
параллельных `fetch` упирается в сокеты, а не в лимитер, и рвётся с `ECONNRESET`.

**Осталось за границей задачи — шапка редактора.** `EditorHeader.tsx` лежит в
`client/project/components/EditorShell/**`, зоне параллельной задачи `0093`, и не тронут. Он
по-прежнему берёт имя из `GET /api/v1/projects`, поэтому запрос списка при открытии редактора никуда
не делся — его делает шапка, а не фаза загрузки. Переключение — четыре строки, зона освободится:

```tsx
// было
const query = useQuery<ProjectDto[]>({ queryKey: PROJECTS_QUERY_KEY, queryFn: getProjects });
const project = query.data?.find(item => item.id === projectId) ?? null;

// станет
const query = useQuery({ queryKey: projectQueryKey(projectId), queryFn: () => getProject(projectId) });
const project = query.data ?? null;
```

Оба хука сядут на один ключ, react-query их склеит, и открытие проекта останется в тех же двух
запросах. После этого `getProjects`/`PROJECTS_QUERY_KEY` перестанут быть нужны модулю `project`.

**Расхождений со спекой и ADR нет.** ADR 0021 («Хранилище и API») эту ручку прямо предполагал —
«`GET /projects/:id`, который обязан оставаться лёгким», — но она не была заведена; задача её и
заводит, ничего не переоткрывая.
