## Описание

Добавление VK ID как второго OAuth-провайдера поверх скелета, поднятого в 0015. Здесь только то, что специфично для VK; общий контроллер, cookie `oauth_state`, обработка коллизий email и `from` уже готовы.

### Backend (`src/server/auth/oauth/`)

- Реализация `VkProvider implements OAuthProvider` — использует креды из `process.env` (0021). Особенности VK:
  - email приходит в теле token-response, а не в userinfo;
  - у части пользователей email может отсутствовать — в этом случае возвращаем `email: null`.
- Зарегистрировать `VkProvider` в маппинге провайдеров, чтобы контроллеры из 0015 начали принимать `:provider = 'vk'`.
- В контроллере `/auth/callback/:provider` добавить ветку «email пуст (сценарий VK) → редирект на `/login?error=oauth_no_email&from=…`».

### Frontend

- В `LoginPage` и `RegisterPage`: включить кнопку VK ID (снять disabled/скрытие, введённое в 0015). Ссылка ведёт на `/api/v1/auth/oauth/vk/start?from=<current-from>`. Иконка — официальный SVG из 0021.
- В `LoginPage` — обработка `?error=oauth_no_email` (плашка над кнопкой: «У вашего аккаунта VK нет привязанного email, войдите через email/пароль»). Обработка `?error=oauth_email_taken` уже есть с 0015 — проверить, что текст плашки корректен и для VK.

### Приёмка UI (Playwright MCP)

Полный e2e с реальным VK-аккаунтом через Playwright автоматизировать невозможно. Приёмка — вручную:

- Пройти вход через тестовый VK ID.
- Проверить сценарий коллизии email: локальная учётка `test@…`, попытка входа через VK ID с тем же email — плашка на `/login`.
- Проверить сценарий VK без email — плашка `oauth_no_email` на `/login`.
- Проверить, что `from` доживает до конца flow.
