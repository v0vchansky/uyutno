## Описание

Написать ADR по геометрическому ядру планера (кандидат **C** из build-order) и открыть его на обсуждение. Кода в этой задаче нет — только `docs/adr/00NN-*.md` (ожидаемо 0017), обновление индекса ADR и парковка. Это самое дорогое для отката решение шага 2: от него зависят все производные сущности (стены-тела, комнаты, оси), формат golden-фикстур, а через них — undo (ADR D), проёмы (шаг 6), меши (ADR G), материалы (ADR J).

Это бриф сессии: читать целиком перед стартом, работать по нему, не расширять скоуп. Разделение с 0052 (ADR D + E): C — чистая математика без Three/DOM и без понятий «инструмент»/«мышь»/«история»; всё про транзакции, снапшоты, FSM и ввод — 0052.

### Что решаем

**ADR C — Геометрический пайплайн планера** (ожидаемо 0017):

1. **Место и форма ядра.** `document/geometry/` (ADR 0015: plain-данные и чистые функции, без Three/DOM/React, тесты в Jest node). Вход — `FloorLayout` (замороженный снимок, `Record<Id, Point>` + контуры по id), выход — plain-структуры для `DerivedState` (ADR 0016 «выводится, не сериализуется»): стены-тела, комнаты (полигоны с дырками + триангуляция), оси, а также результат **нормализации хранимого** (что `normalize()` дописывает/удаляет в `layout` до фиксации снимка — 0048 «две фазы rebuild»). **Что такое «стена-тело» для 2D-отрисовки** — определить явно (README: толщина не хранится, стена — «мясо между гранями»; кандидат — треугольники, классифицированные как `empty`/не-комната между контурами в проходе fill/hole/empty dd01; per-face лента — только для live-превью рисования), иначе 0054 и 0056 разойдутся. Что именно входит в `DerivedFloor` для шага 2 (стены-тела, комнаты, оси) и что появится позже без смены формы (дырки проёмов, плинтусы, потолки — ADR G/шаг 6). Никаких объектов с методами и обратных ссылок (аудит: `WC.core`-синглтон, `point.contour`/`areas[]` — drop/rework).
2. **Библиотеки и их обвязка.** `cdt2d` (`{ exterior: true }`) + `clean-pslg` с npm — решено build-order/аудитом (dd01 keep); здесь: зафиксировать версии, свой `.d.ts` (референс: «no types, ~5-line `.d.ts` of our own»), CJS-импорт в ESM-пакете (`packages/planner` — `type: module`, потребление webpack + Jest/SWC), обёртка в чистую функцию с копированием массивов (аудит: `clean-pslg` мутирует вход in place — keep, но обернуть). Порядок обвязки как у dd01 «Pre & post pipeline» (7 шагов: квантование до 0.001 выше по стеку → дедуп точек/рёбер → `resplitSegments` для коллинеарных осевых T-стыков → `clean-pslg` → `cdt2d` → центроид-классификация fill/hole/empty против четырёх наборов контуров outer/inner/bound/subtract → группировка), с оговорёнными rework: дедуп через hash-map по квантованной координате вместо O(V·E) (аудит dd01), явный стек вместо рекурсии в `groupTriangles`/`indicesToPoints` (аудит dd01/dd03 — единственный «landmine»), плоские массивы вместо глобального пула `TR.points`. `constrainautor`+`Delaunator` и Clipper2 — отсекаются одной строкой (выбор `cdt2d`+`clean-pslg` уже сделан build-order/аудитом; Q2 — бэклог).
3. **Эпсилоны и дисциплина вершин.** Два уровня — `L_EPS = 1e-8` (тождество координат, дедуп, параллельность) и `B_EPS = 1e-4` (близость к границе) + правило «общие вершины бит-в-бит через квантование 0.001 и снап пересечений к общим вершинам» (аудит dd08 keep, «работает только в связке»). Убрать третий эпсилон `1e-6` из ray casting (rework). Единицы — см (ADR 0016 B1). Список констант ядра как именованных экспортов (не литералы в 6 местах): `L_EPS`, `B_EPS`, `MIN_CONTOUR_AREA = 50` см², `MIN_SP_RATIO = 1`, `CLEAR_CONTOUR_MIN_LEN = 5`, `TRIANGLE_NARROW = 0.1`, `SORT_AREA_EPS = 10`, `RE_MITER_ANGLE = 0.75π`, `PARALLEL_EPS = 0.05` рад, `MAX_CONNECTOR_LENGTH = 40`, `MAX_WALL_WIDTH = 80`, `MIN_WALL_LENGTH = 15`, `DEFAULT_WALL_WIDTH = 10`, `CLOSE_EPS = 0.1` (спека 01) — где живут (рядом с использованием, `apps/platform/CLAUDE.md`) и что из них — параметр функции, а что константа модуля.
4. **Предикаты и примитивы (dd08 «Сводная таблица», 22 функции).** Какие берём 1:1 с контрактом и тестами по квадрантам (`angleBetweenLines` через `atan2(dx,dy)`, `[0, 2π)`; `parallelLines`; `rightOriented`; `compareContours` с 8 исходами; `compareContoursByArea` 10×10; `contourArea`/`contourValid`; `pointOnContour`; `pointInBounds`; `bisectorPoint`; `segmentsOverlay`; `checkContact`; `sortByArea`), какие переписываем по вердиктам rework аудита dd08: `perpendicularPoint` → нормализованная нормаль `(dy, −dx)/len` с явным enum стороны и гардом нулевой длины; `projectionPointOnLine` — честная проекция через dot product; `pointOnLine` — параметрически `t ∈ [0,1]` с сохранением B_EPS-коридора и одним явным допуском 1 см для коннекторов (Q33); `pointInContour` — стандартный robust ray casting (полуоткрытые рёбра), контракт «сначала boundary, потом in/out»; `lineIntersectLine`/`segmentsIntersected`/`rightOriented` — ориентационный тест через robust `orient2d` (dd08 §9 рекомендует `robust-predicates` — решить: ставим пакет или пишем свой `orient2d`; memory «не изобретать библиотеки»); `compareContoursOnePoint` — полный тип возврата вместо `undefined`; `distanceBetweenPointAndLine` — abs-вариант с гардом. Ядро отдаёт `manhDist`/`euclDist`; **какую метрику применяет снап/хит-тест/замыкание — решает E** (0052), не C.
5. **Лента и митринг (dd02).** Свой per-segment офсет + пересечение, без polygon-offset либы (аудит keep «три правила»): односторонняя лента (одна грань — сама линия контура), выход — независимые per-segment квады `[A, C, D, B]` с переносом `A=C, B=D`; правило митра→плоский торец `ang > 0.75π && ang < 2π − 0.75π` **и** `!pointInBounds` для открытой полилинии, только по углу — для замкнутого контура (Q32, спека 01 «Митра углов»); null-guard при параллельных соседях → butt; гарды коротких сегментов (1 точка → [], 2 точки короче `wallsWidth` → [], последний сегмент открытой полилинии < `wallsWidth` — отбрасывается); butt-капы концов; T-стык `startNeighbSegments` (ближайшее из двух пересечений); `signSide` — авто-выбор до третьей точки, затем фиксация; замкнутость контура — явный признак, а не дубль первой точки (аудит dd02 rework, обход по модулю длины). Знак офсета — явный enum стороны, а не `d/−d`. Квад-стрип как **промежуточный формат golden-фикстур** (аудит dd02). Кто вызывает ленту: инструмент рисования (0052/E) для живого превью и коммит контура (лента → пара контуров граней «полая комната»); после коммита в документе — только контуры граней, толщина не хранится (README).
6. **Детекция комнат (dd03) и порядок пайплайна (03-rooms).** Триангуляция → fixed-рёбра-стены → flood-fill групп (явный стек) → boundary walk каждой группы (старт с min-X, виртуальная prev `[x−10, y]`, выбор соседа по экстремальному углу) → `clearDict` (удаление dead-end вершин степени 1, повторные обходы для дырок) → нормализация ориентации по знаку площади (rework вместо побочного эффекта первого шага) → `clearContour` (слияние вершин ближе 5 см, удаление коллинеарных) → `contourValid` (площадь ≥ 50 см², площадь/периметр ≥ 1); дырка принадлежит комнате по членству в группе; guard runaway walk — soft-fail с логированием. Порядок стадий `rebuildWallsAndCovers` (аудит 03-rooms keep, 03-rooms «`rebuildWallsAndCovers()` orchestration»: `delIntersectedAreas → roundAllPoints → rebuildWalls → rebuildCovers → findAutoCovers → connectAllPoints → findCoverHoles → findAllCoverTriangles`) — зафиксировать как **наш** порядок фаз `normalize`/`rebuild` с оговорками модели ADR 0016: `roundAllPoints` не нужен (квантование в командах фасада — B1), `connectAllPoints` не нужен (общий id точки — B4), зоны проверяются по тождеству координат (Q22). Явно: какие стадии реализуются в шаге 2 (стены, комнаты, оси, авто-полы как минимум?), какие — позже без смены формы (ручные полы, зоны/cuts, плинтусы, потолки) — см. вопрос автору в эпике 0050.
7. **Пере-привязка данных комнат по площади (Q35, спека 02).** `compareContoursByArea` (сетка 10×10 по bbox старой, INTERSECT при ≥ 1 общей точке, первый матч того же outer/hole) — только для переноса атрибутов `rooms[]` (имя, высота, `anchor: Id[]`), не для структурных решений (`compareContours` — для полов/зон). Кто переписывает `anchor` (`normalize` в той же транзакции — 0048), что происходит с записью без донора (новая комната получает высоту проекта — Q20) и с записью, у которой не нашлось новой комнаты (удаляется? остаётся сиротой? — решить). Материалы граней стен по совпадению концов грани — только принцип, схема ключа — ADR J.
8. **Оси стен (dd07).** Производные, без id: `findAxes` O(n²) по парам граней с фильтрами `parallelLines(0.05)` → `rightOriented` → `parallelBox` (4-case overlap, `manhDist(E,F) < L_EPS` — отказ) → `boxCenterSeg` с порогами `MAX_WALL_WIDTH = 80` / `MIN_WALL_LENGTH = 15`; ось на каждую пару граней по участку перекрытия, длинная грань против двух коротких = две оси, слияния нет (Q19); один источник угла и **детерминированное направление оси** (dd07 гэп «стабильность `point1→point2` не доказана» — у нас правило явное, например по внутренней стороне; аудит rework). Индекс проём→ось — производный локальный результат rebuild (не глобальный словарь). Оси **нужны уже в шаге 2**: инпут ширины стены (0060, спека 01 «ширина = сдвиг стороны») читает текущую толщину = глубину оси, плюс golden-кейсы; проёмы (шаг 6) — второй потребитель. Коннекторы/заглушки (`createConnectors`, `MAX_CONNECTOR_LENGTH = 40`) — стадия после осей: форма и правила фиксируются здесь, реализация — шаг 4 (3D).
9. **Полы, зоны, cuts — форма и стадии, не реализация.** Полы — самостоятельные контуры (Q12); `findAutoCovers` (seed inner-контуры комнат, subtract — существующие полы) → дефолтный пол только там, где нет пола; `rebuildCovers` ужимает ручные полы; `findCoverHoles` (порядок smallest-first явным компаратором); merge полов INTERSECT авто / CONTACT — по решению UI (спека 02); осиротевшие внутренние полы удаляются. Зоны: cut-пары как fixed-рёбра, отбраковка при пересечении стен/самопересечении/потере опоры (тождество координат, Q22). **Cuts — явные записи `cuts[]` `{ id, a, b, материал }`** (парковка build-order из ADR 0016): правило владения записью cut на ребре, общем для двух касающихся зон; удаление записи вместе с зоной без опоры; грань и высота cut — производные. Всё это ADR C фиксирует как стадии и инварианты, реализацию — по решению автора о размещении в build-order (вопрос в эпике 0050).
10. **Тестовый контракт: golden-фикстуры и property-тесты (testing-strategy, build-order «для шага 2 сразу golden-фикстуры»).** Формат фикстуры: вход — `PlannerDocument`/`FloorLayout` JSON с полем `version` (формат сейва фиксируется только в ADR F после шага 2 — фикстуры мигрируются вместе с форматом; build-order шаг 3: «сериализованные планы = фикстуры для шага 2») либо in-code билдеры; эталон — сериализованный `DerivedFloor` (или его стата: число комнат, площади, вершины контуров, квады ленты) — не пиксели; где лежат (`packages/planner/src/document/geometry/__fixtures__/`?), как обновляются (явный ревьюируемый шаг), минимальный стартовый набор (spec-derived: замыкание 4 стен → 1 комната; самопересечение → отказ; внутренняя стенка делит комнату; удалил стену — слились; комната в комнате → дырка; висячая стена → нет ложных контуров; T-стык; плоский торец при ≥ 135°; слишком короткий последний сегмент; две коллинеарные короткие грани против длинной → две оси). Property-тесты (`fast-check`, devDep пакета): нет NaN, комнаты — валидные полигоны без самопересечений, `contourValid` для всех комнат, идемпотентность `rebuild(rebuild(x)) == rebuild(x)`, инвариантность к порядку контуров с точностью до перестановки комнат (донор атрибутов — «первый в порядке обхода», спека 02, поэтому при равном входе детерминирован, при перестановке может смениться — зафиксировать явно). Правило «вся математика и все ветки» — по каждому предикату (обе стороны каждого порога, вырожденные входы, знак/ориентация).
11. **Производительность — явно не решаем.** Полный синхронный recompute на коммит (Q23, парковка build-order); никаких пространственных индексов/debounce/worker (аудит dd08 keep «O(n·m) везде»); bbox-prefilter в классификации точек — допустимая деталь реализации, не архитектура.

**Строки парковки build-order, адресованные C (перенести в решение, источник указан):**
