## Описание

`errorMiddleware` распознаёт только наши `AppError`, а всё остальное сводит к `500 Internal server error`. Из-за этого ошибки, которые порождает сам Express, приходят клиенту не тем, чем являются.

Самый заметный случай — `entity.too.large` от `express.json({ limit: '10mb' })`: запрос сверх лимита должен получить `413`, а получает невнятную пятисотку. Клиент не может отличить «ты прислал слишком много» от «у нас упал сервер» и, соответственно, не может показать пользователю осмысленный текст. Тем же путём теряются и другие ошибки парсера тела — например, битый JSON, который должен быть `400`.

Найдено 2026-08-20 при подготовке ADR F (шаг 3 планера): там лимит на размер документа — часть решения, и выяснилось, что механизм отдачи 413 у нас не работает. Но дефект к планеру отношения не имеет и чинится независимо от него — сохранение документа лишь первый сценарий, где это станет заметно пользователю.

Смежное, что уже есть и переиспользуется: `express-rate-limit` в платформе и `TooManyRequestsError` в `common/errors.ts`.

## Приёмка

- [x] Ошибки Express с собственным `status`/`statusCode` (как минимум `entity.too.large` и ошибки парсинга JSON) отдаются клиенту своим кодом, а не `500`.
- [x] Тело ответа — в том же формате, что и у наших `AppError`; клиент не должен различать источник ошибки по форме ответа.
- [x] Неопознанная ошибка по-прежнему становится `500`, и её детали по-прежнему не утекают наружу.
- [x] Тест на 413 (тело сверх лимита) и на битый JSON.
- [x] `pnpm typecheck`, `pnpm lint`, `pnpm test` зелёные.

## Заметки

Сделано: `errorMiddleware` берёт статус из `status`/`statusCode` (целое 400–599), если ошибка не наш `AppError`. Сообщение чужой ошибки выносится наружу только при `expose === true` — это контракт `http-errors`, где `expose` true ровно у 4xx (текст про запрос клиента); для 5xx и всего сомнительного в тело идёт сухая строка `STATUS_CODES[status]`, детали — только в лог. 4xx логируются как info, 5xx — как error со стеком, как и раньше. Формат тела прежний: `{ error }` плюс `code` только у наших `AppError` (`type` вроде `entity.too.large` наружу не выносится — статуса достаточно).

Задача заведена по ходу подготовки ADR F, но от шага 3 не зависит и не блокирует его. Обратное тоже верно: ADR F вправе назначать лимит размера документа, не дожидаясь этой задачи, — она лишь чинит доставку кода ошибки клиенту.
