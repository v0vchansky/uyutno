## Описание

Первая из двух «нижних» задач шага 3 (вторая — `0079`, они независимы). Даёт документу планера место в базе и **закрывает условие, на котором принято хранение в колонке**: список проектов не должен таскать документы.

Сейчас в `projects` пять колонок (`id`, `user_id`, `name`, `created_at`, `updated_at`), а обе выборки репозитория идут через `selectAll()`. Как только рядом ляжет `document JSONB` с сотней килобайт на строку, `GET /api/v1/projects` начнёт вытягивать из базы всю библиотеку планов пользователя ради сетки карточек — ровно тот сценарий, из-за которого альтернативу «отдельная таблица 1:1» и отсекли (ADR 0021, «Почему»: её единственный плюс даёт явная проекция колонок). Поэтому проекция — не уборка по ходу, а часть решения.

Скоуп:

1. **Миграция dbmate** (`apps/platform/db/migrations/`, `pnpm --filter platform db:new`): `ALTER TABLE projects ADD COLUMN document JSONB`, `ADD COLUMN preview TEXT`. Обе — nullable: существующие строки документа не имеют, и `POST /api/v1/projects` его тоже не пишет (проект создаётся пустым, документ приезжает первым `PUT`). `-- migrate:down` снимает обе колонки.
   - **Тип `preview` — именно `text NULL`, не `bytea`.** Обоснование в ADR 0021: колонка примет и путь к файлу, и data-URL, а чем её наполнять — решает шаг 9 (снимок превью). `bytea` сейчас означал бы принять это решение, не имея ни одного его требования.
   - Индексов по новым колонкам не заводить: по документу не ищут, превью читается вместе с карточкой.
2. **Кодоген Kysely**: `pnpm --filter platform db:codegen` → обновлённый `src/server/postgres/db.generated.ts` в коммите. Проверить, что тип `document` вышел как JSON-значение, а не `string`, и что он не сломал существующие места.
3. **Явная проекция колонок вместо `selectAll()`** в `projectsRepository` — **два места, названные ADR 0021 поимённо**: `listByUser` и `findByIdForUser`. Обе выбирают ровно `id, user_id, name, created_at, updated_at`.
4. **Тем же правилом — `returningAll()`**: `create` и `renameForUser` возвращают строку целиком, то есть после миграции потянут и `document`, и `preview`. ADR формулирует правило как «явная проекция во всех выборках `projects`, кроме чтения самого документа», поэтому оба `returningAll()` заменяются на явный `returning([...])` с тем же набором колонок. Это не расширение скоупа, а тот же пункт: `renameForUser` иначе на каждое переименование вычитывает мегабайтный документ.
5. **`ProjectRow` и `ProjectDto` не расширяются** полями `document`/`preview`. Документ читается своим методом репозитория (заводит `0080`), превью — шагом 9. Тип строки списка обязан остаться лёгким, иначе проекция потеряется при первом же рефакторинге.

Не в задаче: методы чтения/записи документа в репозитории, эндпоинты, валидация конверта — всё это `0080`; наполнение `preview` — шаг 9; копирование колонок при `duplicate` — `0087`.

## Приёмка

- [ ] `pnpm --filter platform db:up` применяет миграцию на чистой и на существующей базе; `db:status` чист; `-- migrate:down` откатывает обе колонки и прогоняется без ошибок.
- [ ] Колонка `document` — `JSONB NULL`, колонка `preview` — `TEXT NULL`; ни одна не `NOT NULL` и ни одна не имеет дефолта.
- [ ] `db.generated.ts` перегенерирован кодогеном (не правлен руками) и лежит в коммите; `pnpm typecheck` зелёный.
- [ ] `listByUser` и `findByIdForUser` выбирают явный список колонок; `selectAll()` в `projectsRepository` не осталось.
- [ ] `create` и `renameForUser` возвращают явный список колонок; `returningAll()` в `projectsRepository` не осталось.
- [ ] Тест, который **падает при возврате к `selectAll()`**: скомпилированный Kysely-запрос (`.compile().sql`) обеих выборок не содержит `document` и не содержит `*`. Обещания в комментарии недостаточно — проекция обязана быть проверяемой.
- [ ] `ProjectRow`/`ProjectDto` не содержат `document`/`preview`; существующие тесты `ProjectsManager` зелёные без правок ожиданий.
- [ ] `pnpm typecheck`, `pnpm lint`, `pnpm test` зелёные.
- [ ] Prettier чист; ровно один PR.

## Заметки

- **Про bloat таблицы от частых `UPDATE` замера нет.** Поведение TOAST при документе ~118 КБ (порог вынесения — 2 КБ) — предположение, а не измерение (ADR 0021, «Что важно знать»). Ни в этой задаче, ни в `0080` не выдавать его за факт и не строить на нём решений; понадобится — меряем отдельно.
- **Кто ставит `updated_at`.** Колонка живёт с `DEFAULT now()`, а обновляется только явным `set({ updated_at: new Date() })` — триггера в базе нет. Это важно для `0080`: служебная перезапись документа после миграции обязана `updated_at` **не трогать**, и по нынешней схеме для этого достаточно его не передавать. Если в этой задаче появится соблазн завести триггер `updated_at` на `UPDATE` — нельзя, он сломает требование ADR.
