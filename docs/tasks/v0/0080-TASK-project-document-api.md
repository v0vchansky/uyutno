## Описание

Задача сводит вместе результаты `0078` (колонка) и `0079` (модуль формата): документ получает свою пару эндпоинтов, а сервер — способность мигрировать документы самостоятельно.

Зависимость **от обеих** предыдущих задач не формальная: миграцию на чтении выполняет сервер, вызывая `migrate` из `@uyutno/planner/format`. Без колонки писать некуда, без модуля формата — нечем валидировать и нечем мигрировать.

### Почему документ ездит отдельной парой эндпоинтов

Не стилистический выбор (ADR 0021): `GET …/document` **мигрирует и пишет**, поэтому не может ни жить внутри `GET /projects/:id` (тот обязан оставаться лёгким), ни кешироваться. Заодно это ровно те две фазы, которые бриф оболочки требует показывать при открытии проекта: сперва карточка проекта, затем документ.

### `GET /api/v1/projects/:id/document`

1. Авторизация и владение: `requireAuth('api')`, выборка по паре `(id, user_id)`. Чужой или несуществующий проект — `NotFoundError` → 404, без различия между «не твой» и «нет такого».
2. Документ из колонки → `migrate(raw)` из `@uyutno/planner/format`.
3. **Если `migrate` что-то изменил — колонка перезаписывается сразу**, и клиенту уходит уже мигрированный документ. Клиент старых версий формата не видит вовсе.
4. **Служебная перезапись не двигает `updated_at`.** Иначе после выката новой версии формата достаточно полистать старые проекты, чтобы галерея, отсортированная по дате изменения, перетасовалась сама собой. По нынешней схеме (`0078`) для этого достаточно не передавать `updated_at` в `set` — триггера в базе нет.
5. **Не удалась запись — документ всё равно отдаётся мигрированным**, ошибка логируется, следующее чтение попробует снова: `migrate` детерминированная и переживает повтор. Ответ пользователю в этом случае успешный.
6. Ответ: `{ document, updatedAt }`. `updatedAt` нужен клиенту как метка серверного снимка.
7. Заголовок `Cache-Control: no-store` — запрос пишущий, кешировать его нельзя.
8. Колонка пуста (`NULL`) — проект создан, но ни разу не сохранён. Отдавать в этом случае `404` **нельзя**: пользователь просто открыл новый проект. Ответ — `{ document: null, updatedAt }`, клиент поднимает пустой документ (`createEmptyDocument`) сам. Форму зафиксировать в общей zod-схеме ответа в `src/shared/projects/`, чтобы клиент не гадал.

### `PUT /api/v1/projects/:id/document`

Тело: `{ document, autosave?: boolean }` — документ целиком. Порядок проверок:

1. `requireAuth('api')` + владение → 404.
2. **Лимит 2 МБ по сырому телу запроса**, а не по разобранному объекту (см. «Лимит» ниже).
3. Валидация конверта zod-схемой из `@uyutno/planner/format`. Невалидный — `ValidationError` → 400.
4. **Отказ, если пришедшая `version` ниже сохранённой** — версия только растёт. Это единственная дыра, которую last-write-wins не закрывает сам: вкладка со старым бандлом, досылая свой автосейв, вернула бы документ на предыдущий формат, потеряв всё, что записала вкладка с новым. Обычную потерю правок спека приняла осознанно, регресс формата — нет. Код ответа — `409` (`ConflictError`), с внятным сообщением: клиенту нужно понять, что надо перезагрузить страницу, а не что «сервер сломался».
5. Запись документа + `updated_at = now()` — **настоящее сохранение дату меняет** (в отличие от служебной перезаписи на чтении).
6. Ответ: `{ updatedAt }`. Клиент кладёт его рядом с состоянием; на этом стоит будущее предупреждение о конкурентной записи, которого в v0 нет.
7. Флаг `autosave` в v0 на поведение сервера не влияет — он нужен логам и будущему разведению лимитов; принимать и не терять.

**Конкурентная запись из двух вкладок — last-write-wins без предупреждения** (выбор спеки 10). `revision`, ETag и optimistic locking не заводим.

### Лимит 2 МБ — ловушка порядка middleware

Считается **по сырому телу запроса**. В `server.ts` парсер стоит глобально (`app.use(express.json({ limit: '10mb' }))`) **до** роутеров, поэтому просто повесить `express.json({ limit: '2mb' })` на маршрут документа **недостаточно**: глобальный парсер разберёт тело первым, пометит запрос разобранным, и роут-локальный парсер молча пропустит его. Маршрут документа надо либо смонтировать до глобального парсера, либо исключить из него (`type`-предикат по пути) — способ на выбор исполнителя, но **приёмка проверяет результат**: тело 3 МБ на `PUT …/document` даёт 413, а не 200. Глобальные 10 МБ для прочих маршрутов остаются как есть.

**Зависимость от [0076](0076-TASK-error-middleware-express-errors.md):** `errorMiddleware` знает единственную ветку `err instanceof AppError`, а `entity.too.large` от `raw-body` наследником `AppError` не является — сегодня 413 приходит клиенту как `500 Internal server error`. Без `0076` лимит бесполезен для пользователя: отличить «документ слишком большой» от «сервер упал» клиент не сможет. Если `0076` к моменту выполнения ещё не закрыта — записать это ограничение в «Заметки» задачи и в приёмку `0077`, а не чинить `errorMiddleware` заходом отсюда.

### Рейт-лимит

Квоты на число проектов нет (замер: полсотни проектов — меньше мегабайта в базе на пользователя, ограничивать нечего). Вместо неё — рейт-лимит; инфраструктура готова (`express-rate-limit`, `TooManyRequestsError`, образец — `auth/middleware/loginRateLimit.ts`). **Числа назначаются этой задачей:**

| Маршрут                             | Окно     | Лимит | Ключ                  | Откуда число                                                        |
| ----------------------------------- | -------- | ----- | --------------------- | ------------------------------------------------------------------- |
| `PUT /api/v1/projects/:id/document` | 10 минут | 60    | id пользователя       | автосейв даёт 10 за окно; запас ×6 на ручные Save и вторую вкладку  |
| `GET /api/v1/projects/:id/document` | 10 минут | 120   | id пользователя       | открытие проекта — единичное действие; запас на перезагрузки и demo |
| `POST /api/v1/projects`             | 1 час    | 60    | id пользователя       | создание проектов — редкое действие; «Save As» укладывается         |
| `POST /api/v1/projects`             | 1 час    | 120   | IP (`ipKeyGenerator`) | второй контур от массового создания с одного адреса                 |

Ключ по пользователю берётся из `req.user` (гарантирован `requireAuth`), фолбэк на IP — как в `loginEmailRateLimit`. Ответ при отказе — `TooManyRequestsError` с человекочитаемым текстом.

### Раскладка кода

По конвенциям `src/server/CLAUDE.md`: методы чтения/записи документа — в `projectsRepository` (`findDocumentForUser`, `updateDocumentForUser` с флагом «трогать ли `updated_at`»), логика — в `ProjectsManager`, контроллеры `getProjectDocumentController` / `updateProjectDocumentController` фабриками `create*`, маршруты — в `projects/router.ts`. Схемы запроса/ответа — в `src/shared/projects/` рядом с существующими; конверт валидируется схемой из `@uyutno/planner/format`, а не переписывается в `shared`.

Не в задаче: клиентские вызовы этих эндпоинтов (`0081`/`0085`), копирование документа при `duplicate` (`0087`), наполнение `preview` (шаг 9), правка `errorMiddleware` (`0076`).

## Приёмка

- [ ] `GET /api/v1/projects/:id/document` отдаёт документ владельцу; чужой и несуществующий проект — 404 без различия.
- [ ] `GET` прогоняет `migrate`; при `changed: true` колонка перезаписана, и **`updated_at` не изменился** — проверено тестом, сравнивающим значение до и после.
- [ ] Неудачная перезапись после миграции не ломает ответ: клиент получает мигрированный документ и статус 200, ошибка ушла в логгер — отдельный тест с падающей записью.
- [ ] `GET` отвечает `Cache-Control: no-store`.
- [ ] Пустая колонка (`NULL`) даёт `{ document: null }` и 200, а не 404.
- [ ] `PUT` сохраняет документ владельцу и двигает `updated_at`; ответ содержит новый `updatedAt`.
- [ ] `PUT` с `version` ниже сохранённой отвергается 409 — отдельный тест; `version` равная и большая проходят.
- [ ] `PUT` с невалидным конвертом (нет `format`, нет `floors`, мусор вместо объекта) отвергается 400.
- [ ] **Тело 3 МБ на `PUT …/document` даёт 413**, а не 200 и не 500 (при закрытой `0076` — JSON-ошибка; при незакрытой — факт зафиксирован в «Заметках» и в приёмке эпика). Тело 1 МБ проходит. Глобальный лимит 10 МБ на прочих маршрутах не изменился — проверено на любом другом эндпоинте.
- [ ] Рейт-лимиты по таблице выше стоят на трёх маршрутах; превышение даёт 429 с `TooManyRequestsError` — по тесту на каждый лимит.
- [ ] `POST /api/v1/projects` (создание) продолжает работать в пределах нового лимита; существующие тесты `ProjectsManager` зелёные.
- [ ] Сервер не тянет Three: импорт в серверном модуле идёт из `@uyutno/planner/format`, а не из `@uyutno/planner` — проверено линтером или тестом-гвардом из `0079`.

## Заметки

- **`GET` документа — пишущий запрос, и это осознанно.** Два одновременных чтения одного проекта могут оба мигрировать и оба записать, но результат `migrate` детерминирован, поэтому пишут они одно и то же и гонка безвредна. Транзакция и блокировка тут не нужны — а вот делать `GET` кешируемым нельзя.
- **Сервер физически не может отстать от клиента.** Платформа — Express и React SSR в одном процессе (ADR 0003), клиент и сервер выкатываются одним куском; у пользователя в закешированной вкладке бандл бывает старее серверного, но никогда не новее. Поэтому классическое возражение «схема на сервере тормозит эволюцию формата» у нас не работает, и миграция живёт на сервере.
- **Про bloat таблицы от частых `UPDATE` замера нет** — поведение TOAST при документе ~118 КБ предположение, не измерение (ADR 0021). Не проектировать под него и не выдавать за факт.
- **Вес документа известен:** замер живого плана конкурента 2026-08-20 — ~118 КБ минифицированного JSON и ~15 КБ под gzip на полноценную квартиру, наш формат скупее. Лимит 2 МБ — с запасом более чем на порядок.
